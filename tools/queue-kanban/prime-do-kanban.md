# Prime: do-kanban

queue-kanban — standalone Go module (`tools/queue-kanban/`, own `go.mod`) that walks the version-controlled `do-work/` Markdown tree and renders it as a Kanban board + completion calendar. Subcommands: `summary` | `generate --out DIR` | `serve` | `next-req` | `next-version <patch|minor|major>` | `verify` | `now` (the last four serve the release ritual and the Timestamp rule, not the board). It ships as part of the do-work skill and rides its version bumps; the ergonomic entry point is the `do-work board` action (`actions/board.md`), which builds and runs it for you.

## Read first
- `main.go` — subcommand dispatch + flags (`--repo-root`, `--out`, `--port`; `--recent-window` on summary only, `--version-file` on next-version only)
- `allocate.go` — `next-req`: max REQ number + 1 across queue/working/archive, built on `enumerateDoWorkTree`
- `release.go` — the `**Current version**: X.Y.Z` line reader/bumper/writer and the `CHANGELOG.md` entry parser
- `verify.go` — the read-only invariant probes and their report (wired into `actions/forensics.md` Check 14)
- `timestamp.go` — `now`: the Timestamp rule's UTC stamp (`actions/work-reference.md`), the only subcommand that reads a clock instead of the tree and so takes no `--repo-root`
- `walk.go` — repo-root resolution (walks up for `do-work/`) + tree enumeration
- `model.go` — Board model; column bucketing driven by REQ status
- `generate.go` — static self-contained site; `//go:embed web/` + inline placeholders

## Do not edit
- `build/` outputs — gitignored, regenerated by every build
- generated `index.html` / `board-data.js` — products of `generate`, not source
- `go.sum` — managed by the Go toolchain

## Must build
- Easiest: run `do-work board` (builds + serves for you; `do-work board static` for the shareable static artifact, `do-work board summary` for counts). See `actions/board.md`.
- Direct (portable, any repo with a `do-work/`): `cd <skill-dir>/tools/queue-kanban && go build -o queue-kanban .` → `./queue-kanban serve --repo-root <consumer-repo-root>` (live board) or `./queue-kanban generate --out DIR --repo-root <consumer-repo-root>` (static). The binary is gitignored in-place. Needs the Go toolchain (see `go.mod` for the required version).

## Traps
- **`next-version` is the tool's only write outside the testing fields** — one line, in one file, outside `do-work/`. It must NEVER write `CHANGELOG.md`: unique version numbers do not make a shared prepend safe, so the changelog stays an owner-only, human-authored write. `next-req` and `verify` write nothing at all.
- **`verify`'s version probe asserts AGREEMENT, not "strictly greater"** — after a release lands, the version file and the newest changelog entry are equal, and that is the healthy steady state. "Strictly greater" is the mid-release condition (the new version beats the entry that already exists); a probe built on it fires on every clean repo. The strictly-greater ordering that *is* checkable lives inside the changelog: newest entry > every earlier entry.
- **The bump size is an argument, never inferred** — patch vs minor vs major is a judgment about what the change did to consumers. An empty or unrecognized size is an error, not a default to patch.
- **`next-req` allocates, it does not reserve** — two captures at the same instant can compute the same number. Accepted on purpose (a reservation would be new durable coordination state); `verify` reports the duplicate, and the title in the filename makes it cheap to renumber. Do not add a locking scheme, and do not claim duplicates are impossible.
- **Columns track REQ status, not folder** — `walk.go` keeps queue/working/archive only as provenance; `model.go` buckets by normalized `status`. A status-alias drift sends tickets to the wrong column.
- **Repo root is auto-discovered from CWD** — prefer `--repo-root DIR` (what `actions/board.md` prescribes); the walk-up skips directories merely *named* `do-work` that are skill installs (SKILL.md at their top level, e.g. `.claude/skills/do-work/`) and errors non-zero only when no queue-holding ancestor exists.
- **`web/` is embedded, not read at runtime** — edits need a rebuild; `serve` re-serves the SAME embedded assets `generate` inlines, never files on disk.
- **Separate Go module** — build inside `tools/queue-kanban/`; a repo-root `go build ./...` from the consuming project won't reach it (it lives under `.claude/skills/do-work/`).
- **Loopback-only by default** — `serve` binds `127.0.0.1:8090` (env `QUEUE_KANBAN_PORT`; 8090 avoids the main goserver :8080). Bare port values also bind loopback; LAN exposure requires an explicit `host:port`.

## Stakes
- `model.go` + `walk.go` — status → column bucketing (`LoadBoard`)
  Req:   bucket every REQ into Pending / Claimed / Needs-input-or-Blocked / Recently-done by its normalized do-work `status`, not its tree location.
  Value: the board reflects the REAL do-work status vocabulary, so the operator and any manager it's shared with trust what each column means.
  Risk:  if status normalization drifts from `actions/work-reference.md`'s Schema Read Contract, tickets silently land in the wrong column or vanish from the board. Reversible (re-run after a fix) but actively misleads viewers until caught.
- `generate.go` + `serve.go` — shared `//go:embed web/` frontend contract
  Req:   `generate` (static) and `serve` (live) render from the SAME embedded `web/` assets; the static output must run from `file://` with zero network via the `board-data.js` sibling.
  Value: one hand-authored frontend source powers two outputs — a manager-shareable static artifact and a live local board.
  Risk:  editing `web/` without rebuilding ships stale UI; breaking the offline `board-data.js` contract makes the shared static artifact render blank for anyone opening it from disk.

## Lessons

- REQ-015: synthetic test tickets must set `OriginalStatus` for unrecognized-status warning assertions to exercise the real path; `deferred` removed from the recognized set
- REQ-016: the `severity` frontmatter vertical was dead (no producer) and is fully removed; the similar-looking `batch` field HAS real producers — re-check before any same-shape cleanup
- REQ-017: bind before announcing — `serve` must `net.Listen` first, then print the banner / open the browser, then `Serve(listener)`; the old `ListenAndServe` ordering printed a false "live board at …" line on port collisions. For opener-style side effects, prefer parameter-injected seams (`browserOpener func`, `goos` as an argument) over mutable package vars — testable without launching anything
- 0.107.0: `cancelled` (won't-do, written by `do-work abandon`) is terminally *resolved* but not terminally *successful* — it shares Recently-done and the calendar via `isTerminalResolvedStatus`, while `isCompletedStatus` stays the success-only gate. Keep the two classifiers distinct; success-readers must never widen to the resolved set
- 0.134.0: pending-tier state timers resolve `status_changed_at` (stamped on no-dedicated-stamp flips like clarify's answered → pending) → later of `created_at`/file-mtime (mtime must beat capture by >5min — capture writes the file seconds after stamping, so a bare comparison would flip every untouched card's verb to "updated"). Mtime NEVER outranks dedicated stamps (`claimed_at`/`blocked_at` — the pipeline appends sections mid-claim, mtime would reset the stopwatch every write) and stays banned from completion dating (`resolveCompletionTime`)
- 0.133.0: a `*_at` stamp parsing past the board's `now` + 2min skew (`futureTimestampSkewAllowance`, mirrored by `futureInstantSkewAllowanceMs` in `web/board.js` — change together) marks the ticket `FutureTimestampFields` → "future stamp" badge + data warning; the stopwatch renders "⚠ clock skew" instead of a clamped-frozen "0s". The usual cause is local wall-clock time written with a `Z` suffix — the Timestamp rule in `actions/work-reference.md` is the instruction-side fix
- 0.129.0: bare `blocked` (waiting on an external condition, written at capture or by work.md's mid-run blocked flip) shares the Needs-input/Blocked column via `isNeedsInputOrBlockedStatus` — distinct from the two `blocked-*` holding states and from `pending-answers`. `blocked_by`/`blocked_at`/`blocked_check` are display-only (the `[data-status="blocked"]` "blocked by" badge + drawer rows); the board never runs `blocked_check` — the work pipeline does. `blocked_by` parses as a list (free-text scalar → one element; legacy id-lists render joined) but is NOT a dependency edge
- REQ-032/034: `write_set` is read verbatim (no normalization, no alias) and the parse is ratcheted by `_dev/tests/contract-regressions.sh`. `annotateWriteSetOverlap` derives each pending/claimed ticket's contending REQ ids for the `overlaps` badge + drawer row; it is called from `buildBoard` deliberately AFTER `bucketColumns` so no column logic can read it. An empty set never overlaps — on the board absence means unknown, which must not render as conflict. Matching is `path.Match` (OS-independent — `write_set` entries are slash-separated repo-relative paths, so not `filepath.Match`, whose separator is `\` on Windows) in both directions plus literal equality, so glob-vs-literal pairs badge regardless of REQ order; glob-vs-glob is compared as literals only (no stdlib pattern intersection). Glob dialect: `*` never crosses `/`, `**` is not recursive (no superglob), and a malformed pattern is no-match for that direction — but literal equality short-circuits before either `path.Match` call, so two entries carrying the SAME malformed text still intersect. Illustrative (not closed) miss-classes: glob-vs-glob, `**`, a malformed pattern against anything but its own twin, and an entry naming a directory (`path.Match` is false both for `actions/` and for `actions` against `actions/board.md`). Nothing schedules, gates, or dispatches on `write_set` at any builder count — under fan-out it is advisory input to the human's pick and the **merge** is the non-interference proof (`actions/work-reference.md` → Worktree Dispatch Mode → Fan-Out Dispatch); the `overlaps` badge is purely an informational read for a human at the board
- REQ-034: display-only derived annotations follow the `annotateDependencyState` pattern — compute in Go AFTER `bucketColumns` (structurally unable to affect placement) and pin it with a buildBoard-level test; glob matching dialect must be chosen and documented deliberately (see the `writeSetPatternsIntersect` caveats).
- REQ-075: a retired premise leaves two fingerprints — the thing it *said* ("one REQ at a time") and the thing it was *called* ("under the exclusive-session model") — and sweeping for one reads as clean while the other still argues for the wrong behavior; the weak form is the more dangerous, because the model it names is still true and only its relevance died. Mechanically: a line-granularity grep is blind to Go/JS comments (they wrap, so the premise and the field land on different lines), while a proximity window false-positives on the canonical Fan-Out section, where "integration runs one REQ at a time" is true — so sweep prose by line and guard comment-carrying source files with a file-level "must not name a builder count" negative
- REQ-072: a probe derived from prose must be run against a known-healthy tree before you trust its fixtures — the version-vs-changelog check passed 21 green tests and still fired on this repo's own clean state, because the code and the fixtures encoded the same misreading of "strictly greater" (a mid-release condition, not a committed invariant). Anchor a file the tool must find on a content marker (`**Current version**: `), never a path: `actions/version.md` exists at the repo root only in a skill-development checkout, and `walk.go`'s `isSkillInstallDirectory` deliberately skips skill installs, so a consumer's repo root would never resolve it. Refuse-and-report beats guessing there — the call sites fall back to the manual procedure they accelerate
- REQ-089: the board's Copy payload is the ticket **file**, not its body — `FrontmatterMarkdown` (on both `RequestTicket` and `UserRequestTicket`) holds the ORIGINAL fence bytes, taken by exact-suffix removal `rawFileText[:len(rawFileText)-len(bodyText)]` **inside** the `hasFrontmatter` guard. Never re-serialize from `yamlText`: that loses key order, comments, trailing spaces and CRLF, and the whole point is that a paste round-trips back into a valid REQ/UR file. `buildGeneratedBoardMarkdownData` is the single projection point for BOTH the static bundle (`generate.go`) and the live server (`serve.go`) — change it and you change `do-work board` in both modes, which is how `serve_test.go`'s contract test broke and revealed the live path was fixed too. Test the round-trip from **parsed files, not hand-built structs**: a zero-value fence concatenates to nothing, so a struct-level fixture passes before and after and can never catch a re-serialized fence — put a comment line and irregular spacing in the fixture so only the original bytes satisfy it. Verbatim also means no synthesized heading and no H1 de-dup on the primary path; `copyTextWithHeading` belongs to the rendered-text fallback alone, which must never fabricate a fence from display state.
- REQ-084: name a probe after the **rule** it enforces, not after the tool it uses — `worktreeDirtyQueueState` implemented "a builder must not write queue state" as `git status --porcelain`, so it caught the builder interrupted mid-write and missed the one that committed (the likely shape, since builders commit by design). The fix is `git diff --name-only <integrationRef>...<branch> -- do-work/`: **three dots** is load-bearing (merge-base→B, so it sees what the *branch* changed and stays blind to how far the integration branch moved) — two dots or `diff -r` fires on nearly every run wherever the consumer commits `do-work/`, which is why the original narrowed to porcelain instead. Resolve the integration ref by **name** from the repo-root checkout, never pass `HEAD`: `HEAD` means "whatever checkout this runs in", so inside a worktree the comparison silently becomes branch-against-itself. Keep both halves — a merge-base diff cannot see uncommitted edits, porcelain cannot see committed ones. Two states, two categories, because the remedies differ (discard working-tree edits vs. drop commits before merge); neither is `Fixable`. REQ-082's hand-back file needs no exemption: main-tree path + never committed makes it invisible to both. `appendWorktreeFindings` now runs three sub-probes and is the file's longest function — the next change here should extract, not append
- REQ-083: `verify`'s `Fixable` flag means one thing only — `do-work cleanup` resolves it mechanically — so it must be derived per finding, never set once for a whole enumeration: `appendWorktreeFindings` hardcoded `Fixable: true` for every `worktree-agent-*` leftover while the merged/unmerged/still-building distinction sat in the `Remedy` *prose*, where no code could act on it and no test could assert it (a fact in the wrong medium, not a missed case). The three states come straight from `actions/cleanup.md` Pass 5's three branches; read that pass before deciding what fixable means for anything else. `git merge-base --is-ancestor <name> HEAD` has **three** outcomes — 0 merged, 1 git's answer "no", anything else (usually 128, a worktree whose branch is gone) git *declining to answer* — and folding 128 into "unmerged" repeats the same defect one level down. Pin it with `git -C <repoRoot>`: merged-ness is HEAD-relative, the same trap `git branch -d` carries. Liveness is a real boundary, not a gap to close — no lock, heartbeat, PID check, or mtime heuristic may be added (REQ-073), so the unmerged remedy names the still-in-flight case instead of guessing. Fixture note: `verify_test.go` now has a real git repo (`newWorktreeFixtureRepo`); before this, plain temp dirs meant every worktree probe silently *skipped*, and any manual reproduction must give the worktree directory and the branch the SAME name or it tests a shape dispatch never produces
- REQ-081: `flag.FlagSet.Parse` halts at the first non-flag argument, so on a subcommand that mixes a positional with flags every flag placed *after* the positional is silently discarded — `next-version patch --repo-root X` bumped the calling repo, exited 0, and printed a plausible version. Parse twice (first Parse halts on the positional; re-Parse `Args()[1:]`) rather than lifting the positional out by index, since a flag may precede it; and reject leftover tokens on **every** subcommand via `rejectLeftoverArguments` — a stray token placed first halts Parse on a flags-only subcommand too, discarding everything after it. Argument handling must live in a function the tests can call: `runXCommand` calls `os.Exit`, so anything inline in it is unassertable, which is exactly why this shipped
