# Fan-Out Orchestration — Reference

> **Companion file to `actions/work.md`.** Holds the coordinator-shape detail for worktree dispatch, fan-out and delegated-integration runs: the per-REQ branch and merge contract, landed hand-backs and dispatch timing, mid-run messages, and the wave-end restatement sweep. It belongs in core because it completes `actions/work.md`: every run mode, the serial default included, integrates a builder branch by the contract below. Each section is pointed to by name from `actions/work.md` or `actions/work-reference.md`. Load only when you reach the step that references it, and read only the named section. If this file is already in context from an earlier step this session, reuse it; don't re-read it at every reference site.

---

## Worktree Dispatch Mode (Step 1)

**Every run mode, the serial default included.** Each builder runs on its own per-REQ branch, in its own git worktree wherever the harness supports one (*Isolation ladder*). The orchestrator merges those branches and stays the only writer of `do-work/` state (`actions/work-reference.md` → **Execution Model — Claim Anywhere, One Releaser**). Isolation changes *where* a builder writes, so it can neither touch queue state nor collide with a sibling, and an interrupted build leaves a branch to merge or discard rather than half-written files in the main tree. Everything in this section is per REQ — one `<operative_name>`, one hand-back sequence, one `<pre>..<merge_hash>` range, one cleanup — so it already holds for any number of concurrent builders. *Fan-Out Dispatch* adds only who picks the set and what never parallelises.

### Isolation ladder

Three rungs, and only the last one has no isolation. Probe `git worktree list` (a non-zero exit, or an unrecognized subcommand, means no worktree support) and confirm the harness can run an agent against a working directory you choose.

- **Both present — worktree rung.** This section applies as written: `git worktree add` under *Naming*, the builder in its own directory, `git worktree remove` at cleanup.
- **Either missing — branch rung.** The second directory goes; the isolation stays. Create `worktree-agent-REQ-NNN-<suffix>` as a plain branch in the shared working tree: check it out, implement and **commit** on it, check the integration branch back out, and run the hand-back sequence unchanged. Merge, range, qualification, review, post-merge verification and cleanup are identical; cleanup is `git branch -d <operative_name>` with no worktree to remove. **Reuse that name — never invent a second prefix:** `actions/work-reference.md` → **Crash Recovery (Step 1)** and `actions/cleanup.md` → **Pass 5: Orphaned Worktrees (consent-gated)** both enumerate `git branch --list 'worktree-agent-*'` independently of worktrees, so a branch-rung leftover stays discoverable. **Builder and orchestrator are roles here, not processes:** one agent usually plays both, and the boundary is the branch. What the builder writes is committed on this REQ's branch; every `do-work/` write is made as the orchestrator, on the integration branch, and never committed on this REQ's branch (step 2's queue guard is the mechanical check). **This rung isolates committed work only.** An uncommitted edit stays in the one working tree for the next REQ, so setting a REQ aside on this rung requires the builder's edits committed on its branch first; an uncommitted set-aside is not isolated and must never be reported as one.
- **Not a git repository — no rung.** There is no branch to isolate onto, and `actions/work.md` Step 9 already skips its Commit Phase here. Say so in one progress line — `⚠ REQ-NNN: no git repository, so this implementation is not isolated; setting it aside would leave its edits in the working tree` — and continue.

**The concurrency degrade stays silent; a lost isolation does not.** Dropping from the worktree rung to the branch rung, or running one REQ at a time because the harness cannot run an agent against a chosen directory, is not reportable and never surfaces as an error, because the REQ is still isolated. The no-rung case is the only genuine loss of isolation, and the only one that surfaces.

### A builder tree does not have to be a worktree

A builder has to satisfy *own tree, own branch, hands back a branch*. A spawned `git worktree`, a second local workspace, a clone, or a remote/cloud sandbox all do, and everything downstream of the merge is identical because the orchestrator integrates a branch either way. Three deltas matter:

- **Naming and cleanup mechanics are worktree-specific.** `git worktree add`/`remove`/`prune` and the `worktree-agent-REQ-NNN-<suffix>` convention apply to a spawned worktree. A workspace, clone or sandbox the *user* opened is not the orchestrator's to name or delete: it hands back a branch, the orchestrator merges it under the name it arrived with, and holds that name as this REQ's operative name exactly as below.
- **A remote builder's hand-back travels on the branch.** The absolute-main-tree-path hand-back file (*Sole integrator*) works only because the builder shares a filesystem with the main tree. A builder that does not, such as a cloud sandbox or another machine, commits its manifest **on its own branch** and the orchestrator reads it after the merge. Never hand a remote builder a main-tree path.
- **A non-releaser checkout's `do-work/` snapshot is potentially stale, and never authoritative.** Where a consumer commits `do-work/`, every non-releaser checkout carries the queue as of its last sync: a `pending` REQ there may already be claimed elsewhere. Read it as a hint about what exists, never as current state, and resolve disagreements by syncing rather than by writing. This is *State stays home* widened from a worktree's snapshot to a checkout's.

### Claim conflicts between checkouts

**They are ordinary git conflicts, and `do-work/CHECKPOINT.md` is where they surface.** Two checkouts claiming the same REQ produce a plain **content** conflict on the REQ file, never a rename conflict, because both sides perform the identical `do-work/queue/` → `do-work/working/` rename and git resolves it silently. The conflict is made of the two claim writes (`claimed_at`, and whatever sections each side generated); with byte-identical claim writes the REQ file does not conflict at all, and the `writer:` label is then the *only* thing that surfaces the double claim. **Expect a `CHECKPOINT.md` conflict on every concurrent claim, including two that overlap in nothing:** two single-line appends land at the same position, so git reports `CONFLICT (add/add)` (`AA`) or `CONFLICT (content)` (`UU`). **Resolve it by keeping every entry from both sides** — the merge-time reading of `actions/work-reference.md` → **In-Progress Record (Step 1)**: every live claim survives. Taking ours strips another checkout's live claim record; taking theirs makes this checkout's own crash unrecoverable. One id under two labels needs no reconciling. On the REQ file itself only one claim survives, a human decision evidenced by which checkout actually has the work. This is observed behavior (`do-work/archive/UR-018/REQ-095-two-clone-acceptance-run.md` → `## Testing`) and holds only where the consumer **commits `do-work/`**; where it is untracked nothing syncs, and `duplicate-req-id` is the only detector left.

**Red Flag — a second checkout running the release tail.** Capturing, claiming and building from another checkout are in contract. The violation is a second checkout merging integration, bumping the version, prepending to `CHANGELOG.md`, moving files into `archive/`, or closing a UR; two changelog prepends against one queue is its usual shape (*Serial-only*).

### Naming

The worktree directory's basename and the branch name are the **same string**: `worktree-agent-REQ-NNN-<suffix>`. The REQ id lets any later sweep correlate a leftover with its REQ by name alone, and one string lets a single grep find both directory and branch. Derive `<suffix>` from the REQ's filename slug, lowercased and reduced to `[a-z0-9-]`, **as a text operation before you compose any shell command** — never pipe raw REQ text through `tr`/`sed` inside a quoted command line, where an apostrophe breaks the quoting and becomes an injection vector.

**Every commit on this branch, and the hand-back merge that brings it in, carries a `[REQ-NNN]` subject prefix.** The builder's own commits start with `[REQ-NNN]`; the orchestrator's merge commit (step 3 below) is `[REQ-NNN] merge builder branch <operative_name>`. This holds on every rung, including the branch rung where one agent plays both roles and no brief is written. The board credits a commit to a REQ by that bracketed token or by a touched REQ path, and by nothing else: since 0.305.88 it does not walk a merge's second-parent range to rescue un-prefixed builder commits. A builder commit without the prefix is visible on its live branch tip until the merge and then not at all, so its instant drops out of the drawer's largest-gap line; a merge without the prefix lists no paths under `--name-only` and is credited to nobody. The prose rule is the whole mechanism; no hook or wrapper stamps it.

**On a name collision at creation** — the name already exists as a leftover, typically a crash-recovered REQ re-dispatching into the name its own reported-but-not-deleted leftover still holds — do **not** delete or force. Append an **incrementing numeric token** to the suffix (`-2`, then `-3`), keeping the `worktree-agent-REQ-NNN-` prefix the sweeps grep for. **One scheme, not a choice:** a free pick between a counter and a timestamp would let two runs shape the same collision differently. Report the coexistence and leave the original to its owners: the crash sweep if it turns out merged, `actions/cleanup.md` → **Pass 5: Orphaned Worktrees (consent-gated)** if unmerged.

### The operative name

**The name actually created is this REQ's operative name.** Whatever `git worktree add` succeeded with — the derived name, or the variant after a collision — is the one string every later operation uses: the hand-back merge's `git merge` argument, Step 8's `git worktree remove` and `git branch -d` (*Cleanup — happy path*), the crash sweep's own-session bookkeeping, and anything reported to the user. This file calls it **`<operative_name>`**; the worktree path is that name under the worktrees parent directory. Hold it like `<pre>`/`<merge_hash>`: known from this session's context and re-typed as a literal into each fresh command (*Hold both endpoints as re-typed literals*). Nothing persists it, because the sweeps discover leftover names by enumerating git. **Re-deriving the name from the slug at cleanup is the failure this closes:** after a variant dispatch the derived string names the *leftover*, so remove and `-d` target unmerged work, refuse, and halt the run on a false "merge skipped or lost" alarm while the variant is never cleaned.

### Where worktrees live

Outside the repo working tree: a sibling directory (`../<repo>-worktrees/worktree-agent-REQ-NNN-…`) or a scratch directory, never nested inside the repo. A nested one is a second checkout sitting in the repo: `actions/cleanup.md` Pass 3a scans for any `do-work/` directory outside the project root and, where the consumer commits `do-work/`, would try to relocate the builder's copy into the canonical queue. That is a corruption path, and the tree also reads as stray residue to every status check downstream.

### State stays home

**Every path under `do-work/` exists in the main tree only and is the orchestrator's** — the queue, `working/`, `CHECKPOINT.md` and `runs/` are examples, not the extent, so a directory added later is covered the moment it exists. Builders receive their REQ brief in the dispatch prompt and never read or write queue state from inside a worktree. Where `do-work/` is untracked a builder finds nothing there; where a consumer **commits** it, the worktree carries a *stale snapshot* from the branch point. Treat that snapshot as absent: never read a status from it, never write to it. **On the branch rung there is only one tree, so this is a role boundary:** no `do-work/` path is ever committed on a builder branch, and step 2's queue guard proves it.

### Sole integrator

The builder never writes the main tree or its branch, **with exactly one exception: its own `do-work/runs/work-<YYYY-MM-DD-HHMMSS>/REQ-NNN-handback.md`**, reached by the absolute main-tree path the orchestrator hands it and **never staged, committed, or merged** — it is an orchestrator-owned working file, not branch content. A sibling's hand-back, `manifest.md`, anything else under `do-work/runs/`, and every other main-tree path remain violations. The exception exists because the hand-back has to survive a dead transcript (`crew-members/background-agents.md`). The builder commits on its own branch and hands back its file manifest; the orchestrator merges. A shared file needing one line of wiring — a `<link>` in a shared template, a registry entry, an export barrel — is an **integration seam**: the builder hands back the exact line and where it goes, and the orchestrator applies it **inside the merge commit** (step 3), which keeps the seam inside this REQ's merge range.

### Merge, never rebase

Integrate with `git merge --no-ff` (the full invocation is step 2). Rebasing rewrites the builder's commits, so `git branch -d` no longer recognizes the work as merged and that free merged-ness assertion is lost. `--no-ff` also keeps the merge commit as the "integrated by orchestrator" provenance record.

### When to merge, and the range every evidence step reads

The orchestrator merges each builder branch **at hand-back — end of Step 6, before Step 6.25 (Implementation Summary)** — so every downstream evidence step (6.25, 6.3, 6.5, 7, 8, 9) observes one integrated main tree. Any later position leaves qualify and review reading a clean tree with nothing to check. Run this sequence on the integration branch:

0. **Settle owner-written run artifacts and the index, then capture `<pre>` — in that order.** Queue-mode `advance` already committed the queue-to-working move plus `do-work/CHECKPOINT.md`; never stage either here. Read `git status --short --untracked-files=all -- do-work/` and sort every path into exactly one category:
   - **stage** the exact owner-written run artifacts (`manifest.md`, each `REQ-NNN-brief.md`, and each `REQ-NNN-integrate.md` under delegated integration);
   - **allow but never stage** each expected `REQ-NNN-handback.md` the run names — builder scratch in the main tree, not an error;
   - **leave alone and name** every other `do-work/` path. It belongs to another session or the user: print it once in the progress output, keep it out of the stage set, and continue. It is never a stop or a blocker and never committed here, because **the pipeline commits only what this REQ declares.**

   Only a dirty path **this REQ itself owns** still stops: its run artifacts, its working REQ file and checkpoint entry, its `write_set`, its release paths. Check the index too (`git diff --cached --name-only`), because every commit in this sequence takes the whole index. A staged path outside the stage set is taken out with `git restore --staged -- <path>`, which leaves its working-tree bytes as they are, and is named with the third category; unstaging is not a stop. **One case is not lossless and the progress line must say so:** a path staged and then modified again (`MM`) loses its staged snapshot to a dangling blob reachable only through `git fsck --lost-found`, while the working tree keeps the newest bytes. Stage only the exact run-artifact paths with `git add -A -- <exact-run-artifact-paths>`, re-run the cached-name guard, then use plain `git commit`. **Never use `git commit -- do-work/`:** a path-limited commit takes tracked paths from the working tree and ignores the index the guard just inspected. If the stage set has no changes, skip the commit; where `do-work/` is untracked there is none. Step 0 ends with the index holding only this REQ's stage set and never requires a clean working tree. **Order matters:** a run-artifact commit must land *below* `<pre>`; committed after the capture it falls inside `<pre>..<merge_hash>`, where qualify and review read it as an undeclared touch of `do-work/`.

1. **Capture `<pre>`** — run `git rev-parse --short HEAD` and read the hash. It is the integration tip before this REQ's **first** merge and the range's lower bound. Capture it **once per REQ** (a remediation re-merge does not re-capture it). Never recover it later as `HEAD^1` or live `HEAD`; both move once the orchestrator commits the changelog or merges the next sibling.
2. **Guard the queue, then merge without committing.** First run `git diff --name-only <pre>...<operative_name> -- do-work/` (three dots: merge-base to branch tip, which is why it runs **before** the merge, after which that diff goes empty). Owner bookkeeping sits below `<pre>` and the hand-back is never committed, so any printed path is queue state committed on the builder's branch, the write *State stays home* forbids: stop and drop or revert those commits on the branch before integrating. On a remediation re-merge whose fix branch was cut from the integrated tip, owner or sibling commits can surface here too; judge them, don't auto-delete. This guard is the only mechanical check that sees them: `tools/checks/qualify.sh` and `tools/checks/scope-drift.sh` exclude `do-work/` by contract, and `queue-kanban verify`'s committed-queue-state probe reads this same three-dot diff, which is blind after the merge. Then `git merge --no-ff --no-commit <operative_name>` and resolve any conflict; `--no-commit` leaves the integration seam somewhere to go. If git answers `Already up to date.` the builder committed nothing and no `MERGE_HEAD` is set: stop and treat the hand-back as empty, because a `git commit` here would fail or fabricate a non-merge commit.
3. **Apply the integration seams, then commit** — stage the handed-back seam lines and `git commit -m "[REQ-NNN] merge builder branch <operative_name>"` (the prefix rule under *Naming*; a remediation re-merge appends its reason in parentheses). A seam committed *after* the merge is the merge commit's child, outside `<pre>..<merge_hash>`, where qualify, review and Step 9's validation never see it.
4. **Capture `<merge_hash>`** — `git rev-parse --short HEAD` on the commit just made. It is the range's upper bound and the supplied-provenance hash finalization records in the REQ's `commit:` field.

### Hold both endpoints as re-typed literals

The canonical [State across command blocks](../docs/prescribed-shell-primitives.md#state-across-command-blocks) rule applies: the consumers sit in later blocks with model round-trips in between, and a `"$pre..$merge_hash"` composed in a fresh shell expands to `".."`, which git rejects. Hold both hashes in this session's context and re-type them into each fresh command, never as shell variables. `tools/checks/qualify.sh` hard-FAILs on a range it cannot resolve, so a lost endpoint surfaces as a qualification failure naming the range instead of a vacuous pass.

### The merge range

**The merge range is `<pre>..<merge_hash>`**, and in worktree dispatch mode it replaces the working diff wherever an evidence step reads changes: **Step 6.3** (`tools/checks/qualify.sh` via `DO_WORK_DIFF_RANGE="<pre>..<merge_hash>"`), **Step 7** (review's Get-the-Diff), **Step 8** (post-merge verification), and **Step 9's** finalization-allowlist validation. Use the *captured* `<merge_hash>`, never live `HEAD`: HEAD moves when finalization commits, and `<pre>..HEAD` would misattribute that commit to this REQ. `<pre>` is `<merge_hash>`'s first-parent ancestor, so `merge-base(<pre>, <merge_hash>) == <pre>` and this is already the merge-base form.

**Remediation re-merges: the range is cumulative.** A failed review sends the REQ back to Step 6 and the fix branch is merged again. Repeat steps 2–4 but **not step 1**: keep the first `<pre>` and re-capture only `<merge_hash>`, giving `<pre₁>..<merge_hash₂>`, which covers the original work *and* the fix. Re-capturing `<pre>` would cover only the fix delta, so review would read the fix in isolation and every originally-touched file would WARN as listed-but-not-in-the-diff. **Step 9 records the latest `<merge_hash>`** in `commit:`. The cost is over-inclusion: an orchestrator commit landing between the two merges falls inside the range and surfaces as an undeclared touch for judgment. That is the safe direction; under-inclusion would hide the REQ's own work.

### Post-merge verification, before finalization

The builder verified its own branch; nobody has verified the merged result. Re-run the REQ's acceptance checks — the `## Red-Green Proof` GREEN condition, the project's test command, whatever `## Scope` named — against the merged main tree **before** Step 9 finalizes anything. **The unit you verify is the unit you roll back:** a red merged state is not an archive-plus-follow-up. Stop, revert to the last verified state, and re-dispatch.

### Cleanup — happy path (Step 9, after typed finalization success)

After finalization reports `cleanup_complete`, remove the builder's worktree and branch **by this REQ's operative name**, never re-derived from the slug: `git worktree remove <path>` (no `--force`; `<path>` is the worktree whose basename is `<operative_name>`), then `git branch -d <operative_name>`, then `git worktree prune`. Run `branch -d` **from the integration branch you merged into**: `-d` tests merged-ness against the current HEAD (or the branch's upstream), so from anywhere else a merged branch can refuse and an unmerged one can pass: "refusal = unmerged" silently becomes "refusal = wrong branch". Both refusals are signal: `worktree remove` refuses on uncommitted builder work, `branch -d` on a merge that was skipped or lost. **Never `-D`, never `--force`.** Report the refusal and stop.

### Cleanup — crash path

`actions/work-reference.md` → **Crash Recovery (Step 1)** sweeps leftovers from an interrupted run: only a clean, merged leftover whose exact REQ is positively settled outside `do-work/working/` is removed mechanically. Dirty, unmerged, still-working, absent, ambiguous, malformed, or unreadable cases are reported and never auto-deleted; discarding one belongs to `actions/cleanup.md` → **Pass 5: Orphaned Worktrees (consent-gated)**, which asks first.

### Fan-Out Dispatch

**Several builders, one releaser.** Every guarantee above is per REQ, so raising the builder count adds no coordination and no durable state. `actions/work.md` processes one REQ at a time unless asked otherwise: `do-work run --fan-out [N]` enters **auto-wave mode** (*Auto-wave*); without it the serial loop runs, and a human or advanced harness can still drive the concurrent path by hand, which auto-wave automates rather than replaces. Concurrency is a flag rather than the default because `actions/work.md` must stay followable by the simplest agent that can read files and run shell commands. `--wave N` chooses which dependency depth runs and composes with `--fan-out`, which chooses how many of that set run at once.

- **The set is picked by a human or computed by auto-wave; `write_set` never gates the first and is not read at all by the second.** It is display-only, and the board's `overlaps` badge misses glob-vs-glob, `**`, and directory entries, so **absence reads as unknown, not safe** (`../../do-work-board/actions/board.md`). A field whose absence means *unknown* can inform a judgment, never make one.
- **The non-interference proof is the merge, not the pick.** `git merge --no-ff --no-commit` refusing is the only mechanical evidence that two builders' work does not collide, and git detects conflicts by line proximity, not meaning. Two REQs each appending to a shared registry merge cleanly and can still be jointly wrong; the **integration seam** rule covers that because one integrator applies every seam by hand. The other meaning collision, a later member restating a contract an earlier member redefined, is covered by the wave-end sweep (*Restatement sweep and wave-end set-aside*).
- **Integration is serial.** Implementation parallelises; merge → qualify → test → review → changelog → archive runs one REQ at a time, and each merge invalidates the previous REQ's post-merge verification, so those checks re-run per REQ. Expect the wall-clock saving in the build phase only, and say so.
- **A worktree per builder is mandatory.** Sharing one working tree was ruled out: every test run, qualification check and review diff would read a tree carrying another builder's unfinished edits, so no REQ's evidence would mean anything. Keep this reason; without it a later reader re-offers the shared tree as a simplification.

#### Auto-wave

`actions/work.md` Step 1 delegates the complete computation and claim transaction to queue-mode `advance`: its typed claimed members are the wave, and its typed exclusions are the reasons. **This prose states policy and must never become a second queue scan.** Readiness, the dependency-source-ready set, the live-claim veto, the `assigned_to` courtesy read, the `--skip-impact-negligible` filter, and the explicit-`REQ-NNN` provenance carve-out each have one definition, held by the command and applied identically in the serial loop and under `--fan-out` (`actions/work-reference.md` → **Schema Read Contract** → *Dependency-source-ready status set*; `actions/work.md` Step 1 for provenance). Targeting tokens scope the candidate pool; `--fan-out` changes only how many run at once, never which.

**`write_set` is not in that computation and must never be added to it.** A wave that read it would treat an absent declaration as safe and produce a set that looks proven and is not. A computed set claims its REQs are *runnable*, never that they do not overlap; two that collide are caught when their branches meet.

**Bounded, and the bound is not optional.** Size the wave to the harness concurrency limit per `crew-members/background-agents.md` (*Write a manifest per wave; spawn in bounded waves*), never an unbounded fan-out. `--fan-out N` sets the bound; bare `--fan-out` uses the harness limit, or two where unknown. Queue-mode `advance` records the bound and returns the continuation that re-observes, projects frozen membership, and only then bounds the next dispatch.

**No confirmation gate.** Auto-wave dispatches its computed set without asking, the deliberate change from the manual path's human pick. It does **not** change the per-REQ steps, the mandatory run directory and briefs written *before* any spawn, or serial integration. Without `git worktree` support, or on a harness that cannot run an agent against a chosen directory, the loop runs one REQ at a time on the branch rung and reports no error (*Isolation ladder*).

#### Serial-only

Never parallelised, at any builder count: every `do-work/` queue transition (claim, status flip, archive move); REQ id allocation (`actions/capture.md`); and the project-owned release version file plus `CHANGELOG.md` — one changelog entry per REQ, written by the owner at merge time. Unique version numbers do not make a shared prepend safe.

### Delegated integration — the coordinator shape

After a wave's builders are dispatched, the orchestrator may hand each REQ's integration, from the hand-back merge through `actions/work.md` Step 9, to one agent at a time, in series, in the same checkout. That agent is the REQ's integrator and plays the orchestrator role for that span; release and changelog stay serial-only. The shape exists because the integration span is long and context-heavy, and running it in the main session blocks the conversation the user steers from.

- **Entry.** The integrator enters with the read-only `advance REQ-NNN`, which continues the live claim. The section steps of `actions/work.md` skip what is already written, and Step 6's landed-hand-back condition takes it straight to the hand-back merge.
- **Never `recover`.** The coordinator already ran it at the queue boundary, and a `recover` mid-wave reads the wave's own in-flight artifacts, such as the untracked run directory, as dirt it cannot attribute. Never give an integrator run-with-recovery, `recover --assume-sole-authority` or `recover --take-over`: the first two reset every sibling claim and requeue the whole wave, and `--take-over` resets the integrator's own claim and strips the sections the coordinator wrote.
- **Never Step 10.** An integrator stops after Step 9 (`actions/work.md` Step 10 says why). The coordinator runs the checkpoint, then cleanup, after the last integrator returns.
- **One writer under the project root at a time.** While an integrator runs, the coordinator writes nothing under the project root: no REQ sections, no manifest edits, no captures. Otherwise this is two sessions in one working tree, which `actions/work-reference.md` → **Execution Model — Claim Anywhere, One Releaser** leaves unspecified. The coordinator writes in the gap between integrators and keeps live notes in its own session scratch until then.
- **The integrator brief.** In the gap before each integrator starts, the coordinator writes `REQ-NNN-integrate.md` in the run directory: the REQ id, the run directory, the hand-back path, the operative name, the wave membership, every wave member the coordinator has set aside (a set-aside member keeps its claim in `do-work/working/`, so without this list the integrator cannot tell it from one still building), any mid-run addendum text, and the instruction not to run Step 10.

### Run directory, briefs and hand-backs

**The run directory is mandatory under fan-out.** Fan-out is a background fan-out, so `crew-members/background-agents.md` applies. Its slots map onto this pipeline:

| Guardrail slot | Fan-out use |
| --- | --- |
| run directory | `do-work/runs/work-<YYYY-MM-DD-HHMMSS>/`, created before any spawn |
| per-builder input | `REQ-NNN-brief.md` — REQ body, worktree path, branch name, never-touch list, the commit subject rule (*Naming*), hand-back format |
| per-builder output | `REQ-NNN-handback.md` — branch, file manifest, integration seams, and **every `##` section the builder would have written into the REQ file** (today `## Discovered Tasks` and `## Decisions`, each under its own heading), because readers take them from here when the REQ lacks them (`actions/work-reference.md` → **Reading a Builder-Authored Section (any step)**). This row and `actions/work.md` Step 6's routed sections are one set: a section Step 6 tells the builder to author and this row does not carry is lost silently. The one main-tree path a builder may write (*Sole integrator*) |
| per-integrator input | `REQ-NNN-integrate.md` — written by the coordinator between integrators, never by a builder (*Delegated integration — the coordinator shape*) |
| `manifest.md` | REQ id → builder, `<operative_name>`, handback file, landed status, held dispatch instant, plus the run's hand-back emphasis note when the user sent one (*Mid-Run Messages (any step)*) — **the orchestrator's**, never written by a builder |
| bounded waves | builders per wave, sized to the harness concurrency limit |

The pattern makes fan-out failures **survivable, not prevented**. Never describe it as a fix.

**The brief and the hand-back path reach the builder as prompt content or an absolute main-tree path.** A repo-relative path resolves inside the worktree, against its stale tracked copy of `do-work/`, so the builder reads a snapshot or nothing. In the return direction it is worse: the write succeeds, lands in the builder's branch, and the orchestrator reads nothing.

**Dispatch mechanism is deliberately unspecified.** The owner synthesizes from files on disk, never from conversation, so a spawned subagent and a human-opened session are indistinguishable to it. Do not document two routes.

## Landed hand-back and dispatch timing

### Landed hand-back — consume it, never re-dispatch

**Condition:** the hand-back file this REQ's run-manifest row names exists on disk. The build already happened, whatever the row's status says, because a crashed orchestrator may never have updated the row (`crew-members/background-agents.md`: an agent whose findings file exists is done). Do not dispatch a builder. Stamp `builder_handback_at` only if the field is absent. Record the builder-work timing event, with the dispatch instant from the manifest row, only when the hand-back has just landed: the recorder times from that instant to now, so a session that arrives later skips the event and says so, since recording it would charge the builder with the gap. Then go straight to the hand-back merge (*When to merge, and the range every evidence step reads*), which proves the branch state. The condition holds for any session that reaches Step 6, including an integrator and a fresh session after a crash.

### Dispatch instant

Once the implementation builder has accepted the dispatch, take the current UTC instant (Timestamp rule) and hold it. When the run has a manifest, also write it into this REQ's row, so a session that did not dispatch the builder, such as an integrator, records the timing event from that row and never from `dispatch_at`. Stamp `dispatch_at` only if the field is absent: after a recovery it still names the first attempt's dispatch, and that observation stays (`actions/work-reference.md` → **Stamps are append-only**). If dispatch fails before a builder accepts it, leave the field absent. When the builder returns its completed hand-back, stamp `builder_handback_at: <now>` on the same condition, before the hand-back merge begins. Then record the delegated wait once through `record-timing-event` (`--category builder-work --started-at <the instant you held>`), which owns every timestamp, duration and redaction mechanic. **Pass the held instant, never `dispatch_at` read back out of the file:** on a retry that field belongs to the earlier attempt, and the recorder would charge this builder with every hour between the two.

## Mid-Run Messages (any step)

A user message can arrive at any step. It never stops the run: route it, keep the loop going, and say in one progress line where it went. Two rules hold on every branch: carry the user's own words, never a paraphrase, because meaning is lost in restatement; and route the message to every REQ it affects, not only the one the user named. **Who writes:** when the session that received the message is the only writer under the project root (the serial loop, or a fan-out run whose main session integrates itself), it writes now. Under delegated integration the coordinator keeps the user's words in its own session scratch, outside the project root, and writes only in its next gap between integrators (*Delegated integration — the coordinator shape*). Pick the branch by what the message changes:

- **It asks about progress or state.** Answer from disk: the REQ files, the run manifest, the hand-backs, read through `actions/status.md`. Never answer from conversation memory, which does not see work agents did out of sight.
- **It changes an in-flight REQ whose builder has not handed back yet.** Write a `## Addendum (mid-run)` section on the working REQ: one framing line saying which requirement the message extends, narrows, or corrects, then the user's words under `actions/clarify.md` Step 4's **Outside-text containment**. A REQ carries one such section: a later message appends a new entry under its own timestamp line inside it, never a second heading of the same name, because `advance` refuses a REQ whose section name appears twice. Under delegated integration the coordinator puts the words in that REQ's integrator brief, and the integrator writes the section before the merge. Where the harness can message a running agent, also forward the words to the builder; otherwise say in the progress output that the builder will not see them and review will judge the build against them, since `actions/review-work.md` reads `## Addendum` sections as requirements. The section is user intent, not a generated section, so a takeover reset keeps it.
- **It changes an in-flight REQ whose builder already handed back.** That is the landed-hand-back condition, and it includes a REQ whose integrator is already running. Use capture's in-flight path, a new REQ with `addendum_to` (`actions/capture.md` → **Immutability Rule**), and report it as queued for the next loop. Under delegated integration the coordinator never runs that capture while an integrator runs.
- **It changes a queued REQ, or asks for new work.** Use capture's existing paths (`actions/capture.md`).
- **It changes only what the hand-back shows first.** When the run has a run directory, write it as the hand-back emphasis note in the run manifest, not in memory; the Decision Brief reads it there (`actions/work-reference.md` → **Decision Brief (hand-back format)**). When the run has no run directory, the session that received the message also renders the Decision Brief, so it holds the note itself and says so in one progress line. Do not create a run directory or any other file for this case.

## Restatement sweep and wave-end set-aside

`actions/work.md` Step 7's **Restatement sweep (MUST)** runs `actions/review-work.md` Step 6 (**Restatement Sweep**) when this REQ's diff redefines something other text restates, or when this REQ is its wave's last successful integration. This section is how the orchestrator knows the second condition and passes it on.

- **Deciding "last successful integration".** It holds when every other member of this REQ's wave is already archived or set aside. The run manifest's rows name the wave's members but do not track who is done: decide from the archive, which shows which members finalized, plus the set-aside list the orchestrator holds. Under delegated integration that list is the one the integrator brief carries (*Delegated integration — the coordinator shape*). A run with no manifest has no wave.
- **Passing it.** When it holds, pass the review agent that this is the wave's last successful integration and those members' REQ ids, alongside the merge range `<pre>..<merge_hash>`.
- **A set-aside after the wave's last review.** When a member is set aside after that review already ran, no review was passed the wave-end fact, so the sweep did not run for that wave. The orchestrator names that gap under HANDLED in the run's Decision Brief (`actions/work-reference.md` → **Decision Brief (hand-back format)**) as its call not to re-run a review, and re-runs none.
