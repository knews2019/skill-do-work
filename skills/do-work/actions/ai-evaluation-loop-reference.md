# AI-Evaluation-Loop Reference

> **Part of the do-work core skill.** Read when `actions/work.md` selects `--review-mode sol-loop|council`, or resumes a REQ with that selection. This companion completes core's work review; it needs the existing REQ evidence and finalization contracts, not an upstream skill installation.

## Input

The parent orchestrator owns selection, candidate identity, finding validation, fixes, counters, checkpoints, and the final decision. Reviewers only return independent evidence. This policy replaces ordinary Step 7's score-based decisions, one-remediation limit, and failed-review fallback for the selected REQ. It changes neither ordinary runs nor standalone `review-work`.

## Steps

### Step 1: Persist selection and resolve reviewers

After claim and before dispatch, write a top-level `## AI-Evaluation-Loop` section in the REQ body. Keep it separate from `## Review` and other generated sections that recovery strips. Persist the selected mode, whether jester was requested, frozen scope and requirements, review base, total rounds used (initially 0), consecutive stalled rounds (initially 0), and outcome `pending`. Update this section in place before dispatch and after each result; preserve round history rather than replacing it with the last score. These are action-authored notes, not new frontmatter or a CLI schema.

Read that section on every claim, resume, handoff, and recovery, even when the new invocation omits the options. Restore its mode and counters before doing work. A conflicting selection is an error, not a new budget. Preserve this section through reset/requeue and carry it into the archive. If evidence is missing or inconsistent, report unresolved; never reconstruct zero counters or ordinary review from silence.

Resolve identities through the harness's available-provider/model discovery:

- `sol-loop`: one required independent OpenAI GPT Sol reviewer. Resolve the available Sol model to its exact identifier; another GPT family is not a substitute.
- `council`: three required independent reviewers, one each from OpenAI, Anthropic, and Google. Resolve a strong available model for each, with high reasoning effort where supported. Record the choice before dispatch. Honor any user-specified model/provider exactly; do not silently replace it.
- `--jester`: a separate optional advisory invocation, defaulting to the latest available Gemini the harness can resolve. Use harness catalog/alias evidence for “latest”; never guess a release order or hardcode Gemini 4 Argon. Honor an explicit user selection. If resolution is unavailable or ambiguous, report advisory absence. A Google council seat remains required even when jester is enabled.

Record the parent's actual provider/model when exposed, and for every reviewer keep requested selection, resolved provider/model, discovery evidence, invocation/task ID, effective settings, returned execution metadata, and result location. Only harness evidence verifies identity; a prompt saying “you are Sol,” a reviewer self-description, or a friendly display name does not. Mark unexposed identity unknown. A required identity mismatching the resolved selection or not verified by execution evidence, unavailable required provider, failed invocation, or missing required reply ends unresolved, never an inline parent substitute or approval. Parent identity unknown must be disclosed, not invented; the parent still supplies its own explicit decision. No automatic upstream install or credentials setup.

### Step 2: Freeze the candidate and retain a recoverable checkpoint

Before each pass, record the full base and current commit IDs plus the actual behavior diff. A HEAD hash alone is insufficient: inventory staged, unstaged, and untracked implementation files, including deletions, file modes, symlink targets and binary bytes. Use a content digest of that complete manifest and exact bytes as the candidate ID, with the derivation recorded. A clean committed tree may instead use its full tree/commit identity with evidence that no relevant dirty or untracked files exist. Include any pre-existing change that affects the tested behavior as read-only context and identify its owner. Exclude only recorded non-behavior evidence such as the loop log itself; exclusions cannot hide implementation bytes.

Save a recoverable copy of the first verified candidate and retain the best verified candidate thereafter, preferably one meeting all requirements. Record its identity, manifest, checks and results, satisfied/unmet requirements, remaining findings, storage path or retained Git reference, and why it is better. “Verified” means the named checks were actually run; it does not mean approved. With no qualifying candidate, say so and retain the available candidate with its failed/unassessed checks. Never delete the only recoverable copy when replacing it.

Use a durable evidence location that survives session and temporary-worktree cleanup. A retained clean commit is sufficient only when it contains all candidate bytes; otherwise also save exact file copies or a binary-capable patch plus untracked files and the manifest. Record pre-existing user changes and index state before making a checkpoint. Do not stage unrelated changes to manufacture a clean commit, stash someone else's work, or use a whole-tree reset/clean for restoration.

To restore, compare current bytes with the saved manifest and ownership record. Restore only this REQ's owned files/hunks, preserving unrelated user changes and index entries. An overlapping later user edit or uncertain ownership refuses that restore; retain both versions and report the conflict. Recompute candidate identity and rerun relevant checks after any restore. A best checkpoint is not implicit approval: obtain a fresh required review of the restored current candidate within the remaining budget, or report it unresolved when no round remains. Counter and ledger history are never rolled back with source files.

### Step 3: Dispatch one independent review pass

One round is one complete review pass, including all required seats and the parent assessment; a fresh pass after fixes is another round. Reserve its number by incrementing total rounds **before dispatch**, recording candidate ID, required seats and pending invocation records durably. Never dispatch a sixth round. An interrupted or failed attempt consumes its reserved round; on recovery recover existing invocation evidence without re-dispatching it. If required evidence cannot be recovered, stop unresolved. Persist each returned result so a crash cannot erase a used round.

Freeze candidate edits while reviewers run. Use fresh independent read-only invocations (parallel where supported); do not ask a reviewer to spawn reviewers. Give every reviewer the same serious neutral brief: requirements and scope, exact candidate/base and readable bytes, relevant checks, changed behavior, open finding IDs, prior evidence and counterarguments. Do not share other reviewers' current verdicts before replies. Do not tell the advisory reviewer it is a jester, reveal its advisory role, or ask for humor. Role, voting rules and counters stay with the parent.

Request `actions/review-work.md` in **caller-owned evidence-only** form: apply requirements, code/acceptance review and the restatement sweep, return candidate ID, findings with severity/impact/evidence, checks actually performed, unassessed checks, and an explicit approve/request-changes verdict. No reviewer edits source, REQ, ledger, follow-ups, lessons, or lifecycle state. Supply necessary REQ/UR extracts without the parent's role assignments. Run checks without mutating the frozen candidate; use an isolated test/evidence location when necessary, or report the check unassessed. Reviewers return a proposed Review block; only the parent writes it. Scores, if supplied, are observations, never acceptance thresholds.

Launch jester only when it can return without delaying required work. Consume whatever advisory result is available at the required-pass decision boundary. Do not wait for an unavailable, failed or slow advisory invocation; record its absence and cancel/detach it according to the harness contract. If the harness cannot provide a nonblocking advisory call, skip it with that reason. Never count an advisory reply as a required seat. Late evidence cannot silently rewrite a finished outcome; report it for validation against the current candidate.

### Step 4: Validate findings and decide whether another round is earned

Keep one parent-owned ledger across all rounds. Each finding has a stable ID, origin/invocation, first/last candidate and round, severity, impact token, concrete evidence/reproduction, disposition (open, accepted, fixed-and-verified, declined, or disputed), and remaining concern. Deduplicate equivalent findings without erasing origins. Preserve declined findings with counterevidence and evidence-based disagreement. “Fixed” requires verification on the current candidate; a claimed edit or a higher score is not closure.

Validate each claim against the reviewed bytes and current requirements before accepting it, including jester findings. Material means an evidence-supported unmet requirement, correctness, security, data-integrity, or meaningful regression issue; a stylistic nit is not material. Noncritical impact does not make a material defect acceptable. Reject invented requirements and review-driven scope growth with reasons; an unresolved material out-of-scope concern remains visible and prevents approval, without authorizing a scope expansion. Parent-controlled minimal in-scope fixes use the existing implementation, qualification and testing phases, then a fresh pass covering changed behavior and all open findings.

**Fix attempts and recovery:** Before re-entering implementation for accepted fixes, preserve the consumed attempt's handback, branch, source commit and integration receipt in the loop history. Allocate a new attempt ID and a unique, initially absent handback path; persist the attempt and update the run manifest's active handback/branch before dispatch. Preserve historical rows or links. The landed-handback rule now reads this active attempt, never the earlier build. Keep the original review base and advance only the latest integrated upper bound; fixes do not reset counters or the ledger.

On recovery, resume that active attempt instead of allocating another. If its builder is still running, recover that invocation; if its handback has landed but is unconsumed, integrate it once. If its source commit is already an ancestor of the integration tip, verify/recover the integration receipt and proceed to qualification/testing without merging again. A receipt records the attempt, source commit and merge commit; verify ancestry before trusting it. Ambiguous execution or integration evidence ends unresolved rather than dispatching a duplicate. Persist the receipt after each merge and before the next review; fresh accepted fixes create the next attempt only after the prior one is consumed.

At each completed pass, compare with the previous verified candidate (the initial checked candidate for round 1). Record concrete improvement evidence: a reproduced defect now absent, an unmet requirement now verified, or a previously unassessed required check now exercised successfully, without a material regression. Supported improvement resets **only** consecutive stalled rounds to 0. Otherwise increment that counter, including a pass that only raises subjective scores, repeats advice or rearranges nits. Fixes, requalification, recovery and checkpoint restoration never reset total rounds. Record counter updates and decision together before any next dispatch. An interrupted assessment with insufficient evidence cannot be treated as progress.

Apply these decisions in order:

1. **Approve** only when the parent and every required reviewer explicitly approve the exact same current candidate, required acceptance evidence is satisfied, and zero supported material findings remain unresolved. Recompute identity after the replies and again before finalization. Any changed behavior, including dirty/untracked bytes or an integration change, invalidates prior approvals and requires a fresh pass within the remaining budget. Nits may remain recorded. No average, majority vote, score increase, missing reply or best checkpoint satisfies this rule.
2. **Stop unresolved** when required review failed/is missing/unverified, material disagreement persists through two consecutive replies addressing its evidence, five total rounds have been used, or two consecutive rounds have no meaningful evidence-supported improvement. A clean approval on the fifth round is allowed; an open finding on it is not. State the actual stop reason and unmet requirements. Do not apply another fix followed by an unbudgeted “confirmation” pass.
3. **Continue** otherwise: preserve/update the best verified checkpoint, make accepted in-scope fixes, rerun the covering checks, and return to Step 2. With no justified fix, recheck the disputed evidence without inventing work; the stall/disagreement limits still apply.

Jester scores never vote, block, change acceptance, or enter council grades in a PR description. Its absence is not approval. A validated material advisory defect enters the same ledger and must be resolved for approval because of the evidence, regardless of that reviewer's score.

### Step 5: Return an honest lifecycle result

Persist a final `AI-Evaluation-Loop: approved` or `AI-Evaluation-Loop: unresolved / not approved` result in the loop section and the parent-written `## Review`. Include mode, candidate ID, actual identities with invocation evidence, rounds used out of five, consecutive stalls, required verdicts, advisory availability, ledger/remaining concerns, checkpoint/recovery location, checks and limitations. Preserve any normal Review scores as labeled per-review observations (or unavailable); never fabricate an aggregate or let it replace this result.

Return to `actions/work.md` after Step 7 with this selected result. Approved work follows normal preparation. Unresolved selected evaluation chooses `completed-with-issues` through Step 8's canonical finalization intent, without directly writing terminal frontmatter. This is not consensus approval: `completed-with-issues` is lifecycle terminal-success and still satisfies `depends_on` and UR completion. Do not promise a dependency hold or a new status. Existing implementation/test failure and repository-gate holds still apply; this policy grants no gate bypass. Route remaining findings once through review-work Step 10's impact rule (only critical findings auto-queue), with the parent performing writes.

Before Step 8 consumes a result after recovery, heavy testing or any later edit, recheck candidate identity, required verdicts and ledger. A missing/stale approval is unresolved unless remaining rounds produce a valid approval. Keep the final result prominent in progress, hand-back and any PR description; never render unresolved work as “approved,” “ship-ready,” or consensus by using a numerical score or terminal status. This feature grants no PR creation or merge permission.
