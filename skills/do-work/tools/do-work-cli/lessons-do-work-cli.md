- [family: closed-enumeration-for-a-condition] [REQ-460](https://github.com/knews2019/skill-do-work/blob/main/do-work/archive/REQ-460-make-outside-text-delimiter-containment-condition-complete.md#lessons-learned): when a contract states a condition, testing membership in a list of examples is a different contract that happens to agree on the examples — `summaryRequiresContainment` recognized ten prefixes and inlined `***`, `___`, `+++`, `:::note`, `$$`, `===`, bare `-`/`*`/`+`, bare `1.`, pipe tables and indented code. **A partially-correct enumeration is worse than an empty one**: `---` and `* * *` were caught while `***` and `___` were not, so the class looked handled. State the condition in the doc comment first, then test its ingredients — Markdown opens every block construct from block-significant leading whitespace, an ASCII punctuation mark, or a digit run forming an ordered-list marker — and take the character set wholesale from the spec's own definition rather than the marks today's syntax uses, or the narrower set is the next enumeration to go stale. Two traps worth carrying: a trim that runs *before* the test can destroy the very bytes that constitute the structure (`TrimLeft(" \t")` made indented code unreachable), and a widening like this is only provable as safe by differential — 160,906 inputs, old predicate against new, 0 weakenings, which no fixture set establishes. Finally, know where the value is written before reasoning about its hazard: this summary lands mid-line at two sites, so it can never start a line, and the delimiter hazard the widening was justified by is unreachable there — the review caught that, and the decision now stands on defence-in-depth for a future line-start writer instead.
- [family: writer-anchored-marker-position] [REQ-528](https://github.com/knews2019/skill-do-work/blob/main/do-work/archive/REQ-528-anchor-resolved-question-marker-matching-to-its-position.md#lessons-learned): a marker the writer composes onto a shared line must be read at the position the writer places it, never by containment over the line — but **position anchoring alone is not sufficient when the neighbouring field is human text that can occupy the same position**. `allResolvedQuestionsMatch` searched the whole `- [x]` line, so an answer summary supplied the disposition and cancelled an answered REQ; anchoring to the writer's separator closed that, and a summary *beginning* `Discarded: ` still forged it, because the label and the summary share one position and the document records nowhere which wrote those bytes. The contract needs both halves: refuse the collision on the write side, and read only at the anchored position. Sibling to `closed-enumeration-for-a-condition` (REQ-460) — that one stated the condition, this one states where it is evaluated and who is allowed to have written the bytes. Three more traps: a line where the anchor is not unique has no determinable marker and must fail toward the non-terminal verdict (measure the cost first — 2 of 124 real lines carry a second arrow, from this repo's own `A → B` style); a guard that fires for every outcome rather than only the ambiguous one is defense nothing earned, so pin the carve-out or a later hardening will pass silently; and attack the built command, not the test harness — the first implementation's lock-ins were real and all green while the forgery still worked end to end.
- [family: closed-enumeration-for-a-condition] [REQ-461](https://github.com/knews2019/skill-do-work/blob/main/do-work/archive/REQ-461-require-affirmative-project-owned-release-targets.md#lessons-learned): the family's second sighting in three REQs, so its trap is now promoted into the prime. `installedReleasePath` denylisted `vendor`, `node_modules`, `.claude/skills` and `generated`, so `third_party/do-work`, `dist/skills/do-work` and any differently-named cache tree were accepted for a consumer release. The replacement proves ownership from two declarations the repository already makes — Git's index, and no `SKILL.md` between the root and the target's parent — and **neither half is sufficient alone**: a committed vendored package satisfies the index and is caught only by its marker, while a `dist` or cache tree carries no marker and is caught only by the index refusing to claim it. Four traps worth carrying. **Anchor an attestation on the directory the file actually lands in**: walking up to the nearest *existing* ancestor reaches a repository root that always attests, so every not-yet-created tree was accepted — the realistic case — while only the already-existing one refused. **A negative test can pass by fixture accident**: deleting one `placeholder` line flipped this REQ's sole create-path test from refusing to accepting, and the neuter table showed the same hole from the other side by *not* reddening it. **`git ls-files -- <dir>` prints `<dir>` itself** for a gitlink or tracked symlink, so a directory with no tracked file inside it attests; filter to entries strictly within, and use `-z` so git's path quoting cannot break the prefix test. **Pair every refusal gap with its own remedy in a typed result**, because one shared remedy line was wrong for two of three gaps and steered a consumer whose file was merely uncommitted toward the maintainer escape hatch. Finally: when a fix renames a refusal code, a single revert differential cannot isolate the condition — rows redden on the rename. Run one differential per half.
- [family: single-exit-owner] [REQ-525](https://github.com/knews2019/skill-do-work/blob/main/do-work/archive/REQ-525-block-the-install-confirmation-before-signalling-it.md#lessons-learned): **two goroutines that can both reach `os.Exit` have no correct ordering** — whichever gets there first decides the status. A signal handler doing `os.Exit(130)` raced the ordinary return path, and because a cancelled confirmation is indistinguishable from a typed "N" and reports `OutcomeSuccess`, `Ctrl-C` at the install prompt exited **0** under CPU contention. Give the status one owner on the goroutine that owns the work, recorded by the handler and taken in a defer registered immediately before the recovery defer, so recovery-before-exit is defer order rather than a handshake. **Store the record before cancelling**: cancellation is the only thing that frees a goroutine parked in a select or a subprocess, so every path that can see the cancellation has already seen the record — that ordering, not the atomic, is the correctness argument. Four traps. **A single exit owner still needs to know what the work concluded**: taking 130 unconditionally reported an empty stdout and a failure status for a complete verified install, and the guard must key on the *specific* terminal state, never on "success" — the interrupted-confirmation case this exit owner exists for also returns `OutcomeSuccess`, so an outcome-shaped predicate silently re-breaks the fix. **`os.Exit` in a defer skips every outer defer**, so a caller's scratch-tree cleanup stops running the moment you take the exit rather than returning it. **Pin the child to `GOMAXPROCS=1`** to test a starved-handler race: on the broken tree that fails 9 of 9 every run while the unpinned control fails 0 of 9 across three — the pin is what makes such a test a lock-in, and it is a configuration real single-vCPU runners hit. **And a sub-millisecond window cannot be hit by an externally timed signal**: park the child inside it with I/O back-pressure (fill its narration pipe to one buffer so the next write blocks) and prove the preceding step completed, rather than sleeping and hoping.
