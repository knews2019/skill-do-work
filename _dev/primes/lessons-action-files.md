- 0.295.1: when a schema field becomes append-only, re-read every prose site that WRITES it and every step that PASSES IT ON. `actions/work.md` told the orchestrator to stamp `dispatch_at: <now>` and, two sentences later, to hand that same field to `record-timing-event --started-at`. Once recovery stopped deleting the stamp, a retried builder's five-minute wait was recorded as 86,700 seconds, because `dispatch_at` still belonged to the previous attempt. All four phase-stamp instructions in that file said `<now>` with no absent-condition at all, contradicting the schema paragraph they were meant to implement. A rule stated once in the reference does not reach the prose that acts on it: grep the field name and fix the writers and the passers-on in one pass.

- 0.266.6: a deterministic refusal is a fact, not an instruction. `do-work run` stopped a whole queue on a Finder `.DS_Store` under `do-work/` because the prose read every `recover-finalization` refusal as "stop and hand back", and the "no free-form fallback" sentences beside it were taken as forbidding thought rather than forbidding hand-made mutations. The command was right to refuse: it cannot know what the bytes are. Knowing what the bytes are is the orchestrator's job, and the prose never said so. When an action wires a canonical command into a step, state both halves: the command owns the mutation and the exact verdict, the orchestrator owns judging and clearing whatever the command refused on. The fix landed twice for that reason — once at the inventory chokepoint so the specific stray never reaches a gate, and once as the general rule in `skills/do-work/actions/work-reference.md` → **Stuck Runs Hand Off to Judgment (any step)**, strongest under `run-with-recovery` where ownership is already asserted.
- 0.235.0: when a pipeline rule cannot use the pipeline's own convention, that is the signal to move the rule out of the pipeline, not to invent a second convention. The standing prose-reconciliation sweep was a REQ that never reached a terminal status, so it could not use `commit:` for provenance — and two branches independently invented the same workaround, a hand-written hash on a body `## Drains` line, the one write in the pipeline bypassing `record-commit-hash.sh`. The workaround was cheap each time; what was expensive was that every new selector, filter, and terminal-set reader had to be taught the exception, so the cost arrived in installments and never looked like a decision. Count the carve-outs before hardening the newest one: a mechanism that needed one in every selector, filter, terminal-set reader and provenance rule it touched, across two skills, is not worth guarding — it is worth deleting.
- 0.221.0: a contract stated where it is introduced does not reach the readers it invalidates. The Fold-First Rule landed in `capture.md` and left four downstream contracts wrong at once — `verify-requests.md` still selected REQs from the `requests` array a fold deliberately skips (so a folded request graded as a *dropped* requirement), capture's own checklist still counted REQ files a fold does not create, the composed exit summary had no headline for the permanent queue state a standing sweep creates, and the Commit Phase named only "the archived REQ" for a REQ that is never archived (the standing sweep itself was retired in 0.235.0; the lesson is about the readers, not that mechanism). When a rule changes what a field means or what a status can be, grep for every **reader** of that field and that status before calling the rule shipped: the readers are where a contract takes effect, and a rule that only its author's file knows about is half-landed. Two of the four were found and fixed independently on another branch within a day, which is the corollary: when a contract lands half-way, the same holes get found repeatedly by whoever reads the next file down.

## Template

Action files follow a consistent structure. When adding or modifying actions, use this template:

```markdown
# [Action Name] Action

> **Part of the do-work skill.** [1 sentence: what it does and when it's invoked.]

[Optional: read-only flag, philosophy, or key principles — 1-2 paragraphs max]

## When to Use

**Use when:** [2-4 bullets — positive triggers]
**Do NOT use when:** [2-3 bullets — explicit exclusions, with redirect to correct action]

## Input

[What parameters drive behavior: $ARGUMENTS, target REQ/UR, modes]

## Steps

### Step 1: [First action]

### Step 2: [...]

### Step N: [Final action]

## Output Format

[What gets produced — report structure, file changes, or user-facing output]

## Rules

[Include only if earned — see below. Constraints specific to this action, not restated engineering hygiene.]

## Common Rationalizations

[Include only if earned — see below.]

| If you're thinking...              | STOP. Instead...     | Because...               |
| ---------------------------------- | -------------------- | ------------------------ |
| [Shortcut the agent might attempt] | [What to do instead] | [Why the shortcut fails] |

## Red Flags

[Include only if earned — see below.]

- [Observable symptom that something went wrong — helps reviewers detect problems after the fact]

## Verification Checklist

[Include only if earned — see below.]

- [ ] [Concrete exit criterion with evidence requirement]
```

**Required:** Description blockquote, Steps (numbered). **Common:** Input, Output Format, When to Use.

**Earned, not mandatory: Rules, Common Rationalizations, Red Flags, Verification Checklist.** Add one only when the file has something a capable model would otherwise get wrong — do-work machinery (a queue/pipeline mechanic, a frontmatter or schema contract) or a hard-won failure mode with a traceable origin (a real REQ or incident this stops from recurring). "This is generic engineering advice a capable model already follows" is an explicit *non*-reason — true or not, it doesn't earn a section.

**The test, not a vibe:** before adding a Common Rationalizations row, ask *can I name the specific failure this row prevents, and where it happened?* No → don't add the row. If every row in a table fails that test, omit the whole section — a generic table is worse than no table: it teaches the reader the section is decorative, so they stop reading the ones that aren't. Apply the same test to Rules and Red Flags — specific to this action, not restated hygiene ("write tests," "don't skip validation"). When a file has nothing that passes, omit the section entirely; don't ship it empty or generic to satisfy the template.

**State intent, not a directive rule, when a capable model can infer the rest.** "Report drift, don't fix it inline" gives the model this action's boundary in one line — a five-line Rules section re-deriving why inline fixes are bad adds nothing a capable model didn't already know.

`_dev/tests/contract-regressions.sh` locks in the Common Rationalizations rule: a new action file's table must contain at least one do-work-specific noun (illustrative, not exhaustive, per Closed Enumerations Go Stale in `prime-shell-commands.md` — e.g. REQ, UR, queue, frontmatter, pipeline, archive) or the suite fails, naming the file and the fix.

**Section order when present:** Philosophy → When to Use → Input → Steps → Output → Rules → Common Rationalizations → Red Flags → Verification Checklist.

## Agent Compatibility

Action files must work with **any** agentic coding tool:

- Use generalized language ("spawn a subagent", "use your environment's ask-user prompt") — no tool-specific APIs in action files.
- Each action file should work as a standalone prompt pasted into a basic chat interface.
- Design for the floor: the simplest agent that can read/write files and run shell commands must be able to follow the instructions. Subagents and parallel execution are nice-to-haves.
