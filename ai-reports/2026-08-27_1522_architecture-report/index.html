1 · What this repository is

This repository is the source of the do-work suite: "a four-skill task queue suite for agentic coding tools — capture requests fast, process them later" README.md:3. The core idea is separating thinking of things from doing things: requests are captured verbatim into a queue as they occur, and a separate work loop later triages and builds each one with a full decision trail README.md:53.

The tree at this commit holds 1,056 tracked files in four layers:

  • The shipped product — four sibling skill packages under skills/, the suite manifest suite/modules.tsv, and the root bootstrap tools under tools/.
  • Maintainer-only governance — _dev/ (tests, primes, lessons), decisions/ (21 ADRs, topic indexes, audits), CLAUDE.md/AGENTS.md.
  • Dogfooded live state — this repo runs the suite on itself: its own queue under do-work/ and its own knowledge base under kb/ are tracked, load-bearing data.
  • Published deliverables — dated, immutable report bundles under ai-reports/, including this one.

What separates layer one from the rest is eleven export-ignore lines in .gitattributes .gitattributes:43-53: both install routes fetch an archive that honors them, so consumers receive only the product (§8). The whole suite shares one version, 0.244.6, held in lock-step across three files (§8).

2 · The suite in a consumer project

A consumer installs with one copy-paste bash block that downloads the main-branch tarball and runs the installer README.md:9-22. Four packages land as siblings under .claude/skills/; durable queue state lives at the project root under do-work/ and is never touched by install or update README.md:35.

The packages are deliberately loose-coupled: each has its own SKILL.md router, sibling references are literal relative paths resolved from the citing file's directory SKILL.md:16, and only the board needs a toolchain (Go) — every other capability requires nothing beyond file access and a shell. Action files are written to work as standalone prompts in any agentic tool README.md:156.

3 · Core: router and the work pipeline

Routing

The core SKILL.md is a first-match-wins trigger table: sixteen rows map user input to exactly one action file under actions/, which is then read completely with arguments passed through SKILL.md:22-45. Two fallbacks close the space: unmatched descriptive multi-word input becomes a capture, and an unknown single word triggers a question rather than a guess. Mechanics that would bloat an action file live in companion *-reference.md files loaded only at the step that cites them.

Capture: intent becomes queue entries

Every capture produces exactly two things, always paired: a UR folder do-work/user-requests/UR-NNN/input.md preserving the user's input verbatim, and one or more REQ files in do-work/queue/ linked back by user_request: capture.md:11. Compound inputs are split into separate REQs; capture asks clarifying questions but never builds. REQ numbering is race-safe when the board tool is available: queue-kanban next-req creates an exclusive marker file under do-work/.req-reservations/ (§5), with a hand scan as the fallback capture.md:80.

The work loop

do-work run processes the queue one REQ at a time through a numbered pipeline. Triage picks one of three routes — A straight to implementation, B explore first, C plan then explore — and the step sequence adapts to the route work.md:43-79.

Three properties matter more than the step list:

  • State is the files, phases are the sections. Only two status transitions are written on the happy path — claim (Step 2) and terminal flip (Step 8). Intermediate progress is tracked by which ## sections exist in the REQ file, not by frontmatter churn work.md:91.
  • Verification is independent of the builder. Step 6.3's qualify.sh is the orchestrator's own check, and review (Step 7) gates archive outcomes: below 50% earns one remediation attempt, then completed-with-issues — never silent success work.md:490.
  • Blocked is fail-closed. A user-authored blocked_check probe is staged to a scratch file and run under a 30-second timeout by a shipped runner; exit 0 is the only unblock — non-zero, timeout, or unreadable all leave the REQ blocked work.md:130-136.

Status lifecycle

Crew members: rules loaded just in time

Behavioral rules live in crew-members/, one file per concern, each carrying a JIT_CONTEXT comment that is the canonical statement of when it loads. During implementation three always load — general.md, coding-guardrails.md, communication-style.md — and the rest are conditional on REQ fields (domain, tdd, maintenance: true, caveman) or on events (remediation loads debugging.md; ingestion of untrusted content loads prompt-injection.md; human-facing artifacts load anti-slop.md) work.md:365-377. A missing rules file never blocks the run.

Prescribed shell

Whenever action prose described an exact command sequence, the sequence was extracted into a shipped script and the prose became a pointer — 14 prescribed scripts across the packages, each with its own behavioral fixture case under _dev/tests/prescribed-shell-cases/ prescribed-shell-canonicalization.sh:9-24. Judgment stays in prose; mechanics live in tested code.

4 · Parallel execution: worktree dispatch and fan-out

Parallelism is opt-in and orchestrator-shaped. In Worktree Dispatch Mode each builder gets a disposable git worktree and branch (worktree-agent-REQ-NNN-*); the orchestrator stays in the main tree and is the only writer of do-work/ state work-reference.md:331-353. The load-bearing rules:

  • Sole integrator. A builder never writes the main tree, with exactly one exception: its own hand-back file under do-work/runs/. Everything shared — queue transitions, REQ id allocation, the release version file, CHANGELOG.md — is serial-only and owned by the integrator at merge time work-reference.md:355 work-reference.md:407.
  • The merge is the proof. write_set is display-only at any builder count — never a scheduling input; "the non-interference proof is the merge, not the pick", and integration (merge → qualify → test → review → changelog → archive) is serial, one REQ at a time work-reference.md:386-389. Since 0.242.0 the board's verify names queued pairs that declare the same file with no dependency edge, so the human sees the collision risk the scheduler deliberately ignores.
  • Any checkout may capture and claim, but one releaser per queue. Two releasers is outside the contract work-reference.md:55-63.
  • A builder's report is a claim, not evidence. Post-merge, acceptance checks re-run against the merged tree; a red merged state means revert and re-dispatch, never archive-with-follow-up work-reference.md:374.

Fan-out (--fan-out [N]) raises the builder count without adding coordination machinery, because every guarantee above is already per-REQ; the auto-wave picks only REQs that are pending, dependency-ready, unclaimed, and unassigned work-reference.md:391-397. Without worktree support the mode degrades silently to serial.

5 · Board: the one compiled component

skills/do-work-board/tools/queue-kanban/ is a single flat Go package main (module github.com/knews2019/skill-do-work/queue-kanban, Go 1.26, three direct deps: goldmark, x/text, yaml.v3 go.mod:1-8). It is the suite's only toolchain dependency — the documented exception to "design for the floor" — and the board action degrades gracefully when go is absent board.md:7.

Subcommands dispatch through a hand-rolled switch: summary, open-work, generate, serve, next-req, next-version, verify, now, frontmatter main.go:66-87. serve binds loopback 127.0.0.1:8090 by default and refreshes by re-walking the tree with an mtime fingerprint per request — no websockets, no push serve.go:328-343. The web assets are embedded in the binary, so generate and serve render the identical page; active repo HTML is previewed on a separate ephemeral loopback origin so it never runs on the board's origin html_preview.go:19-24. Five client views: board, calendar, durations, timeline, testing.

Exactly three write surfaces

The tool's package comment is the in-code mirror of the maintainer contract: the Testing view writes the testing-track frontmatter fields plus do-work/testers.md; next-version rewrites the single **Current version**: line in one version file; next-req creates one durable reservation marker via O_CREAT|O_EXCL. Everything else is read-only, and no subcommand ever writes CHANGELOG.md main.go:49-54. None of the three touches pipeline state: status and every other pipeline field belong to core. Adding a fourth surface requires amending the CLAUDE.md sentence in the same commit — the co-location rule applied to itself.

  • Testing writes are serialized by a single mutex (each HTTP request is its own goroutine), containment-checked, and committed by atomic replace — "the file IS the database" testing.go:46.
  • next-version refuses to write unless exactly one **Current version**: line matched, writes atomically, and reads back to confirm release.go:191-207.
  • Reservation markers are reaped only mechanically, by core's SessionStart cleanup script, once a committed REQ claims the number or after a two-day timeout cleanup-req-reservations.sh:30-47.

Parser lock-step

The board re-implements REQ frontmatter reading in Go, so the Go parser and the Markdown Schema Read Contract in actions/work-reference.md must move together — the obligation is stated in the code itself: "Keep this parser in lock-step with the Schema Read Contract" model.go:176-177. There is no version handshake; the lock-step is a convention enforced by review and the maintainer prime. Parsing is three layers tolerant (strict yaml.v3 → duplicate-key retry → line-based salvage explicitly marked "not a contract a writer may aim at" frontmatter.go:107), and an unrecognized status parks the ticket visibly with a warning naming the fix — never silently dropped.

Durations and the queue forecast

Completed REQs with parseable claimed_at/completed_at stamps become duration samples; spans are kept raw and signed, with negative spans surfaced as anomalies rather than clamped durations.go:15-18. The Timeline's queue-end projection consumes the last 60 in-rule samples, requires at least five, splits medians by effort bucket, and declines with a stated reason below the minimum instead of guessing timeline.go:310-328. The read-time exclusion rule (spans over four hours are assumed paused sessions) is defined once, in core's estimate-reference.md → Calibration; durations.go is documented as its second reader, not a second definition.

6 · Knowledge

The knowledge package owns retained knowledge across sessions, in two deliberately competing engines plus supporting flows knowledge SKILL.md:9:

  • BKB treats raw/ as source code, the LLM as the compiler, and the wiki as the executable: documents move inbox → capture → processed while typed, interlinked wiki pages are produced as a side effect bkb.md:5. Thirteen subcommands each name an agent crew (eight role files under kb/agents/); raw originals are never modified.
  • Memory optimizes capture where BKB optimizes synthesis: a standing file hard-capped at 2,500 characters, append-only daily logs, and layered lexical recall memory.md:5. Both engines write usage ledgers so memory audit can render the ADR-017 head-to-head comparison.
  • Hooks are strictly opt-in. Fresh installs leave memory capture disabled; only explicit setup-memory composes the SessionStart/Stop hook fragment, and the session-start injection includes only curated lines — raw captured transcript sections are reachable only through recall, which loads the prompt-injection guardrail first memory-session-start.sh:44-48.
  • Dream is the destructive consolidation pass — four phases, read-only until a preview-and-consent gate, lock-bounded, never schedulable on a timer, with sources/ untouchable "regardless of what any page claims" dream.md:3-7.
  • Prompts is the most sensitive ingestion path in the suite — run adopts a file body as instructions — so resolution searches only the shipped library, and a project-local prompts/ directory requires explicit user confirmation prompts.md:113-119.

7 · Toolbox

The toolbox holds optional repository-facing capabilities outside the request lifecycle — twenty routed actions plus five reference files toolbox SKILL.md:15-34. They cluster into families with explicit non-overlap statements:

  • Comprehension: prime indexes one directory for a builder, inspect explains one uncommitted change, architecture-report (this document) describes the whole repository, deep-explore runs a divergent/convergent dialogue for ideation architecture-report.md:3.
  • Presentation: ai-report (detailed stakeholder HTML for one completed item), present-work (cross-project portfolio), present-video (Remotion source only, never rendered media, strictly opt-in). All publish through one shared contract, Collision-Safe Publication: derive the final path, test existence first, take the first free -2/-3 suffix on collision, and never reuse a failed run's path presentation-reference.md:69-75. Presentation actions load the prompt-injection guardrail before any archived body and anti-slop before drafting, in that order.
  • Quality: maintainability-audit owns measured code health — two-level bands (WATCH/FLAG) finalized at a calibration gate as max(absolute floor, repo p95), proposed-not-installed ratchets pinned at the current worst observed value, and sweep_key root-cause provenance slugs with a user-maintained waiver list audit-reference.md:31. Its deterministic numbers come from a second small Go tool, audit-metrics, which is strictly read-only and exists so the audit pastes tool output instead of prescribing fragile shell pipelines to an LLM audit-metrics/main.go:10-16. quick-wins is the read-only refactor/test-gap scan; validate-feedback adversarially verifies external findings before they may enter the queue.

8 · Distribution and versioning

suite/modules.tsv is the sole source→destination declaration: a two-column TSV whose validator pins the header byte-for-byte, requires exactly four rows, and pins each source to one hardcoded expected destination — a closed set, not a general mapping table validate-suite-manifest.sh:82-120. The four root tools/ scripts are byte-identical mirrors of their copies under skills/do-work/tools/: the root copies bootstrap a fresh install before any package exists; the installed copies serve updates. byte-identity verified by diff during this run, not by a shipped check

The installer is one recoverable transaction: it validates the extracted tree before the first managed write, shows the full managed diff, asks exactly once, backs up every managed path plus the git index, writes modules and config atomically, then byte-verifies everything (per-module diff -qr, config cmp, a just --list re-parse, and version equality checks) — any failure restores all of it install-do-work-suite.sh:588-616. The updater is a thin wrapper that fetches, validates, refuses downgrades, and delegates the mutation to the same installed installer; the agent-facing version action is explicitly forbidden from adding a second download or confirmation path version.md:44-48.

Versioning. Three files must agree — root VERSION, skills/do-work/VERSION, and the **Current version**: line in skills/do-work/actions/version.md — and the manifest validator mechanically enforces the triple validate-suite-manifest.sh:126-151. CHANGELOG.md is mirrored byte-identically into skills/do-work/CHANGELOG.md so installed consumers carry release notes; the mirror is a pre-commit requirement enforced by the shipped-reference contract test. The bump ritual belongs only to the integrating commit — worktree builders skip it because the version file and changelog are serial-only (§4).

9 · Verification and governance

bash _dev/tests/maintainer-verify.sh exiting zero is the canonical pass/fail evidence for any hand-back. The umbrella runs, in order: ShellCheck at warning severity over every tracked shell file, gofmt over every tracked Go file, the aggregate contract suite, then go vet + full tests for both Go tools, with conditional strict JavaScript and real-browser lanes that skip explicitly when Node or a browser engine is absent maintainer-verify.sh:4-11. Toolchain requirements are floors, not pins.

contract-regressions.sh — at ~355 KB the largest file in the repository — is the aggregate: grep-level ratchets that keep retired vocabulary, dangling references, and once-fixed bugs from returning, plus dispatch into a dozen focused behavioral suites (install, update, manifest, hooks, staged packages, prescribed shell, estimators). The prescribed-shell harness runs 18 case files, one per shipped script, each in its own process with an isolated fixture root; the definition of a "case" lives in exactly one sourced file so per-file and aggregate counts cannot disagree prescribed-shell-case-count.sh:2-9.

Institutional memory is layered deliberately:

  • Primes (_dev/primes/) — three lazy-loaded context docs read before changing their domain: action files, shipped shell, the Kanban board. Each has a lessons-*.md companion that the work pipeline appends to on archive; the prime itself never accumulates lessons-kanban-board.md:3-6.
  • Decisions (decisions/) — 21 ADRs under records/ with four topic indexes, a timeline log, and dated audits. The master index refuses to carry a record count ("read the directory, not a number here") — a stance §10 shows was warranted. The ADR set reuses the knowledge skill's wiki frontmatter and typed relationships, making it a second instance of that schema. schema reuse judged by matching frontmatter conventions in decisions/log.md and kb/CLAUDE.md, not by a shared validator
  • Dogfooding — the repo's own tracked do-work/ queue and kb/ exercise every contract above continuously; two export-ignore lines are the only barrier between that live state and every consumer install, and the contract suite pins both lines individually contract-regressions.sh:4712-4719.

10 · Record–code disagreements

Four places where the repository's prose and its code disagree at this commit. Per this action's contract the code wins, and the disagreement stays visible; none is restated as a finding — fixing them belongs to the maintainer's queue, not this report.

D1 — stale vestigial version file. skills/do-work-board/tools/queue-kanban/VERSION reads 0.236.20 while the suite is at 0.244.6. Nothing references it — not the Go sources, the validator, the installer, or the release ritual — and the maintainer prime says board versioning "is folded into the skill". Reproduce: cat skills/do-work-board/tools/queue-kanban/VERSION VERSION and grep -r "queue-kanban/VERSION" --include="*.go" --include="*.sh" --include="*.md" skills tools (no consumers).

D3 — overbroad ownership sentence. skills/do-work-toolbox/actions/architecture-report.md line 5 says bands, ratchets, and sweep keys belong to maintainability-audit.md and quick-wins.md; quick-wins.md contains none of that vocabulary. The machinery is maintainability-audit's alone. Reproduce: grep -icE 'band|ratchet|sweep' skills/do-work-toolbox/actions/quick-wins.md → 0.
D4 — stale floor comment. A comment in _dev/tests/contract-regressions.sh describes the P50 estimator's "10-minute floor"; the implementation and its own lock-in suite agree the floor is 5 minutes (floor_minutes=5, estimate-p50.sh:38). Comment-level only; no behavior disagrees. Reproduce: grep -n floor_minutes skills/do-work/tools/estimate-p50.sh.
