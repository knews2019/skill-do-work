2 · Spoken briefing — read this aloud

Briefing

Written to be listened to: continuous prose, no shorthand, no file paths, nothing you need prior context to follow. Every identifier is explained the first time it appears.

The headline is that the project's time estimator now predicts from measured history instead of from a guess, and the project's task board can no longer quietly render a finished task whose completion timestamp sits before its start timestamp. Five units of work delivered that on 17 August 2026, and all five verified clean.

Some background, because none of this makes sense without it. This repository builds do-work, a task-queue skill that coding agents install into their own projects. Work arrives as what the project calls a user request, meaning a durable written statement of what the maintainer wants, and it is then split into numbered requests, each of which is one implementable slice that runs through the pipeline on its own. The batch this report covers is UR 48, the user request titled calibrate the estimator from archive actuals and surface negative-duration anomalies. It came straight after UR 47, the user request that had built the estimator in the first place — a small script that prints a fifty-percent-confidence figure for how many active minutes a piece of work will take, before anyone starts on it.

The trouble with that estimator was that its numbers were never measured. Its starting figures had been lifted from a worked example in the design document, so it was guessing with the confidence of arithmetic. REQ 211, the re-fit of the estimator's scoring table to archive actuals, replaced those guesses with the record. One hundred and ninety completed requests in the archive carried both a claim timestamp and a completion timestamp. Two were discarded under a rule the maintainer set, namely that any span longer than four hours is assumed to be a paused session rather than four solid hours of work. That left one hundred and eighty-eight real measurements. Their medians, grouped by the three difficulty routes the pipeline uses, came out at 4.7 minutes for the light route, 9.2 minutes for the medium route, and 21.4 minutes for the heavy route — against the old starting figures of ten, twenty-five, and forty-five minutes. The estimator was between two and a half and five times too pessimistic. So the starting figures became five, ten, and twenty minutes, the minimum possible estimate dropped from ten minutes to five, and every add-on weight for things like a wide set of files or browser testing was divided by roughly two and a half. The provenance of that arithmetic — the sample counts, the outlier rule, the medians, and an honest note that wall-clock time is a slightly generous proxy for active time — was written into the estimator's reference document so the next person re-fitting it does not have to guess where the numbers came from.

Then came the obvious follow-on. Re-fitting the table required mining the version history by hand, which is exactly the kind of archaeology nobody wants to repeat. REQ 212, the archive-time calibration log, makes the system record its own accuracy from now on. Every time a completed request is archived, if it carried an estimate, the pipeline appends one line to a small tab-separated log holding the request identifier, its route, the minutes that were estimated, the raw minutes it actually took, and its completion timestamp. The log deliberately stores the raw span with no judgement applied, and the four-hour outlier rule is applied later, when the log is read. That split matters: it means a future maintainer can change the outlier rule without having lost the underlying data. The log already holds eight lines, seeded with this session's own work, and it makes a quietly uncomfortable point — REQ 208 was estimated at eighty-five minutes and took fourteen, and REQ 211 was estimated at thirty-five minutes and took three. The calibration was needed, and the log now proves it continuously.

The second half of the batch came out of the same archive mining. While measuring those spans, one archived request turned out to have finished six seconds before it was claimed, which is not physically possible for timestamps written in order. The usual cause is that one of the two stamps was written using local wall-clock time but labelled as universal time. The board, which is the human-readable view of the queue, had a check for suspicious completion data, but that check gave up as soon as the completion timestamp parsed successfully, so a reversed span sailed through and rendered as a perfectly normal card. REQ 213, the board's negative-duration anomaly detection, closed that hole. It fires only when both timestamps parse and the finish is strictly earlier than the start, it reuses the anomaly reporting channel that already existed rather than inventing a second one, and its message names both raw timestamps along with the likely cause and the fix.

That change was reviewed, and the review found two things worth its fee. The first was a genuine gap between what the work promised and what the code did: the board's mechanical checking command, called verify, was reporting no findings at all on a tree that the board's own summary said carried flagged anomalies, because verify only ever lifted duplicate-identifier warnings into findings. So REQ 214, verify surfaces completion anomalies as findings, added that probe — verify now reports each anomalous request and exits with a failure code, which means broken completion bookkeeping fails the mechanical gate instead of passing silently. The second finding was that all the shipped prose describing this family of anomalies still defined them as cases where the completion instant cannot be resolved, which is simply untrue for a reversed span whose completion instant resolves perfectly well. Worse, the warning line was telling people to re-stamp a timestamp that was already valid. REQ 215, the anomaly-class prose sync, fixed that in four places, and it also updated a test that had been pinning the self-contradictory wording in place.

After the batch was archived, a pull-request review on the branch — pull request one hundred and forty — produced four more findings, all accepted and fixed in one commit that also carried the version to 0.199.2. Three tightened the multi-request estimate summary so that dependency chains and unestimated members no longer distort it, and the fourth made verify honest in environments without version-control access: an anomaly that consists only of a commit hash the system cannot date is a missing tool, not a broken record, so it is reported as a skipped check rather than a failure. Genuine on-disk defects still fail.

There is one honest wrinkle worth stating plainly. During the work, the archive appeared to carry ten anomalies. Today the same commands report one. That is not a regression and not a silenced check: nine of the ten were requests whose recorded commit hashes the working copy could not resolve at the time, because those commits lived only on a branch that had not yet been merged. All two hundred and four recorded hashes resolve now, so those nine were never archive defects at all. The one that remains is the genuinely reversed span, REQ 91, and repairing an archived timestamp is the maintainer's call rather than something a tool should rewrite on its own.

What all of this is worth, in plain terms: estimates are now defensible rather than decorative, they will keep improving without anyone doing archaeology, and a class of bookkeeping corruption that used to be invisible now fails a check instead of rotting quietly in the archive. The one decision waiting on the maintainer is whether to repair REQ 91's timestamp, because until it is repaired, the board's mechanical check will keep exiting with a failure on this repository — which is the check working as designed, but it does mean any automation that treats that command as a gate is currently red.

REQ-211 re-fit the P50 estimator's scoring table to 188 measured archive spans. Route bases moved from 10/25/45 minutes to 5/10/20, the floor from 10 to 5, and all twelve signal weights were divided by ≈2.5. The confidence rubric was re-anchored to the new scale. REQ-214 — generated by REQ-213's review — made queue-kanban verify lift those anomalies into findings and exit non-zero, closing a gap where verify reported OK: no findings while the board's own strip showed flagged tickets.

REQ-215 — also review-generated — swept four places whose prose still defined an anomaly as an unresolvable completion instant, including a warning line that told users to re-stamp an already-valid timestamp.

What was wrong before

Why the estimator was wrong, not just imprecise

An estimate derived from a design document's illustration is a prior dressed as a measurement. Measured against 188 real spans it ran 2.5–5× high. The fix was not to nudge it but to replace its scale with the distribution it was supposed to be describing.

Acknowledged bias: wall-clock span is used as a proxy for active time. For this corpus the runs were autonomous, so the proxy is close; where it errs it errs upward, keeping estimates mildly conservative. That caveat is recorded in the reference file, not just in a commit message.

5 · How it works

Two flows, both now closed loops

Why the gate had a hole

Three of the four consumers on the right already existed. The board's summary strip, the generated payload the web view reads, and the "never-silent" warning line all consumed the anomaly flag — so a human looking at the board would see the problem.

The fourth, verify, is the one a script or a pre-commit habit calls. It had never been wired in: it lifted only duplicate-identifier warnings into findings. So the anomaly was visible to a person and invisible to automation, which is the wrong way round.

REQ-213's requirement text asserted verify already surfaced the class. The review checked the consumer instead of trusting the claim, which is how the gap was found rather than shipped.

6 · Value delivered

What the maintainer gets

Estimates you can defend

A signal-free estimate for a route is now that route's empirical median from 188 samples, with the sample count, outlier rule, and bias direction recorded next to the number. When an estimate is questioned, the answer is a measurement rather than a rationale.

Calibration without archaeology

The next re-fit reads a log instead of reconstructing history from commits. Because raw spans are stored and filtering happens at read time, the outlier rule can be changed later without the underlying data having been thrown away.

Corruption that fails loudly

Impossible completion bookkeeping now fails a mechanical check rather than rendering as a normal card. The check reports and routes; it never rewrites archived frontmatter, so repair stays a deliberate human act.

Documentation that matches the code

Every surface describing an anomaly now reads true for all four classes, and each class states its own fix where it is detected — so a new class cannot inherit a stale, self-contradicting instruction.

No throughput, cost, or adoption figures are claimed. The measurable figures in this report are the calibration samples and the estimator's own outputs, both reproducible from the commands below.

10 · Decisions for you

Two open decisions, with recommendations

Should REQ-091's reversed timestamp be repaired, and if so, by whom?

Context. One archived request, REQ-091, records a completion instant six seconds before its claim instant — almost certainly a local wall-clock time written with a UTC Z suffix. Since REQ-214 shipped, queue-kanban verify exits non-zero on this repository because of it. Repairing archived frontmatter is deliberately outside every tool's write surface, so it needs a human decision.

Why it matters. The mechanical gate is currently red on a clean tree. If any automation, hook, or habit treats a green verify as the precondition for committing or releasing, that signal is now permanently red until the stamp is fixed — which trains people to ignore it. Ignoring a check is worse than not having one.

Trade-off. Editing an archived record rewrites history and sets a precedent that archive frontmatter is mutable; the wrong true instant is also unknowable now, so any repair is a best estimate. Leaving it alone preserves the record exactly but keeps the gate red and normalises a failing check.

Recommendation: repair it, as an explicit owner-authored commit that states in its message that the stamp was corrected and why — one honest edit with visible provenance beats an indefinitely red gate. Set completed_at to the claim instant plus the observed work duration if that is recoverable, otherwise to the claim instant itself, and note the estimate in the commit message.

Should the estimator be re-fit now that the log shows the calibration still runs high?

Context. The calibration log's first eight lines show every estimate exceeding its actual — REQ-208 at 85 estimated against 14 actual, REQ-213 at 35 against 10. The first two REQs priced by the calibrated table, REQ-214 and REQ-215, were estimated at 10 minutes and took 2. The re-fit reduced the error substantially but did not remove it.

Why it matters. An estimator that is consistently 3–5× high on the signal-bearing cases will be silently discounted by whoever reads it, which is functionally the same as not having one. But the eight samples are all from two autonomous sessions on one machine, which is a thin and possibly unrepresentative basis.

Trade-off. Re-fitting now risks chasing noise and locking in a bias from a single fast session; churn also costs a re-pin of nine lock-in tests each time. Waiting collects a broader sample but leaves the known upward bias in place, and the bias is in the direction the calibration record already declared acceptable.

Recommendation: wait. Do not re-fit until the log holds roughly 30 lines spanning more than one session, then re-fit the signal weights rather than the route bases — the eight samples show the bases landing reasonably and the per-signal surcharges overshooting. This is a deliberate defer, not an oversight; the log now accumulates the evidence without further effort.

Reported, no decision needed

Three minor findings were recorded as report-only and remain open by choice: the confidence rubric's constants are restated in reference prose and pinned only by tests; the calibration log's wall-minutes lack an explicit rounding rule in prose, so two agents could differ by one minute; and an anomalous ticket inside the recent window appears in both the anomaly strip and Recently done. The third was flagged as wanting a deliberate policy decision eventually, but nothing depends on it today.

11 · Lessons and open questions

What the session learned

Worth keeping

Running the stale test pins as the RED phase turned a 17-constant recalibration into a real red-green cycle: nine probes failed naming the exact old values, then went green on the re-pin. Arithmetic was never trusted on its own.

Constraining the reviewer to hands-on execution — run the binary, probe the edges — found the gap that mattered. No static read would have noticed that a never-silent warning existed while nothing consumed it.

Uniqueness-asserted anchor rewrites (assert exactly one match before replacing) made a seventeen-constant edit safe in one pass.

Worth not repeating

REQ-213's requirements named "verify's never-silent line" from a capture-time assumption nobody re-checked against verify.go. The builder noticed the mismatch and quietly dropped the word "verify" from its summary instead of surfacing the discrepancy — the false premise survived into a shipped contract and cost a follow-up REQ. The lesson recorded: verify the consumer, not just the producer, when naming a reporting contract.

A first insert was numbered 8.5 while physically placed before substep 8; and the baseline gate was once invoked from the Go module's working directory, exiting 127 with an empty log. Anchor placement and label must be decided together, and relative-path gates run from the repository root.

Open questions in the archive

None of the five REQs left an unresolved ## Open Questions section. All decisions were recorded as decided-and-stated, including two that a future re-fit will want to know about: the confidence low-threshold was set to a raw score of 75 (about twice the heavy route's p80) rather than the arithmetically scaled 72, purely for a rounder number; and a zero-length span with identical stamps stays legal, because only a strictly reversed span is impossible.

Absent optional evidence: no screenshots or assets exist for any of the five REQs, which is expected for this change set. Every REQ carries a recorded commit hash, testing record, and review verdict; nothing required was missing.
