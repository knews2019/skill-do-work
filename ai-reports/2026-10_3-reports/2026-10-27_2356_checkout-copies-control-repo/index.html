Checkout copies: a control repo with do-work on top

Proposal report, 2026-10-27. Nothing is built yet. Written by Claude (Fable 5.1) from the do-work 0.307.0 sources and a read-only look at the target folders.

Verdict: workable, with one real cost. The parent folder becomes a small private git repo that owns do-work and the queue. The checkout copies sit inside it as ignored, fully independent clones. The team repo and every copy stay free of do-work files. The cost: the do-work loop cannot see code changes inside a copy, so code is committed with plain git inside the copy and the REQ only records the evidence. That turns do-work here into a planner, tracker, and log, not a builder that commits and releases your code.

1. What the folder looks like

/Users/t2/2code/etc-checkout-work-folders/        private git repo ("control repo")
├── .git/                                         tracks only the lines below marked [tracked]
├── .gitignore                       [tracked]    ignores etc-checkout-*/ and .DS_Store
├── CLAUDE.md                        [tracked]    map of the folder + rules for sessions
├── .claude/skills/do-work*/         [tracked]    the four do-work skills, installed from 0.307.0
├── .claude/settings.json, justfile  [tracked]    do-work hooks and Just recipes
├── do-work/                         [tracked]    the queue: URs, REQs, archive, changelog
├── tools/new-copy.sh                [tracked]    clone + branch one new copy
├── tools/copies-status.sh           [tracked]    branch, ahead/behind, dirty count per copy
├── tools/sync-copies.sh             [tracked]    fetch all, fast-forward clean copies
├── etc-checkout-kuki-2026-10-27_print_gift_bonus_list/   [ignored] standalone clone, own branch
├── etc-checkout-kuki-2026-11-02_some_feature/            [ignored] standalone clone, own branch
└── ...

/Users/t2/2code/etc-checkout-main/                team repo, untouched: no do-work, no CLAUDE.md

Each copy is a normal git clone with origin pointing at git@github-work:thevirtuelabs/checkout.git. No submodules, no worktrees, no shared .git. The control repo ignores them, so git never records them as gitlinks.

2. How one task flows

  1. You start Claude Code in the parent folder. It loads the control repo's CLAUDE.md and the do-work skill.
  2. You capture a request. The UR and REQ files are written into do-work/ in the control repo. The REQ names the target copy on a Copy: line, or asks for a new copy first.
  3. The loop runs the REQ. The implementation step edits files and runs tests inside the copy, then commits there with plain git on the copy's own branch.
  4. The REQ records the copy's commit hash and the test command as evidence. The control repo commit holds only REQ files plus the control repo's own changelog and version bump.
  5. You push the copy's branch and open the pull request yourself. That is operator work and never a REQ.

3. Pros and cons

Pros

  • clean The team repo and every copy never see do-work/, .claude/, URs or REQs. Your pull requests carry only product code.
  • one queue One place holds every task across all copies, with one changelog as the cross-copy work log.
  • one session You run Claude Code once, in the parent folder, and reach every copy from there.
  • independent Copies are plain clones. Deleting one, or breaking one, cannot damage another or the control repo.
  • visible Sessions started inside a copy still read the parent CLAUDE.md, so the rules travel with you.
  • cheap Setup is a git init, one install run, three short scripts, and one doc.

Cons

  • blind loop do-work's diff, commit, and release steps only see the control repo. Code in a copy is invisible to them. Every REQ must state its evidence by hand (copy commit hash, test command). This is the main cost and it does not go away.
  • no fan-out Parallel builders use git worktrees of the queue's repo. A worktree of the control repo contains no copies, so run --fan-out and --coordinate are useless here. Serial runs only.
  • unsupported shape do-work's documented multi-checkout model is "queue inside the product repo, synced by git". This setup is outside that contract, so future skill updates may add checks that fight it (for example a rule that refuses a REQ with an empty project diff).
  • meaningless version The release tail bumps a version and writes a changelog for the control repo on every finished REQ. Harmless, but the number means nothing.
  • two git contexts Every command must be clear about which repo it runs in. A commit made in the wrong directory is the most likely daily mistake. The scripts and CLAUDE.md reduce this, they do not remove it.
  • disk Each copy is a full clone. A local clone from etc-checkout-main shares object files through hardlinks, so the cost is mostly the working tree.

4. The alternatives that were rejected and why

ShapeWhy not
do-work inside the team repo, copies sync the queue by gitThis is the shape do-work supports best. Rejected because do-work files would reach the team's main branch through your pull requests. You confirmed the team repo must stay clean.
do-work inside each copy, ignored by gitClaiming and finishing a task are commits. With the queue ignored there is nothing to commit, so the loop breaks at the first claim.
No do-work; only CLAUDE.md and scripts in the parent folderSimplest, but gives no task queue across copies. You said you want the skill available.
git worktrees instead of clonesWorktrees share one .git and one branch cannot be checked out twice. You asked for standalone copies.

6. How we check it works

  • Create a smoke copy on a throwaway branch. The control repo's git status stays clean. The copy has no do-work/, .claude/, or CLAUDE.md. etc-checkout-main is unchanged.
  • The status and sync scripts list the smoke copy correctly. Then the smoke copy is deleted.
  • The installed CLI reports version 0.307.0, and /do-work help routes in a session started in the parent folder.

7. Open point for you

The "blind loop" con is the one to accept or not. If you want do-work to actually build, test, commit, and release code, this setup will not do that for code inside a copy. If you want it as the task queue, planner, and log across copies, with the code commits done by plain git in the copy, this setup fits. The plan assumes the second reading.
