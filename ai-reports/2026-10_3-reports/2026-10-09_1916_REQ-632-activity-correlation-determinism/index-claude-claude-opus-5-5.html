How the board decides when a request was last worked on

This page rewrites the original report for clarity and brings it up to date. The original was written on 2026-10-09 to help the maintainer make one decision. That decision has since been made and shipped, so parts of the original now describe code that no longer exists.

The main change since the original report: the original asked whether to keep or delete the "merge-range" code. On 2026-10-10 the maintainer deleted it without building the commit-stamping tool the report paired with deletion (release 0.305.88, commit 4cc2fb20). See Decisions and Corrections.

TL;DR

The do-work board shows each in-progress request card with a ticking "last activity" line. Each finished request's detail drawer gets a "Largest gap between events" row. Together they replaced a badge that guessed "assumed pause" from total duration alone.

The board combines two kinds of evidence: the timestamps the request file records about itself, and the git commits linked to that request. A commit is linked only if it touches the request's file or its subject carries a [REQ-NNN] tag. A live builder branch's latest commit also counts.

The feature has shipped and works. The extra code that credited untagged commits through merges was deleted on 2026-10-10. Correct crediting now depends on agents following a written commit-tagging rule, and nothing enforces it.

How it works

These steps run once for each board page the live server serves, and once for each static generate.

  1. Read worktrees and branches once. readWorktreeAgentGitState runs worktree list, branch --list, rev-parse --abbrev-ref HEAD and one for-each-ref --no-merged. The verify probes reuse this result instead of running git again.
  2. Pick the cards and the window. Only claimed and recently done cards are tracked. The log window starts 7 days back, or at the oldest claim among those cards if that is older (activity_correlation.go:276-285).
  3. Run one git log. It returns each commit's hash, date, subject and touched paths. If git fails, the stamps are still used (:157 comment, :162-164).
  4. Credit each commit. A commit counts toward a request if it touches that request's file or run artifact, or if its subject has [REQ-NNN].
  5. Add live branch tips. Each owned builder-branch tip date is added as one more commit event for its request.
  6. Merge, clip and sort per request. Only events between claimed_at and the later of completed_at and release_at count. An open request's window runs to now. When a stamp and a commit share a timestamp, the stamp sorts first.
  7. Report. A claimed card gets its newest event and that event's phase. Any card with at least two events gets the largest gap and the phases on each side of it.
Worked example: why the old badge was wrong (from UR-135)

In UR-135 (the maintainer's design brief), a consumer-project request, REQ-2248, took 4h 21m from claim to completion. The old badge would label that a pause. Its stamps showed the largest gap between phases was about 67 minutes, and "Nothing was paused" (do-work/archive/UR-135/input.md, the "Evidence from one real REQ" section).

Searching only for [REQ-2248] in commit messages showed a false 2h53m gap. During that gap, seven commits with other prefixes touched the request file. That is why touched paths are the main signal and the tag is secondary.

Git commands per refresh: 5, however many branches exist

The original report counted five commands on a canned runner with 0, 1 and 4 branches (evidence/git-call-count.txt). A detached repo-root checkout adds one rev-parse HEAD. Three of the five are needed by the verify probes anyway, so the feature itself adds two: the for-each-ref and the git log.

That count came from base 2eb14357. At HEAD the sequence of calls is unchanged (verify.go:1478-1503, activity_correlation.go:160), and TestServedResponseListsWorktreesAndBranchesOnce (activity_correlation_test.go:287) still pins that the count does not grow. I did not rerun the count.

The decision the original report was written for

The maintainer's concern was "I don't want to build scaffold around not-deterministic behaviour" (do-work/archive/UR-143/REQ-651-…md, Why). The report offered two options. A third one shipped.

What shipped (option 3)

Delete the scaffold and write no stamp code. The commit message gives the reason: "A stamp cannot be deterministic without owning the commit (a hook in every consumer repo, or a wrapper any agent can bypass), so it would only move the non-determinism down a layer."

Instead, the tagging rule was written into the per-request branch contract, covering both builder commits and the hand-back merge (skills/do-work/actions/fan-out-reference.md:39, step 3 at :80). That file says plainly: "The prose rule is the whole mechanism; no hook or wrapper stamps it."

Sources: commit 4cc2fb20 (0.305.88) and commit 7676a183 (0.305.89); CHANGELOG.md:290-300.

Report option 1

Stamp the tag, then delete. A CLI or commit hook would add [REQ-NNN] to every builder commit, taking the id from the branch name. Then the merge-range code would be deleted. The report estimated 54 production lines and 92 test lines removed, but the size of the stamp code was unknown.

Report option 2

Keep the current code. Untagged builder commits would keep getting credit through the merge that brought them in, in any repository. No new code would be needed.

What the shipped choice gives up

A claimed card loses nothing, because a live builder's work shows up through its owned branch tip. After merge, a builder commit with neither a tag nor a request-file change no longer appears in the finished request's largest-gap line. The lessons file calls this "the honest consequence of the missing prefix" (lessons-do-kanban.md:15).

Glossary

REQ / URA request (one unit of queued work, file REQ-NNN-*.md) and a user request (the original ask that one or more REQs come from, folder UR-NNN/).
ClaimedA request an agent has picked up and is working on now. Only claimed cards show "last activity".
Lifecycle stampA timestamp in a request's frontmatter recording when it entered a phase, such as claimed_at or review_at. Stamps are only ever added, never edited.
BuilderA sub-agent that implements one request on its own git branch and worktree.
WorktreeA second working folder attached to the same git repository, so a builder can work without touching the main checkout.
Hand-back mergeThe merge commit that brings a builder's branch into the integration branch. Its subject should be [REQ-NNN] merge builder branch ….
Integration branch / refThe branch builders merge into, which is the repo-root checkout's branch (usually main).
Owned tipA builder branch's newest commit, but only if the integration branch does not already contain it.
^1..^2 rangeFor a merge commit: the commits reachable from its second parent but not its first. In other words, what the merge brought in.
ScaffoldThe maintainer's word for code that exists only to cope with agents not doing something reliably.
DeterministicFully fixed by recorded facts, such as git history and frontmatter, rather than by how an agent happened to write a message.
Verify probesThe board's checks for leftover worktrees and branches. They share the git read with this feature.
mtime, pathspecFile modification time; a path filter on a git command. Hover the underlined terms above for short versions.
