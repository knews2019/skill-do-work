level 1 · the sixty-second version

What was delivered

Tasks that touch different files can now run at the same time, each worker in its own isolated copy of the project, with one coordinator merging results. And the system's bookkeeping — which task is claimed, what a review actually inspected, when a request counts as finished — was made to tell one consistent story everywhere it is written down.

Why it took ~19 hours, not one

The two asks started as 11 tasks and grew to 28. Every change was attacked by independent reviewers before it could ship, and those reviews kept finding real, quiet flaws — each became a new task, was fixed, and the fix was reviewed the same way. A few decisions were escalated to you, and the work waited for your answers.

What it is worth

The failures this closes were the silent kind: a review that passes while inspecting nothing, a half-built task reset because its claim was forgotten, a request filed as done while follow-ups still sat in the queue. Each of these existed in the rulebook until this batch; none survives it.

level 2 · the story, for listening

Plain language, written to be read aloud

No prior knowledge assumed. About four minutes.

This is the story of one day of work on a piece of software called do-work. First, what do-work is. When a person asks an A. I. assistant to do programming work, big jobs go better if they are broken into small tasks, written down as cards, and finished one by one, with every card checked before it counts as done. Do-work is the rulebook and the filing system for that. It keeps a to-do list called the queue. Every task is a card in that queue. And it holds the written instructions for how a card gets picked up, built, checked, and filed away.

Until this week, that rulebook had one big limitation. Only one card could be worked on at a time, even when two cards had nothing to do with each other. You asked for that to change. That was the first request.

The obvious danger in working on two things at once is two workers changing the same file at the same moment — like two people editing the same page of a shared document and saving over each other. So the change came in two layers. First, every card must now declare, up front, exactly which files it plans to change, and the system only lets two cards run together when their lists do not overlap. Second, each worker can be given its own private copy of the entire project to work in, and a single coordinator is the only one allowed to bring finished work back into the real copy, one merge at a time. The task board — the visual view of the queue — also got a warning badge that lights up when two waiting cards want the same files.

That first request began as three tasks. It ended as seventeen. Here is why, and this is the heart of the story. Every change in this system is examined by independent reviewers whose entire job is to prove the change wrong. Those reviewers kept finding real problems — not typos, but the quiet kind that lose work without anyone noticing. One example: the note that records which card a session is working on could only remember one card at a time, so starting a second card made the system believe the first had been abandoned — and it would have reset that card in the middle of being built. Another: after a worker's private copy was merged back, the quality checks looked in the wrong place, saw nothing, and would have said all clear about work they never actually inspected. A passing check that inspected nothing is worse than no check at all.

Each finding became a new card, was fixed, and the fix itself was reviewed the same way. Then you asked for something harder: a second, deeper review of everything that had already shipped. That was the second request. It started as eight repair tasks and grew to eleven, and it kept finding one pattern over and over: the same rule written down in two places, where one copy had been updated and the other still carried the old meaning.

The biggest case was the definition of done. Three different parts of the system decide whether one of your requests is completely finished. They disagreed. One of them would have filed a request away as complete while another could still see unfinished work sitting underneath it. All three now point at one single definition instead of keeping their own copies. And the review instructions themselves were changed, so that from now on, whenever a rule changes, the reviewer is required to hunt down every other place that states that rule and flag the stale ones.

So why did this take most of a day rather than an hour? Because all twenty-eight changes were reviewed by independent checkers — the riskiest ones by panels of ten or twelve, half of whom existed only to shoot the findings down. Because the checkers kept being right, and every fix they forced was itself re-checked. And because a handful of decisions were genuinely yours, so the work paused and waited for your answers.

The payoff: many tasks can now run at the same time without stepping on each other, and the bookkeeping that decides what is done, what failed, and what still needs attention finally tells one consistent story. The very last review found one more loose end — a task that fails permanently had no way to ever be laid to rest, so the request above it could never close. You have since answered how it should work, and that final fix is approved and waiting in the queue for the next run.

level 3 · what shipped, by theme

Three themes, twenty-eight items

Every item below is a written rule, check, or document in the skill — versioned and committed like code. The full list with commits is under the table toggle.

Run work in parallel, safely

8 items · the original ask

  • Every task declares its files up front; only non-overlapping tasks co-run — with a re-check once real file lists firm up, on every task route.
  • Each worker gets an isolated project copy on its own branch; one coordinator merges, in dependency order.
  • The board warns about overlapping queued tasks — with a matcher that behaves the same on every operating system.
  • Crashed tasks restart under a fresh name instead of jamming on their own leftovers, and cleanup targets the name that was actually used.

Checks that see what was actually built

8 items · found by reviews

  • After a merge from a worker copy, quality checks, review, and reporting all read the merged range — not the clean main copy — and fail loudly if the range is unreadable.
  • Re-reviewing parallel-built work now shows the real change instead of an empty page (merge-aware diff reads, six sites).
  • A worker that did real work before hitting an outside blocker is recorded as failed-with-follow-up, not "never started".
  • Reviews must now sweep for every restatement of a changed rule — the batch's most common defect, made a required hunt.

One definition of done, honest records

10 items + 2 decision tickets

  • All three places that decide "is this request finished?" now share one canonical definition — a failed task holds its request open.
  • The session lock records every claimed task, survives its own crash recovery, and cannot be clobbered by a slow predecessor.
  • Documentation corrected wherever it described behavior the software does not have; a human guide to the board was written.

level 4 · why it took the time

Eleven tasks in, twenty-eight out

Where the hours actually went

Each shipped item ran the full per-card pipeline:

claim→build→automated gates→adversarial review→commit→archive
  • Reviews were adversarial and they kept winning. The riskiest changes got panels of 10–12 reviewers — half assigned to refute the other half's findings. Three of this batch's final changes came back "fix, then pass"; every forced fix was re-verified.
  • Findings became tasks, recursively. Ask 1's three tasks spawned six follow-ups; the deep review's sweeps found the same bug in two more places and three documentation mismatches.
  • Some work had to wait in line. Five of the deep-review repairs all edited the same two instruction files, so they ran one after another — the overlap rule this very batch built, applied to itself.
  • Some decisions were yours. Two decision tickets and four clarify rounds paused for your answers — including one where you overrode the builder's own recommendation.
  • Two incidents, both absorbed. One builder died mid-task on a transient error and a successor finished from the recorded trail; one review round hit a usage limit and the coordinator ran the review itself.

level 5 · the value, concretely

Seven silent failures that no longer exist

Every one of these was possible in the rulebook before this batch. None is exotic — each was found by an actual review of actual instructions, and several were caught live.

  1. Two tasks running at once edit the same file and silently overwrite each other.
  2. Starting a second task erases the record of the first, which gets reset mid-build as "abandoned".
  3. Quality checks and review pass on merged work they never saw — an empty inspection reported as clean.
  4. Re-reviewing finished parallel-built work shows an empty change list, so there is nothing to catch mistakes against.
  1. A request is filed away as complete while unfinished follow-up work still sits underneath it — three deciders, three definitions of done.
  2. A worker that did real work before hitting an outside blocker is misfiled as "never started", losing the failure signal and the follow-up.
  3. A rule is updated in one place while a stale copy elsewhere keeps the old meaning — the root shape behind most findings, now a mandatory review hunt.
