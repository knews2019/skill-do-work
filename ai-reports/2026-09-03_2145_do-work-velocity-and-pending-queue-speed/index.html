02 / Understand the time

A request’s elapsed time includes much more than building.

A REQ is one queued request. Its lifecycle includes preparing the work, building it, checking it, and closing its records. This diagram explains those stages; its boxes are not proportional to duration.

1 → PrepareSelect, plan, explore

Read context, decide scope, record the approach.

2 → BuildImplement and test

Change the code and check the intended behavior.

3 → VerifyIntegrate and review

Check the landed change. Failed checks can require remediation.

4 → CloseRelease and archive

Record the outcome and settle the request’s lifecycle.

04 / Lessons to keep

Use the evidence without making the process heavier.

L18 · Measurement cost

Instrumentation must be cheaper than the work.

Write bounded raw events in Git-private state and fold one summary into finalization. Extra planning, artifacts and commits can overwhelm the small measurement they support.

L19 · Comparable samples

A new median needs its sample beside it.

The 65-, 11- and 51-minute figures cover different requests and intervals. Show counts, endpoints and caveats before using them to claim a speedup or regression.

L20 · Lifecycle state

Implemented and completed are separate states.

Timestamp preservation and the previous Activity wave are now archived. The evidence-gate regression request is merged and reviewed but remains claimed. Read the archive and current phase evidence together: neither an old report nor a commit alone tells you what remains.

L21 · Expected return

A prerequisite is not the source of the saving.

The shared-principles move enabled the now-completed reference cut. The reference is smaller, but neither moving prose nor deleting it proves a runtime saving. Measure comparable requests before assigning a speedup.

L22 · Safe reuse

Reuse evidence when the inputs match.

The heavy-lane cache is bounded by age and fingerprints, and now refuses reuse when another lane changes tracked inputs or HEAD. Queue-only bookkeeping stays exempt. A recent timestamp alone is not valid evidence.

L23 · Remaining uncertainty

Parallelism is not proven to be the only remaining lever.

Three real timing summaries exist, but only two of ten categories are wired. One reports zero unattributed while omitting 52m 32s outside its event window. Measure missing and overlapping time before ranking the next speed optimization.

L24 · Passing checks close

A check that passes must never lower readiness.

The retired green-heavy answer lowered dependency readiness. The held-request fix removed that detour: reviewed work stays claimed, and a green drain finalizes it. Preserve this principle when changing another successful transition.

L25 · Read the rule, not the word

The same status can mean two different things.

“pending” covered both never-started and merged-verified-awaiting-review. When a board row looks wrong, read the request’s frontmatter fields and the selector’s typed exclusion reason before concluding anything from the status column.

L26 · Machine load

Passing assertions can still miss a time budget.

An optional experiment left six CPU loops running for about 4.5 hours. A background worker must own its deadline even if its parent is killed. Mark loaded measurements as loaded; they cannot establish normal gate speed.

L27 · Actual savings

Fewer processes can save time; moving tests only changes attribution.

The completed test repair removed repeated setup and saved four seconds in the comparable module run, without splitting files. A per-package saving and a whole-module saving differ under contention; report the workload beside each number.

L28 · Worktree evidence

Read the branch reference before judging a leftover.

A directory name omitted the branch’s codex/ prefix, so two fully merged worktrees appeared unresolved. Clean state, actual branch ancestry and a settled request proved removal safe; age and the warning label alone did not.

L29 · Drain completion

Finish held work as well as building new work.

More claimed requests can include reviewed work waiting for heavy checks. Measure completed requests and retries, and give the run a finite endpoint; the number of busy or claimed lanes is not throughput.

L30 · A zero residual needs a complete interval.

“0s unattributed” describes gaps inside the recorded window. If only building was recorded, planning, review and closure can be entirely absent. Require full-lifecycle endpoints before reading that number as complete accounting.

Why: a green result lowers readiness

The dependency rule (DependencySourceReady, schema_normalization.go line 240) counts a dependency as landed when it is terminal, or when it is pending-heavy-testing with a commit. A green heavy answer flips the request back to plain pending, which the rule does not accept.

So the request is more available to dependents while it waits for slow tests than after it has passed them. Three independent reviews that could run side by side are forced into a chain, and the board shows the same word for “never started” and “merged, verified, awaiting review”.

Proposal P1 (recommended): the heavy hold is a phase of a claimed request, not a status. Delete pending-heavy-testing.

The work action already states the rule at line 93: intermediate phases are tracked by which sections exist in the request file, not by status changes. The heavy hold is such a phase, and it already has its marker: a ## Heavy Verification Plan section plus a commit: on main. Giving it a status word broke that rule; the return trip through pending is the damage that followed.

The change, in three parts. First, move Step 7 (review) and Step 7.5 (lessons) ahead of the hold, so a request is held only after fast tests, qualification and review have all passed. Second, the held request stays claimed in do-work/working/; the session that claimed it still owns it. Third, at queue exhaustion the same session runs the lanes and then, in the same turn, runs Step 8 and Step 9 for each green request (terminal judgment, release judgment with the version assigned at that moment, one finalization transaction) or enters ordinary remediation for each red one. No answer transaction, no re-queue, no re-claim.

The status flow becomes pending → claimed → completed with no detour. What this deletes: the status value itself and its case in eight readers (checkpoint counts, the advance skip list, clarify Step 2.5, cleanup, roadmap, the restart handoff, the work action, and the heavy-testing answer mode with its five refusal codes); the resume_phase projection and matchingHeavyReviewPhase in the selector; one re-claim commit and one selection pass per request; the dependency gap above; and the board ambiguity. The heavy_verified_* fields stay as durable evidence on the archived record.

Two conditions make it safe. Dependents keep building on landed code: the readiness rule accepts claimed with a nonblank commit: in place of pending-heavy-testing with one. Same fact, truer name; the commit field is written at integration, so a claimed request that has one is on main. Recovery reads the phase from the file, not the clock: if the session dies during the hold, the next session’s recover step finds a claimed request with a heavy plan and no live writer. It must route that request to its own exhaustion drain, not treat it as interrupted build work. The section already exists; this is a condition on recover, not new state.

Cost: review runs before the slow lanes, so a lane that goes red after a passed review costs a fresh review after remediation, which is today’s cost too. The checkpoint will count held requests as in progress while only one builder is active; that is accurate and the plan section explains it. Land it after REQ-504 to REQ-506 have closed, so no compatibility path is needed.

P2 (patch only): widen the readiness rule

One extra condition in DependencySourceReady: pending with heavy_verified_revision equal to commit: counts as landed. Two focused tests, one clause in work.md line 97, one release. It removes the serial chain but keeps the status, the round trip and the board ambiguity. Skip it if P1 is accepted; P1 deletes the code P2 would add.

07 · Why the queue refills

Why the queue refills

In the 30 days to 22:00 today the pipeline created 395 REQs and archived 391. It shipped 439 releases and 1,863 commits in the same window. That is not slow. The queue has stayed near 40 the whole time because intake tracks output, and it does so because the pipeline is its own largest customer: 130 of the 391 archived REQs were minted by a review handback, 182 were addenda to a prior REQ, and only 21 carried impact-critical. The 2026-08-20 report measured the same equilibrium at 145 of 298 REQs ever written; the share has not moved.

The mechanism is the contract suite. _dev/tests/contract-regressions.sh is 8,479 lines of assertions that pin specific sentences in the action Markdown: about 200 grep predicates and 25 embedded Python programs, each added when a REQ fixed a behavior that existed only as a sentence. When a later REQ edits prose that disagrees with a pinned sentence, the gate goes red, the review names the discrepancy, and the pipeline mints a REQ to reconcile the two. That REQ edits more prose, which meets more pins. The pins are not where the gate's seconds go; the 00:10 analysis measured them at about 9 s against 140 s for the 14 sub-suites that build throwaway git repositories. They are where the REQs come from.

Two brakes exist and neither is engaged. REQ-531 (review findings below impact-critical stay in the report, the maintainer captures by hand what is worth building) is the one that closes the tap: 126 of the 130 review-born REQs this month were below critical. It waited on REQ-548 (repairing the gate's broken pipe) until 21:46 and has been claimed since 21:47. The second is UR-100's line-count ratchet on the contract file: the ceiling was 8,417 lines on 09-02, REQ-519 that carried it was cancelled, and the file is 62 lines over with no ratchet in place. REQ-539 carries it now, behind REQ-538.

Every one of the 40 open REQs is do-work working on do-work. Seven batches: orchestrator simplification (8), the two-tier gate (5), non-blocking orchestration (4), the Go command platform (4), today's validate feedback (3), recovery never traps (2), close the tap (1). Nothing in the queue or the archive this month came from a project that uses the skill.

09 · Lessons learned today

Lessons learned today

What this day taught about making the queue move, written so a session that has none of this context can act on it. Each lesson names the evidence and the rule that follows from it. Added at 22:25; instrumentation lesson added at 00:53.

Gate and tests
#LessonEvidence
L1A tier is not a speedup until the heavy tests are excluded before they start. Skipping inside a test still pays its fixture setup. Exclude by test selection (run pattern or knob checked at the top of the test), then measure.REQ-537: fast 629 s, heavy 631 s. Codex profiling: the JavaScript probes "skipped" after doing most of their setup, so the fast tier still took 109 s.
L2A time budget is a program, not a sentence. The gate times every file, logs the durations with the number of concurrent gate processes, and fails the fast tier over 30 s. Prose limits are never enforced; suites grow back.UR-100's ceiling was 8,417 lines; the file was 8,479 with no ratchet. First budget run caught generate_test.go at 30.35 s; reusing its fixture brought it to 7.30 s.
L3One gate per machine. The same tier measured 301 s, 363 s and 641 s on the same day. Under load every timing is wrong, including the budget. Before starting a gate, look for another one running.At 22:15 two contract-regressions runs and one go test were executing at once, from two sessions.
L4Delete before you skip. A meta-test that re-executes the whole binary is replaced by a unit test of the guard it protected. A sentence pin whose comment names no incident REQ, or whose target is not a shipped file, is deleted, not moved to heavy.Codex diff: two RejectsZeroProbes meta-tests (41.8 s and 16.1 s) became one table-driven test of strictProbeGuardFailed.
L5The gate runner only helps if something starts it. It has existed since 0.266.9; nothing launched it, so every REQ paid two gate runs. Start it by hand until REQ-542 lands.Two runs at 629 s are about 21 of the 65-minute median REQ.
L6A change to the gate lands in place, never through the pipeline. The pipeline would run the gate two or three times to ship a change to the gate.UR-104's batch constraint; REQ-537 landed at 8d9d1bb that way.
Queue and coordination
#LessonEvidence
L7A batch order is not a dependency. Capture encodes "do A1 then A2" as a depends_on chain. Before accepting a chain, ask whether the dependent reads the other's output; if not, drop the link so builders can run in parallel.REQ-540 and REQ-542 waited on REQs whose files they never touch; dropping both raised ready work from 20 to 22.
L8A claim without a worktree is a stall, and unclaimed parallel work is a collision. Check git worktree list and do-work/working/ together. Only the maintainer releases another session's claim.REQ-538 claimed at 19:49 by a cloud session that went idle; a Codex worktree did the same cuts on its own branch.
L9Several sessions in one checkout must announce before touching shared files. Cross-session messages work; use them. Land with explicit paths, never git add -A.Four sessions touched this checkout tonight: the REQ-531 run, Codex, a report revision at 9d18e031, and this one. The other checkout asked by message before claiming REQ-267.
L10Two records of one duration disagree for known reasons; do not "fix" one to match the other. Log rows are written once and sometimes hand-rounded; frontmatter is re-stamped by crash recovery and measures only the last re-run. Say which is which.REQ-460 log 421 min vs frontmatter 20; 17 of 203 log rows end in :00Z. The two rows were later rewritten to the frontmatter values.
L11Two checkouts on one port kill each other's board. just run-kanban stops any queue-kanban on 8090 by design. Give each checkout its own port.The n1-weekly-signal-diff checkout took 8090 at 21:16 and killed this one's server; the browser looked "not opened".
L12Draining faster does not empty a queue that refills itself. Review-born REQs below critical are the intake; REQ-531 closes that tap and belongs beside the gate fix, not after it.395 created, 391 archived in 30 days; 126 review-born below critical.
L13Amend queued REQs by addendum, verify by parsing. Append a dated Addendum section with the user's words contained (blockquote plus a fence longer than any backtick run), record a "Resolved conflict" line when the original is superseded, and prove the edit with queue-kanban summary.Commit d00da469; the board parsed all four files, zero malformed.
L14When you delete gate work, keep its assertions. A test file can be dead as a gate step and still be the only home of a zero-hit guard. Before deleting one, grep it for the assertions it carries and re-home them in a fast file, or the guard is gone with the seconds.0.266.9 (5e0e166c) deleted _dev/tests/shipped-shell-thinness.sh as "no gate path executes"; the 2026-09-03 maintainability audit found the "every shipped .sh reaches do-work-cli" assertion now has no home. REQ-551 re-homes it in _dev/tests/audit-lockins.sh.
L15Measure one REQ phase by phase before optimizing the gate again. In the one run decomposed from persisted timestamps, the gate detour was 11% of the hour; the builder's own work was 34%, planning before the first edit 21%, integration 14%. The next second saved comes from retrying a transient red once, splitting the contract file, and one policy home per rule, not from the gate.REQ-531 run, 21:19:03 to 22:46:42 EEST, 87 min 39 s; phase table under "Where a REQ's hour goes".
L16Declare a target and write it under one condition, never two. The cancel plan computed the post-cancel checkpoint bytes for every working/ departure, declared the path only when the bytes changed, and wrote them regardless, so a foreign-labelled or absent entry made the transaction refuse its own no-op. A dry run cannot catch this: the guard lives in the mutation recorder.REQ-468 and REQ-538 rolled back four times with "path do-work/CHECKPOINT.md is outside the declared transaction targets"; fixed in place as 0.272.1 (b7c35e99) with a red-then-green lock-in.
L17Two shell traps from tonight. The CLI launcher rebuilds only when a source file is strictly newer than the binary, so an edit in the same second as the last build runs stale code; delete the ignored binary to force it. And in zsh a variable named path is PATH, so a script that assigns it loses every command.The fixed CLI kept refusing until the binary at 23:45:14 was removed (state_plan.go also 23:45:14); one cancel batch printed "command not found: head".
L18Instrumentation must be cheaper than the work it measures. Record only major serial stages and material commands. Keep raw events Git-private, create no instrumentation-only commits or agent turns, and fold one compact timing summary into finalization.REQ-561 took 20 min 47 s before builder dispatch, produced 5,316 words of raw planning and exploration, and made eight pre-builder commits. REQ-562 was narrowed accordingly in ffbc3628; nested spans, overlap, parallelism and critical-path analysis are out of scope.
