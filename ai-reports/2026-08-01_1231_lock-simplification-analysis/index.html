do-work · concurrency machinery · simplification analysis

Delete the lock. Verify the commit instead.

About 6,500 words of concurrency machinery — a sixth of the core pipeline — can be removed and replaced by roughly 600. The lock's real job was never owning REQs; it was owning the git index, and it only needs to be held across the stage-and-commit window rather than the whole REQ lifecycle.

Analysis only — nothing is implemented. Every word count below was measured from this repo with the commands in Verify It Yourself; the design argument is the author's, not a benchmark.

The defect this exposes

Two resources can be owned: the ticket (a REQ file) and the repo files that ticket writes. The lock tracks the first across every session. The write_set gate tracks the second within one session only — every disjointness check in the pipeline compares against "every other in-flight REQ this batch," which means this session's own batch. A coexisting session's requests are never read.

The two mechanisms were built for different problems and never joined. The lock exists because of the 2026-07-01 incident, which was a ticket-level collision. The write_set gate exists so one orchestrator could run several builders at once. Neither is defective; the gap is in the space between them.

The replacement

Prevention asks an unanswerable question — which files will I touch? Escalation asks an observable one — did something break, and did fixing it break again? Each rung has a defined next action, which is what the current machinery lacks: it detects, then has nothing to do about it.

escalation ladder

  1. A commit carried someone else's work — leave it. Attribution impurity is a property of the log, not the tree. Git history can't be rewritten on a shared branch anyway, so a check whose only outputs are "fine" and "too bad" is decoration.
  2. It broke the feature — fix it. Ordinary work. No new concept, no new state.
  3. Fixes keep breaking it — escalate to pending-answers. Repeated failure means two REQs with genuinely conflicting intent. The REQ stays in do-work/queue/, the default scan walks past it, a human arbitrates. The status already exists with exactly these semantics.

One gap, and it closes with the same check. The ladder is driven by breakage, but this repo's deliverable is markdown instructions, which have no runtime behavior. A clobbered paragraph passes all 1,521 lines of grep-based contract assertions and never reaches rung 2. The fix is the presence check in the diagram: not "did my commit contain only my change" (unanswerable, no remedy) but "is my change present in the tree after commit" — answerable from git, and its failure is actionable.

Why four REQs is the tell

REQ-018 built the lock guard. Then REQ-035 (multi-claim representation), REQ-044 (claim coherence), and REQ-047 (mutex pre-write ownership check) each fixed a correctness hole in it after the fact.

Three post-hoc corrections on one mechanism is the signature of accidental complexity. The write_set gate shows the same pattern: REQ-032 built it, REQ-036 and REQ-045 patched it.

Open questions

Two residuals, both small, both undecided.

Where does the attempt counter live?

Rung 3 needs a count that survives the REQ's lifecycle. There is no such field in the frontmatter schema today — the only attempt-related prose in the repo sits inside the mutex block this proposal deletes. It needs a named field and a defined threshold, or the agent either loops forever or escalates on the first failure.

How aggressive should the index retry be?

Concurrent git commit in one folder doesn't queue — it fails on .git/index.lock. A bounded retry is the entire residual of the deleted machinery, but the backoff and give-up behavior aren't specified, and giving up mid-REQ needs its own disposition.
