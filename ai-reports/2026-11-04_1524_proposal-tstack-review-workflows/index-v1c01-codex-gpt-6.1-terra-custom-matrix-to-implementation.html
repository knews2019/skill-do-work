Implement O2 in slices changed

These are proposed steps, not completed work. Start with the existing review-work and Review section before introducing separate storage or scheduling.

  1. Define the opt-in contract

    Specify when the mode applies. Review one request’s requirements, change and tests, while inspecting related callers or documentation where needed to assess effects. Record the base and revision reviewed. Keep ordinary run behavior unchanged; decide how an unresolved request is handed back without stopping unrelated queue work.

  2. Record findings and decisions

    Extend the existing Review section with stable finding IDs, round records, actual reviewer/model identities and the reviewed revision. Verify each finding, record accepted fixes or evidence-based pushback, and preserve unresolved dissent.

  3. Set limits for one reviewer

    The report proposes three rounds by default, with a deliberate extension for consequential open issues; the extension limit is not yet chosen. Stop when only nits remain. A persistent dispute, missing required reviewer, timeout in a required review or exhausted budget is unresolved, and approval must cover the current behavior diff.

  4. Add council as a separate choice

    After the one-reviewer slice works, allow three distinct providers through available harness capabilities. Give reviewers the same frozen scope and evidence before sharing other reviews, preserve dissent and budget the whole round. These are proposed additions, not claims about the upstream council.

  5. Verify lifecycle edges

    Check that changed code needs review of the current diff, that missing required replies and disputes cannot become approval, and that ordinary runs and unrelated queue work retain their existing behavior. Keep reviewer scores as information, not an averaged permission to complete.

Jester — optional advisory reviewer

When enabled, the jester defaults to the latest available Gemini resolved through the harness. Gemini 4 Argon is the user’s example, not a fixed model ID or a claim about current availability. Record the actual model used.

Give it the same serious brief and evidence as the regular reviewers. The parent knows its advisory role; do not ask it to act funny. Its numerical score cannot approve or block completion and is excluded from council grades in a PR description.

Check useful findings against the version reviewed. A verified defect matters because of the evidence, even though its score does not count. An unavailable, failed or slow jester does not delay the main loop; report that advisory feedback was missing. Required council reviewers still follow the ordinary approval rules.

How would the review be evaluated?

The proposed AI-Evaluation-Loop could check the request’s acceptance criteria, the test evidence and the findings that remain. A reviewer would recommend approval only when the required evidence is present and no consequential supported finding remains; a budget limit by itself would not be approval.

Today’s review-work also scores requirements, code quality, test adequacy and scope, and records an acceptance result. The proposed AI-Evaluation-Loop has not selected a new grading scheme or changed those existing rules; averaging different reviewers’ scores into approval is not recommended.

Why the handoff is a design decision: today’s run can proceed to archive when the review agent fails. A strict opt-in mode needs a different, explicit path for that case; the report recommends holding only the opted-in request.

What the two upstream workflows say

Sol-loop: one reviewer, fixed scope and base, stable finding IDs, and a default of three rounds. The original report says it can extend to five in named high-risk cases while supported issues remain, or when requested. It stops on nits, a dispute persisting after two replies, or budget exhaustion; approval covers the current behavior diff.

Council: three providers review in parallel after known issues are fixed and checks run. Findings are collected, accepted fixes made, and fresh reviews requested until satisfaction. Scores are recorded without a numerical passing threshold; the report found no explicit round or deadlock limit.

Reviewer independence before sharing other findings, a council cap and a whole-round budget are this proposal’s adaptations. The source description is in the original Council / Sol section.
