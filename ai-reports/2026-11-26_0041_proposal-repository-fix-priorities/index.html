Match known board executable names before stopping a listener.

Restarting the board with just run-kanban can stop an unrelated program on the same port. In a fixture, the real launcher sent its stop signal to queue-kanban-helper. One shell pattern decides which process it may stop.

How much of the restart should change?

O1 · Recommended

Match known names exactly

Under 15 minutes of implementation and fixture work. Protects similarly named listeners. Accept the current queue-kanban and legacy go-bin-queue-kanban. Other custom names need a manual stop.

O2 · Broader fix

Also build before stopping

About 15–60 minutes. A build failure leaves the running board available. Requires a second fixture for ordering and a fresh listener check before signaling.

O3 · Defer

Use a free port

No code change. A caller who picks an unused port avoids replacement for that run. Every default-port caller still depends on the substring match.

The maintainer and installed recipes call the same shipped script. See justfile:5, skills/do-work-board/justfile.template:5 and skills/do-work-board/tools/run-kanban.sh:13–38.

Land O1 first. It changes one decision immediately before a process signal and has a regression case that can run without a server. F2 makes the next restart safer even when the launcher identifies the board correctly.

Evidence and acceptance checks

F1 · A name containing “queue-kanban” is enough to receive a signal

The shell strips the executable’s directory, accepts *queue-kanban*, and calls kill. The existing foreign-process fixture uses python3, so it cannot distinguish an exact match from this wildcard. In the audit fixture, the launcher recorded a stop for queue-kanban-helper.

Smallest fix. Match the two documented executable basenames exactly. Commit 0a3d12e7 explains why the older go-bin-queue-kanban from another repository must still work. Add that success case and the lookalike refusal to the existing fixture. Both known names should restart. Both foreign names must exit 1 with an empty signal log.

F2 · A failed build takes a healthy board offline

The launcher stops the recognized listener at line 23 and builds the replacement at line 38. With the exact board name and a build stub returning 9, the audit recorded one signal, exit 9 and no replacement. The existing build-failure check covers static export.

Two concerns deserve separate investigation

Release retries can replace assets under an existing version

A manual dispatch builds the selected checkout. If its version already has a release, the workflow uploads with --clobber. The launcher reuses an executable cached by version and platform. If the uploaded bytes change, two machines can run different binaries for the same version. This is a possible outcome from the source. No published release was inspected.

Smallest safeguard. Make existing assets immutable. For retries, accept identical published digests, fail on differing bytes, and allow missing assets to be repaired only from the matching tagged commit. Verify with local fixtures for identical, differing, and missing assets before exercising publication.

.github/workflows/release-binaries.yml:11,29–46 · skills/do-work/tools/do-work-cli.sh:116–126 · _dev/tests/do-work-cli-launcher-behavior.sh:185–193.

Measure the cost of second-opinion verification on large checkouts

The recent outside-change check hashes every regular file outside the bundle in the temporary checkout. An ordinary successful subprocess run scans three times, before the probe, after the probe, and after generation. Automatic AGY model selection adds a fourth pass. The work grows with checkout bytes as well as file count. The tests justify the checks because committed and ignored changes must both be detected.

Smallest next step. Benchmark the existing snapshot function with fixed fixtures for many small files and fewer large files. Report bytes, file count, time and allocations. Use those measurements before changing the guard. Keep the committed, staged, ignored-file and deletion cases green.
