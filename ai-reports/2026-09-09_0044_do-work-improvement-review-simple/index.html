What each change means

R2 · FIX

Resolve conflicting guidance

The backlog lists 19 places where written guidance may be wrong or outdated. Check each against the code and intended behavior. Fix what is still wrong; close what is already resolved.

Done when: all 19 entries have an explained outcome, with unresolved intent questions made clear.

Example and limits

If instructions describe an old command format, correct the text. If the code and intended behavior disagree, record the conflict. Do not assume the code is always right.

These are 19 reported discrepancies, not 19 newly confirmed bugs.

R1 · SHORTEN

Explain each rule once

Four core instruction files total 42,737 words. Remove proven repetition and point to the place that owns each rule. Keep the guidance an agent needs to act and recover from errors.

Done when: the text is shorter and still supports simple, complex, and interrupted work.

Example and limits

If two files explain the same command check, keep one authoritative explanation and a useful reference. Preserve command inputs, result meanings, required evidence, judgment, and recovery steps.

Fix conflicting wording in R2 first. There is no justified percentage-cut target or need for a full rewrite.

R3 · ARCHIVE

Keep recent history easy to find

The changelog has 89,526 words, plus an identical installed copy. Keep the newest 50 release entries in both. Move older entries into linked repository archives.

Done when: all history survives, both live copies match, and version/history tools still work.

Example and limits

Recent releases stay in the main changelog. Older releases remain in dated archives that are excluded from the installed package. Older history then requires repository access.

Fifty is a proposed default. Check whether any supported tool needs older entries. This changes packaging, not how often releases happen.

What the evidence actually tells us

The files are large.

The reported word counts describe whole files. They do not show how much an agent reads during a task. Removing duplicate text is useful without promising a speed improvement.

The timing data does not explain the cause.

Almost every recorded test-duration sample overlapped another test-runner process. There is too little idle data to show how much the overlap slowed tests down.

Sources, scope, and omitted detail

This is a plain-language rewrite of the rev-v2 report, not a new repository audit. Counts and findings are carried forward from its snapshot of do-work 0.305.35 at commit ff82f62d. No new performance experiment or runtime read measurement was run for this rewrite.

  • Audit evidence: 21,755 timing samples; only three recorded no other gate process. The dataset also spans different code revisions.
  • Measuring savings: collect suitable runtime evidence before making a token-cost or speed claim. It is optional for removing proven duplication.
  • Other ideas: command deletion, automatic updates across live tasks, and separate recipe templates remain outside this batch.
  • Article and guide context: useful assignment examples, without a demonstrated need for another workflow layer.
  • Revision history: the full explanation of what changed from the first review.
