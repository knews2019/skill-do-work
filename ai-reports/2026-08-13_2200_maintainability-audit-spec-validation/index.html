3 · Design seams — proposals

seam

S1 · Rule 8 has no first-run branch, and "Read-only in the repo" mislabels itself

The audits directory does not exist yet, so "read the most recent report first" cannot be satisfied on run one; the repeat-run path is the special case that got specified. And the rule's headline contradicts its own carve-out (writes inside the report directory). Proposal: "First run: no baseline — say so in the header, skip deltas, create the directory. Writes only under do-work/audits/; nothing else in the tree."

seam

S2 · "Checkpoint" and "operator" collide with pipeline vocabulary

do-work/CHECKPOINT.md is an existing crash-recovery artifact — that capitalized noun is taken in a do-work repo. "Operator" is not glossary vocabulary. Proposal: call the gate the calibration gate; the person is the user.

seam

S3 · Instances pinned to path:line collide with a recorded lesson

The 2026-08-05 census recorded that a path:line evidence table over an active repo "started lying within hours," and the 2026-08-11 audit's lesson is "paths, not line numbers, are the durable coordinates." The spec partially pre-empts this (SHA-anchored header, instances "independently greppable"). Proposal: make the grep pattern the primary coordinate — path — greppable pattern, line number optional annotation valid only at the audited SHA.

seam

S4 · Missing action-file apparatus

To ship it needs: the description blockquote, trigger-style description, When to Use (positioned against code-review / quick-wins / forensics), an Input contract, crew loads (clear-questions.md before the calibration gate, anti-slop.md before the report, prompt-injection.md before reading archived Lessons prose — the forensics precedent), SKILL.md routing + help entry, and the router word-budget lock-in limit honored (2,650). At 2,350 words before any of that, the established shape is action + reference companion (seven such pairs exist; nearest analog: deep-explore).

seam

S5 · "Loop usage (for the operator, not the agent)" has no home in an action file

A floor agent reads everything as instructions; a section addressed to a different reader is a misfire. Proposal: loop steps 2–4 become the report's output footer (the validate-feedback handoff pattern); the full loop narrative goes to a docs/ guide, the established home.

seam

S6 · The three-question budget vs the approval flow

The calibration gate needs approvals on installs, bands, and scope plus up to three domain questions, and never says whether approvals count against the budget. Proposal: one bundled approval (installs + bands + scope as a single proposal the user edits) plus at most three domain questions.

seam

S7 · Sweep markers won't survive capture

The audit emits root-cause classes shaped like sweep REQs, but sweep: true/sweep_key are review-flow-only markers capture never writes. Proposal (YAGNI): no schema change — sweep_key travels in the captured REQ body as provenance; cross-run dedupe is what waivers and the delta table are for.

4 · Decisions

Decided: reports live in do-work/audits/

Your call. Consequences folded into the plan: the audit's write surface becomes do-work/audits/ (reports + waivers.md); it sits inside the already export-ignored do-work record in this repo, so nothing ships to consumers; capture's first-run bootstrap is untouched (the audit creates the directory itself); the EXCLUDE list must exclude it from its own metrics.

Decided: prime coverage is a judgment finding, not a machine-enforced lock-in limit

Missing-prime findings stay a judged Phase-2 dimension with REQ-touch counts as impact evidence. No structured scope field is added to primes. This uses the spec's own escape hatch (a limit "if none is possible, one sentence why") and avoids new prime-format surface.

Decided at capture (default adopted, revisitable): lock-in limit enforcement — what a lock-in limit is (the draft spec's "ratchet")

A band says what good looks like (FLAG > 600 lines) — aspirational, so a repo that's already worse fails day one and the check gets ignored. A lock-in limit is pinned at today's worst observed value instead: worst folder today is 46 files → the check says "no folder over 46." It passes immediately, blocks any regression, and when a fix brings the max to 30, the pin moves to 30 — improvement gets locked in one notch at a time. The repo already does this, under the glossary name lock-in test: the 2,650-word router budget (contract-regressions.sh:1145 — a pinned ceiling raised only with a decisions/ note) and the zero-hit phrase sentinels of defensive-surface-audit.sh. Two days ago (13f22c9) a broad registry-style check of that kind was deliberately narrowed to incident-anchored sentinels — the repo's taste is minimal, earned enforcement.

Recommended: the report only proposes each lock-in limit (with its red case); accepted ones flow through triage → capture and land as lock-in tests in _dev/tests/ (or the user repo's CI). Alternatives: the audit self-checks stored limit values each run (no test-suite coupling, but enforcement only when the audit runs), or drop lock-in limits from v1 and rely on the delta table.

Decided at capture (default adopted, revisitable): packaging and the audit codebase trigger

Adopted: new action skills/do-work-toolbox/actions/maintainability-audit.md + reference companion + docs guide; the trigger phrase audit codebase (currently on code-review, SKILL.md:17) moves to it as the better semantic match, code-review keeps code-review / review codebase. Alternatives: leave the trigger alone; or extend code-review with a metrics mode instead of a new action (one fewer file, much heavier).
