Problem and change

The badge guessed a pause from one number, the total span. UR-135 (the maintainer's design brief) showed a 4h21m REQ that was worked without a break. The evidence already existed in per-phase stamps and in commits that touch the REQ file.

File modification time cannot replace git here. A commit changes .git/, not do-work/, and builder commits land in other worktrees. This is the REQ-284 lesson (never cache the verify probes, because their inputs change while every file mtime stays the same). The code comment at activity_correlation.go:19-22 repeats it.

How it works

Hand-authored diagram of the current code at base 2eb14357. Solid outline: deterministic git structure. Dashed outline: scaffold around agent behaviour. Line numbers are in activity_correlation.go unless named.

Each served board response reads the worktree-agent state once and shares it with the verify probes. It then runs one windowed git log with hash, committer date, parents, subject and touched paths.

A commit is credited to a REQ when it touches that REQ's file or run artifact, or when its subject carries [REQ-NNN]. If a two-parent merge is credited, every commit between its first and second parent is credited too. That walk uses the logged parent hashes in memory and never runs merge-base or rev-list.

The tip date of each builder branch that owns its tip is added as one more commit event. The union with the stamps gives the newest event for a claimed card and the largest gap for the drawer.

Value delivered

An in-progress card now shows a stuck signal that grows when nobody touches the REQ. A finished REQ no longer carries a pause label that the evidence contradicts. Both statements come from observed events, not from a threshold.

Lessons and open questions

REQ-632 recorded that the do-work pathspec drops every merge and the builder commits behind it. It also recorded that plain git log --name-only lists no files for merge commits, so a merge is credited only by its subject prefix and its second-parent range.

Six findings from REQ-632 stayed report-only. Two touch this question: one abandoned claim widens the git window, and a finished REQ without completed_at gets a window that runs to now. REQ-632 recorded no open questions.

The decision this report exists to support

Should the [REQ-NNN] commit prefix become deterministic, so the code around missing prefixes can go? This report does not recommend either option.

Option 1: stamp the prefix, then delete

The do-work CLI or a commit hook stamps [REQ-NNN] on every builder commit. The id can come from the worktree-agent-REQ-NNN-* branch name. Then delete the merge-range expansion, the in-memory ancestry walk and the REQ-646 guard. Commits are credited by prefix plus path only. The owned-tip read stays.

Lines deleted from activity_correlation.go: 70, 96, 111-113, 116-120, 139-164 and 174-191. That is 54 lines. Deleted from the test file: 141-232, which is 92 lines.

New stamp code and its testsnot written; size unknown

A builder's merge of main would carry the stamp itself, and main's commits keep their own ids, so the REQ-646 failure could not happen. A commit made outside the stamp gets credit only if it touches the REQ file. Examples are commits made before the stamp exists, by a person, or by another tool. The counts come from pruning a scratch copy of both files with those exact ranges.

Option 2: keep the current code

Un-prefixed builder commits keep their credit through the merge they arrive in, in any repository, however the commits were made.
