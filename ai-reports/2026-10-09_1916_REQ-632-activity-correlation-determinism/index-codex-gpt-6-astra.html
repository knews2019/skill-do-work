What counts as activity
on a request card?

Recorded timestamps and related commits give the board two useful readings: when activity was last seen, and the largest gap between events.

Original report: 9 October 2026, base 2eb14357. Repository reviewed here: 406ff3c4fda1d083dc144c01929b453360583ae5. This is a source review; project tests and benchmarks were not rerun.

The central decision has already been made. Release 0.305.88 removed merge-range attribution; 0.305.89 clarified the prefix convention. There is no automatic prefix-stamping mechanism. [6] [7]

01 / TL;DR

An observation, not a pause verdict

The queue-kanban board links each work request (a REQ) to its lifecycle timestamps and related Git commits, then shows last activity on claimed cards and the largest event gap in the detail drawer. It replaces a badge that called work “paused” merely because its total span exceeded four hours. The feature is implemented, but its former merge-history fallback has been removed: current attribution uses request paths, bracketed request tokens and eligible live branch tips. [1] [4] [6]

02 / The big picture

Three inputs become one event stream

The collector combines the request’s timestamps with matching commits and live branch-tip dates. It computes the readings in Go and sends them to the browser in a requestActivity map keyed by request ID. [1]

04 / How it works

From a refresh to a reading

  1. Select claimed and recently done requests.The history window starts at the configured recent-window boundary (seven days by default), or an earlier claim date among those tracked requests. Older archived requests are excluded. [1] [12]
  2. Read shared branch state and fresh history.Verification checks and activity share the branch read. The activity log runs on every board-data response, outside the file-modification-time cache, because commits can change without a request file changing on disk. [2] [3]
  3. Match commits, then add stamps and branch tips.A subject such as [REQ-701] [REQ-702] shared fix credits both requests; a bare REQ-703 mention does not. A matching request path also works with no token. [5]
  4. Clip to the work window and assign phases.Events before a valid claim are excluded. For a finished request with a valid completion stamp, the endpoint is the later of completion and release; a commit inherits the latest preceding phase. [1]
  5. Calculate and display.The newest event drives the claimed card. Consecutive event pairs determine the largest gap; the elapsed time after the newest event is not part of that gap. [1] [4]

The stopwatch is not a live feed. The browser updates elapsed text each second using the loaded timestamp. A fresh board-data response is needed to discover later events; the activity ticker itself does not reread Git. [3] [4]

A commit can split a long stamp gap

This example comes directly from TestRequestActivityLargestGapUnitesCommitsWithStamps. Its completed request has stamps at minutes 0, 10, 130, 180 and 200; a matching commit at minute 70 splits the 120-minute dispatch-to-handback gap into two 60-minute gaps. [5]

Window and failure details

The collector allows timestamps up to two minutes beyond the supplied current time. Missing or invalid claim stamps remove the lower bound; a finished request without a valid raw completed_at stamp keeps the current-time endpoint, even if another mechanism supplied its completion date. [1] [12]

If the history read fails, timestamps and any available owned-tip dates still contribute. If the integration reference cannot be resolved, owned tips are omitted; this can leave less evidence without a dedicated activity-error field in the payload. [1] [2]

05 / Decisions and trade-offs

Less inference, more reliance on the prefix convention

The original report offered two choices: automatically stamp every commit, then remove the fallback; or keep the fallback. The later implementation chose a third: remove it and document the prefix rule, without adding a stamping hook or wrapper. [6] [7]

What became simpler

The collector no longer reads parent hashes, walks merge ancestry or needs the REQ-646 guard against attributing unrelated main-branch commits through a nested merge.

Release 0.305.88 [6]

What can disappear from the evidence

After merging, a builder commit with neither a bracketed request token nor a matching request path contributes no timestamp of its own. A prefixed merge can still count as its own event; it does not recover the builder’s earlier events.

Current rule [1] · Written convention [7]

“Deterministic” needs a boundary. The code applies exact rules to the evidence it receives. Whether a person or agent records the correct request token is still a convention, so exact matching does not guarantee complete evidence. [1] [7]

Read cost: fixed shared calls, variable total work

The original canned-runner measurement recorded five calls for 0, 1 and 4 builder branches: worktree list, branch list, integration-reference lookup, owned-tip listing and the activity log. Activity adds the last two; a detached repository root needs another reference lookup. Recorded measurement · [2]

That is not a universal total for every refresh. Verification also invokes Git directly for leftover-branch checks, and the activity log is skipped when there are no tracked requests; a longer history window also means more data to read. [1] [2]

Known risks

  • An old claim among tracked requests widens every history read.
  • A missing completion stamp can admit later archive-touching commits into a finished request’s gap.
  • Missing tokens and failed Git reads can omit evidence.

Collector and windows [1] · Recorded review findings [9]

Do not confuse the drawer with duration calibration

The Durations page’s Panel B filters samples using gaps between lifecycle stamps only, with a two-hour limit compared in whole minutes rounded down. The drawer also includes commits, so it can show a smaller gap for the same request; its displayed gap has no threshold. [10]

Open questions

  • Current runtime health and cost: do the tests pass at the reviewed revision, and how fast are responses on today’s data? No project workflows were run.
  • Coverage outside this repository: how often do current consumer repositories omit or mislabel the token? The bundled counts describe this repository on 9 October; the consumer example in UR-135 is reported evidence, not independently available history. [8]
  • Historical equivalence: did removing expansion preserve every per-request assignment in the reported seven-day sample? The bundled coverage summary does not compare request IDs on each assignment.

08 / Glossary

Terms used here

REQ / UR
A work request / the user request that groups it. [8] [9]
Lifecycle stamp
A recorded date for a transition such as claim, dispatch or completion. [12]
Phase
A label derived from lifecycle timestamps, such as dispatch or review; in-flight requests remain claimed. [1] [9]
Correlation / attribution
The rule that assigns a recorded commit to a request. [1]
Branch tip / owned tip
The branch’s latest commit; eligible here when it is not reachable from the integration reference. [2]
Worktree
A separate working checkout used for a builder’s branch. [7]
Merge expansion
The removed rule that assigned commits brought in through a matched merge’s second-parent history to that merge’s request. [13]
mtime cache
A cache refreshed by file modification times; activity is read outside it. [3]
