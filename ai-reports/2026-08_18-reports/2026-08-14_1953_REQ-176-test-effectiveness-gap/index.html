Layer 2 · the visual model

Two small tests. Very different guarantees.

“Small” describes the test’s surface area, not the weakness of its claim. A compact contract test can govern a large implementation when it watches the behavior callers actually depend on.

Behavioral contract

Protects behavior
  1. Enter through the real seamPublic API, route handler, CLI entry point, or another production caller.
  2. Use production-faithful inputFields, nesting, and enum values match the schema the application receives.
  3. Assert an observable promiseOutput, side effect, error condition, or state transition—not internal wiring.
  4. Change the inside freelyA behavior-preserving refactor stays green; wrong behavior turns red.
RESULTA small test constrains the contract while leaving the implementation room to grow or simplify.

Mock-heavy shell

Can prove wiring only
  1. Replace every collaboratorThe test builds a world of scripted responses that production never inhabits.
  2. Call the isolated lineThe subject returns the value the mock was told to return.
  3. Assert the mock was calledInternal interactions become the test’s main evidence.
  4. Break the user outcomeThe suite may remain green because it never observed the public promise.
RISKThe test can certify that a line and its wiring exist without proving that useful behavior survives.

Mocks are not the defect. They are legitimate at slow, unsafe, or external boundaries. The defect is calling a test “protective” when no observable contract or meaningful failure replay supports that claim.

Why a green suite and line coverage are weak evidenceEXPLANATION · BEHAVIORAL LOGIC

Line coverage answers whether code executed. A green suite answers whether its existing assertions passed. Neither answer tells you whether the assertions would detect the wrong outcome.

A stronger replay changes meaningful behavior: reverse a permission decision, remove a required side effect, return the wrong value, or violate an error contract. If the test remains green, the behavior was not protected—even if every line ran.

The useful question is not “did the test touch the implementation?” It is “what wrong behavior would make this test fail?”

How VERIFIED should differ from INFERRED herePROPOSED · GUIDANCE ONLY

The reference currently defines VERIFIED broadly as tool output or a grep hit, and INFERRED as judgment after reading code. For test effectiveness, a grep hit can verify that mocks exist, but not that the tests fail to protect behavior.

Proposed: call test ineffectiveness VERIFIED only when a concrete mutation or wrong-behavior replay stays green. Use INFERRED when static review shows interaction assertions, absent caller-seam coverage, simplified fixtures, or high mock pressure without a replay.

Why audit-metrics should stay out of thisVERIFIED BOUNDARY

The mechanical tool has four subcommands: inventory, folders, churn, and hotspots. Those are deterministic repository measurements. Cross-language “mock density” would be syntactic, framework-specific, and easy to game.

The right boundary is: scripts measure what is mechanically stable; the audit uses explicit evidence rules for judgment. Optional language-native mutation tools can corroborate a hotspot when approved at calibration, but their absence must not be disguised as a score.
