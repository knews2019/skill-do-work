Example 1 · Follow a request through the system

The example connects the user command to instructions, Go functions, and persistent files.

Illustrative input: “add a filter to the queue board.”

VERIFIED

These are two separate agent invocations. They are examples to explain the route; they were not executed for this report.

do-work capture-request: add a filter to the queue board

# Later, when ready to implement:
do-work run
  1. 1

    Route the request

    The agent reads the core SKILL.md. A capture invocation selects capture.md; run selects work.md.

    SKILL.md routing

  2. 2

    Preserve intent

    Capture creates a UR with original input and one or more REQs. It does not implement the request by itself.

    Capture boundary

  3. 3

    Claim work

    The run action invokes recover, then advance. Queue advance selects eligible work and commits a claim into working/.

    Work entry · Claim composition

  4. 4

    Build and review

    The agent chooses the triage route, implements the change, and writes evidence sections. advance runs mechanical gates and identifies phases that require agent judgment.

    Review and lessons phases

  5. 5

    Finish the record

    After required verification, a strict finalization manifest supplies terminal intent and exact paths. The engine applies archive/release changes, commits, records provenance, verifies, and cleans up.

    Finalization phases

Where the files go
do-work/user-requests/UR-<allocated>/input.md  ← original input
do-work/queue/REQ-<allocated>-<slug>.md       ← pending request
do-work/working/REQ-<allocated>-<slug>.md     ← claimed work
do-work/archive/UR-<allocated>/REQ-…md       ← terminal record

Numbers and filenames above are placeholders. Intermediate build phases are recorded in sections, not new folders.

Boundaries worth knowing

Writes, installation, and recovery have explicit owners.

VERIFIED
  • Capture and execution: capturing intent does not automatically build it.
  • Parallel work: fan-out is explicit; one releaser owns the shared release tail.
  • Heavy tests: reviewed requests can stay claimed with a landed commit while selected heavy lanes wait; queue exhaustion drains them before finalization.
  • Board writes: Testing fields/profiles, a version line, and reservation markers are the declared write surfaces.
  • Installation: four skill modules are installed together; managed writes are verified and recovered on failure.
  • Recovery: finalization journals are processed before working claims; takeover authority remains explicit.
  • Memory: transcript capture is opt-in; machine-local logs differ from curated committable memory.
