The decision

Simplify first. Add only a demonstrated missing check.

The alternate candidate list is directionally sound about size and maintenance cost. Its strongest proposals survive a narrower reading. Several supporting claims overreach: the full instruction files are not necessarily read on every run, release-heavy history does not establish causation, and a command missing from prose is not necessarily unused.

The manager pattern in Nate’s material is already central to do-work: keep intent, carry state, delegate bounded work, verify results, and continue through recoverable blockers. The useful new direction is how to judge the assignment: compare alternatives, pursue the unknown that changes the decision, and stop when the next step is supported.

Reduce orchestration instructions

Four central instruction files contain 42,737 words. Their size makes duplicated rules worth removing, but work-reference already prescribes selective reading. The claim that every REQ necessarily consumes roughly 57k instruction tokens is unsupported.

Recommended change. Subtract mechanics already enforced by canonical commands. Keep command inputs, typed-result interpretation, authored evidence, judgment, and recovery guidance. Correct overlapping drift before compressing it.

Pros

Less repeated context, fewer competing explanations, and fewer places for the next change to drift.

Cons

A typed result cannot explain every input precondition or recovery decision. Over-compression could make an uncommon failure harder to resolve.

Keep current

Preserves familiar detail and existing selective loading, but leaves duplicated guidance.

Smallest change · recommended

Edit the four core files around canonical owners; preserve behavior and useful judgment.

Broader change

Rewrite the whole harness or demand a 50% cut. Neither scope nor percentage is justified yet.

What could change this recommendation?

Can the reduced prose still guide a simple REQ, a complex REQ, and an interrupted run without guessing? Restore any removed contract whose absence changes a decision.

Evidence required before calling it done

Use existing focused contract checks and representative walkthroughs. Compare whole-file size separately from the instructions actually required on those paths; do not present word counts as measured token savings.

Evidence: Selective loading and command ownership · Core routing · Draft R1 capture prompt

Recommended change. Keep the newest 50 release entries in both live files. Preserve older entries in dated repository archives using the existing export-ignore rule. Keep archive links and the two live files byte-identical.

Pros

Cons

R4 / I6 · Replace the proposed remedyNext

Separate slow tests from failing tests

Ordinary maintainer verification can fail when passing tests accumulate 30 seconds in a source file. Heavy verification already disables that budget. Historical records show duration-only failures; they do not prove machine contention caused every overrun.

Recommended change. Make duration-only overruns explicit warnings in ordinary verification. Preserve an intentional strict performance mode, actual test failure, empty required-selection checks, execution timeouts, and duration logs.

Pros

A passing correctness run no longer creates a repair task solely because of timing. Strict checks can still expose regressions.

Cons

Performance regressions receive less automatic pressure. Strict runs need a clear entry point, and reused evidence must distinguish advisory from strict enforcement.

Keep current

Strong routine timing pressure, but elapsed-budget failures mix correctness and performance.

Smallest change · recommended

Reuse the existing budget control, report warnings, and preserve strict-mode evidence semantics.

Broader change

Delete the gate or replace elapsed time with CPU time. Both lose useful checks; CPU time misses I/O waits.

What could change this recommendation?

Would an advisory default let a real performance regression escape the checks that matter? Keep a deliberate strict check and verify that cached advisory passes cannot satisfy it.

Evidence required before calling it done

Exercise slow-pass, actual-failure, empty required-selection, strict-mode, and evidence-reuse cases. Existing execution timeouts must still fail. No weakened assertions.

Evidence: Default and heavy budget modes · Budget enforcement · Historical failure and subsequent repair · Draft R4 capture prompt

R5 / Earlier autonomy discussion · Narrow clarificationNext

Clarify authority for irreversible assumptions

The work loop says an assumption marked Irreversible never blocks completion. Broader authorization rules still apply, so this is an overbroad local instruction—not evidence that an unauthorized action occurred.

Recommended change. State that an unresolved assumption supplies no missing authority for an irreversible or destructive action. Finish reversible preparation, surface the specific missing decision, and continue unrelated runnable work. Preserve permission already given.

Pros

Removes an instruction conflict while retaining autonomous progress and standing authorization.

Cons

Vague wording could recreate needless approval requests for routine choices or already-authorized work.

Keep current

Relies on broader rules to override an unconditional local instruction.

Smallest change · recommended

Align the assumption rule and existing crew guidance around actual authority.

Broader change

Add a new approval subsystem or require approval for every plan. Neither is needed.

What could change this recommendation?

Does the user’s existing authorization already cover the action? If yes, continue. The clarification earns its place only where a consequential action depends on authority that is genuinely missing.

Evidence required before calling it done

Check authorized irreversible work, an unauthorized irreversible action, a reversible choice, and unrelated work continuing. No repeated permission requests.

Evidence: Unconditional assumption rule · Existing decision guidance · Draft R5 capture prompt

R6 / Earlier outcome discussion · Retain narrowlyLater

Review the combined user outcome

Explicit UR review currently reviews each successful REQ. Individual reviews already require end-to-end acceptance. What is less explicit is one scenario proving that several completed REQs jointly satisfy the original request.

Recommended change. For explicit review-work UR-NNN, add a combined-outcome check only when the outcome spans requests. Reuse original input and equivalent existing evidence; report delivered, partially delivered, or unverified as prose.

Pros

Can catch integration or usability gaps between individually correct components, including whether an artifact works in its receiving application.

Cons

May need an unavailable environment or extra review effort. No concrete missed integration incident was established in this audit, so priority is lower.

Keep current

Per-REQ acceptance may already cover the whole outcome. Reuse it when it does.

Smallest change · recommended

One smallest cross-request scenario in explicit UR review, only where needed.

Broader change

Make it a new finalization gate, add statuses, or reopen archives automatically. Premature.

What could change this recommendation?

Can a plausible integrated scenario fail while all individual REQs pass? If existing evidence already proves it cannot, reuse that evidence rather than add another test.

Evidence required before calling it done

Tie the verdict to the original need and observable results. Distinguish unavailable evidence from failure. An investigation can succeed by supporting no change; output volume is not the success criterion.

Evidence: UR reviews each successful request · Existing end-to-end acceptance · Draft R6 capture prompt

Ideas that need more evidence

Four proposals to defer

Deferral is a decision about the current evidence. These ideas should return only with a concrete problem that the narrower improvements leave unresolved.

I2 / Release batching

Do not treat commit churn as a causal diagnosis.

Potential gain: fewer release bookkeeping operations. Cost: a real distribution-policy change. Updates fetch the main archive and skip equal versions; batching can expose changing content under one version unless release distribution is isolated.

Commit, path, rollback, and recovery guards still have jobs under batched releases. In the sampled 300 subjects, 40 mention “release” and 15 mention “guard”; those counts do not show which checks batching would eliminate.

Revisit when: a bounded design names the removable guards, the retained guarantees, and how installs of the same version remain equivalent.

main-archive source · Equal-version skip

I4 / CLI deletion

No safe bulk deletion scope was established.

Potential gain: less public surface. Cost: breaking compatibility or recovery. The proposed ten-command list includes active wrappers, internal authorities, maintainer calls, and generated recovery commands.

associate-files and uncommitted-inventory have compatibility launchers. Green-gate logic is used internally; the three fast-stage commands are used by maintainer verification; recovery emits recover-finalization. A selector’s internal use is distinct from use of its public adapter.

Revisit when: a specific adapter has a caller audit and a compatibility decision. Absence from a repository grep cannot prove absence of external users.

Maintainer call sites · Internal gate use · Generated recovery command

Earlier coordination idea

Defer automatic reconciliation of in-flight work.

Potential gain: changed decisions propagate to affected work. Cost: interruption, invalidation, and ownership rules across live tasks. Queued semantic revalidation already exists as an advisory step and excludes in-flight work.

Revisit when: a concrete changed decision demonstrates stale active work that existing steering and queued revalidation cannot handle. The cards support the principle, not a new coordination engine.

I7 / Recipe-card front door

Use examples without importing a second workflow.

Potential gain: easier assignment writing for unfamiliar jobs. Cost: duplicated intake, permission, and output rules. Existing capture, specs, interviews, and discovery cover much of this need.

Revisit when: repeated newcomer failures show that a short example would fix a specific gap. Do not turn the 23 paid cards into 23 maintained skill files or mandatory prompting rounds.

do-work capture-request: Separate Go test correctness from per-file performance budgets in maintainer verification.
