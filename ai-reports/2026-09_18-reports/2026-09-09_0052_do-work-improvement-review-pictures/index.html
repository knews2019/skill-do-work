Three cleanups for the do-work instructions

The instructions that drive do-work have grown. Some sentences are wrong, some rules are written twice, and the release history ships whole. Three work requests fix this, in a fixed order. Nothing else is planned yet.

3 changes queued as work requests 1 idea on hold 2 ideas dropped

A "REQ" is one work request in the do-work queue. REQ-622, 623 and 624 were created on 9 September under user request UR-130. When this page was written, REQ-622 had just started and the other two were waiting.

The plan, in order

Fix first, then shorten. If you shorten text that is still wrong, you keep the mistake and lose the context around it. Archiving the release notes is independent, but it was placed last so the whole batch reads as one job.

How big are the files?

The four core files together hold 42,737 words. The changelog alone is more than twice that. These are file sizes, not proof of what an agent reads on a normal task. Agents are told to read selectively, so nobody has measured how much of this text is actually loaded per run.

What happens to the release history

Every entry must still exist exactly once, and the root changelog and the installed copy must stay identical. Fifty is a starting number, not a measured best value. Before trimming, check that no version or update tool needs older entries.

Why one idea is on hold

The held idea, R4, would turn test time-budget failures into warnings. Two things stop it. The timing data above cannot show that budgets are the real problem. And the maintainer test runner that enforces those budgets is marked for deletion in an earlier request, REQ-566, even though later work still optimized it. Decide the runner's future first, then decide its budgets.

What "done" means for each request

1

REQ-622 · Fix wrong sentences

Do
Take each of the 19 recorded mismatches. Check it against the current code and the intended behavior. Fix the text, or record why it is already obsolete.
Do not
Assume the code is always right. If code and intent disagree, write down the conflict instead of picking one silently.
Done when
All 19 entries have a written outcome.
2

REQ-623 · Remove repeated rules

Do
Where two files explain the same thing, keep the one that owns it and point to it from the other. Keep everything an agent needs to act, judge, and recover from errors.
Do not
Chase a percentage target or rewrite the whole thing. Do not claim faster runs or fewer tokens without measuring.
Done when
The four files are shorter and a simple task, a complex task, and an interrupted task can still be completed from the text alone.
3

REQ-624 · Archive old release notes

Do
Keep the newest 50 entries in both changelog copies. Move older entries into dated archive files with working links.
Do not
Change how often releases happen or how versions are numbered.
Done when
Every entry exists once, both copies match, and version and update commands still work.

What this report does not claim

It does not claim the changes will make do-work faster or cheaper in tokens. The files are large, and that is measured. How much of them an agent reads per task is not measured. The reason to do this work is easier maintenance: fewer wrong sentences and fewer places for the next change to drift.
