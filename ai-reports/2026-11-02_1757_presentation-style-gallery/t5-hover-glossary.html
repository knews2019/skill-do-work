The 16 MB limit that never ran

Proof

Verdict

Fixed and pinned by a test in release 0.306.5 (2026-10-19). When a backend prints too much, the second-opinion launcher now keeps the first 16 MB and reports "backend output exceeded capture limit". Before this release, the code for that capture limit existed, but it never ran.

83146e48 (release 0.306.5, REQ-702)aa61c81a (the fix)

Problem

What went wrong

When the launcher starts a backend, the operating system gives it a pipe for its output. The launcher collects that output in a buffer, one for stdout and one for stderr. The buffer has its own Write method, and Write holds the limit: it keeps at most 16,777,216 bytes and sets a truncated flag when it cuts.

report_second_opinion.go:1061-1080report_second_opinion.go:1144-1145

The old buffer used embedding: it held Go's bytes.Buffer without a field name. That gave it a promoted method called ReadFrom. Go moves the bytes from the pipe into the buffer with io.Copy, and io.Copy prefers ReadFrom when the destination has one. So io.Copy called ReadFrom, and our Write never ran. The limit never ran either. The truncated flag stayed false, and the error could never fire.

aa61c81a (old struct)report_second_opinion.go:1141report_second_opinion.go:1194-1195

Change

The fix

The buffer now keeps bytes.Buffer in a named field called captured. A named field keeps its methods to itself, so the buffer has no ReadFrom. Every byte now goes through Write, and Write applies the limit. The same commit added a live progress mirror that copies each backend line to stderr, and that mirror lives in Write too.

report_second_opinion.go:1055aa61c81a

Proof

The proof

A pin test, TestSecondOpinionCaptureCapsBackendOutput, sends 16,777,300 bytes through a real process. It expects exactly 16,777,216 bytes back plus an error. It passed on 2026-11-02 in 0.11 seconds.

A short Go program written for this gallery copies the old and new buffer shapes and shows the same thing side by side. It is not project code. The old shape kept 16,777,300 bytes with truncated=false. The new shape kept 16,777,216 bytes with truncated=true.

Effect

What changes for you

Nothing to do. If a backend ever floods its output, a second-opinion run keeps only the first 16 MB of each stream and reports "backend output exceeded capture limit". Before the fix, the launcher kept everything in memory, with no limit.

Every word on this page, explained

backend
The other AI tool the launcher runs to write a second opinion: codex, gemini or agy.
launcher
The do-work-cli command that starts the backend, collects its output and checks the result.
pipe
A channel the operating system gives two programs: the backend writes into one end, the launcher reads from the other.
buffer
A piece of memory that collects bytes as they arrive. Here: secondOpinionBuffer, one for stdout and one for stderr.
Write
Our own method on the buffer. It checks the 16 MB limit, cuts extra bytes and marks the buffer as truncated.
capture limit
The most backend output the launcher keeps in memory: 16 MB (16,777,216 bytes). Anything past it should be cut and reported.
truncated
A flag set when output was cut at the limit. The launcher turns it into the error "backend output exceeded capture limit".
embedding
A Go feature: put a type inside a struct without giving it a field name. The struct then gets all of that type's methods for free.
promoted
A method the outer struct gets from an embedded type. You did not write it, but the struct has it.
ReadFrom
A method on bytes.Buffer that keeps reading a stream into memory until the stream ends. It does not know about our 16 MB limit.
io.Copy
Go's standard function that moves bytes from a reader to a writer. If the writer has ReadFrom, io.Copy hands it the whole stream and skips Write.
named field
A struct field with a name, like captured bytes.Buffer. Its methods stay on the field, so the struct does not get them.
pin test
A test that fails if this exact bug comes back. It names the failure it guards against.
