  1. 1

    The commit names the cause

    Problem

    The ReadFrom method, promoted from bytes.Buffer, let io.Copy skip Write. The 16 MB limit and its error live in Write, so they never ran.

    aa61c81a (commit message)
  2. 2

    The embedded field

    Cause

    This line has a type but no field name. Go calls that embedding. The struct gets every bytes.Buffer method for free, ReadFrom included.

    aa61c81a (old struct)
  3. 3

    The named field

    Change

    Now the buffer is a field called captured. Its methods stay on the field, so the struct has no ReadFrom. Write is the only way in.

// Reproduction of the 0.306.5 capture-cap bug: same Write as the old secondOpinionBuffer, two struct shapes.
package main

import (
    "bytes"
    "fmt"
    "io"
    "os/exec"
)

const limit = 16 * 1024 * 1024

// embeddedBuffer is the old shape: bytes.Buffer is embedded, so its ReadFrom method is promoted.
type embeddedBuffer struct {
    bytes.Buffer
    truncated bool
}

func (buffer *embeddedBuffer) Write(data []byte) (int, error) {
    length := len(data)
    if remaining := limit - buffer.Len(); len(data) > remaining {
        data, buffer.truncated = data[:remaining], true
    }
    _, _ = buffer.Buffer.Write(data)
    return length, nil
}

// namedBuffer is the fixed shape: the bytes.Buffer is a named field, so Write is the only way in.
type namedBuffer struct {
    captured  bytes.Buffer
    truncated bool
}

func (buffer *namedBuffer) Write(data []byte) (int, error) {
    length := len(data)
    if remaining := limit - buffer.captured.Len(); len(data) > remaining {
        data, buffer.truncated = data[:remaining], true
    }
    _, _ = buffer.captured.Write(data)
    return length, nil
}

func main() {
    old := &embeddedBuffer{}
    command := exec.Command("/usr/bin/head", "-c", "16777300", "/dev/zero")
    command.Stdout = old
    _ = command.Run()
    _, hasReadFrom := any(old).(io.ReaderFrom)
    fmt.Printf("old (embedded):  io.ReaderFrom=%v  captured=%d bytes  truncated=%v\n", hasReadFrom, old.Len(), old.truncated)

    fixed := &namedBuffer{}
    command = exec.Command("/usr/bin/head", "-c", "16777300", "/dev/zero")
    command.Stdout = fixed
    _ = command.Run()
    _, hasReadFrom = any(fixed).(io.ReaderFrom)
    fmt.Printf("new (named):     io.ReaderFrom=%v captured=%d bytes  truncated=%v\n", hasReadFrom, fixed.captured.Len(), fixed.truncated)
}
  1. 4

    The old shape has ReadFrom

    Cause

    io.ReaderFrom=true means Go sees a ReadFrom method on the old buffer. When Go copies the backend's output, it uses that method and skips Write.

    scratch program, 2026-11-02
  2. 5

    84 bytes past the limit, no flag

    Problem

    It kept 16,777,300 bytes. The limit is 16,777,216. The truncated flag stayed false, and that flag is the only thing that turns into the error "backend output exceeded capture limit".

    report_second_opinion.go:1194-1195
  3. 6

    The new shape stops at the limit

    Effect

    No ReadFrom, so every byte went through Write. It kept exactly 16,777,216 bytes and set truncated to true.
