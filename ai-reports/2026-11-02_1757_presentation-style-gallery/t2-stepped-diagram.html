  1. Cause

    1The backend prints its answer

    The launcher starts a backend program, for example codex. Everything the backend prints goes to its stdout and stderr, and the launcher collects both in a buffer.

    report_second_opinion.go:1142-1145
  2. Cause

    2Go opens a pipe and runs io.Copy

    The buffer is not a file. So Go's os/exec package opens a pipe and starts io.Copy to move the bytes from the pipe into the buffer.

    report_second_opinion.go:1141
  3. Cause

    3io.Copy asks one question

    Before it copies, io.Copy checks the buffer: does it have a ReadFrom method? If yes, io.Copy hands the whole stream to ReadFrom and never calls Write.

    aa61c81a commit message
  4. Problem

    4Before 0.306.5: yes, so ReadFrom

    The old buffer used embedding for bytes.Buffer, so it had a promoted ReadFrom. ReadFrom kept every byte. The 16 MB check in Write never ran. A reproduction kept 16,777,300 bytes and reported truncated=false.

    aa61c81a (old struct)reproduction run, 2026-11-02
  5. Change

    5Since 0.306.5: no, so Write

    The buffer now holds a named field, captured bytes.Buffer. The buffer type has no ReadFrom, so io.Copy calls Write. Write keeps at most 16 MB.

    report_second_opinion.go:1054-1059report_second_opinion.go:1075
  6. Effect

    6The error fires

    Write cuts the extra bytes and sets the truncated flag. When the backend is done, the launcher turns that flag into the error "backend output exceeded capture limit".

    report_second_opinion.go:1076-1078report_second_opinion.go:1194-1195
  7. Proof

    7A test pins it

    TestSecondOpinionCaptureCapsBackendOutput sends 16,777,300 bytes and expects exactly 16,777,216 bytes plus an error. It is a pin: it fails if the old path comes back. It passed on 2026-11-02 in 0.11 s.

    report_second_opinion_test.go:804go test run, 2026-11-02
