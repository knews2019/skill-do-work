  3. 03

    Implement the single-reviewer loop first with explicit stopping rules

    Ship the one-reviewer loop before multi-provider council. The proposal recommends a default cap of 3 rounds (extendable to 5 rounds for consequential supported issues), while REQ-710 leaves the exact numerical cap to the builder. Later rounds recheck changed code and open findings. Stop early when clean or only nits remain; invalidate prior approval if any meaningful code change lands after the reviewed diff.

    Upstream pattern: tstack/skills/sol-loop/SKILL.md Smallest first slice
  4. 04

Offer the optional Jester advisory reviewer (defaulting to the latest available Gemini via the harness, such as Gemini 4 Argon) on the same serious brief: never wait on a slow or failed Jester, exclude its numerical score from acceptance or PR grades, and act on its findings only when verified against the code.

    Upstream pattern: tstack/skills/council/SKILL.md Clarification: UR-163 / REQ-710
  5. 05

    Target: skills/do-work/actions/work.md Step 7 & Error Handling Proof: REQ-710 Red-Green Proof

3. Open Decisions & Advisory Reviewer Contract changed

REQ-710 locks the core invariants (opt-in only, finding ledger, verified model identity, current-diff approval, truthful unresolved state, and optional Gemini Jester) while leaving three integration choices open.

Q1 · Unresolved Lifecycle Handoff

Question: Should an unresolved opt-in review hold the claimed request in place, or record a dedicated unresolved review outcome and hand back?

Report recommendation: Hold only the opted-in request so unrelated queued requests keep moving ("One broken pipe doesn't stop the rest of the factory").

Q2 · Provider Selection Environments

Question: Which harnesses and CLIs must support multi-provider council dispatch first?

Report recommendation: Use available harness capabilities, record actual resolved models, and report missing named providers rather than silently substituting or breaking platform independence.

Q3 · Scope Boundary & Non-Goals

Boundary: Pull-request creation, PR comment posting, watcher daemons, and merge permissions are explicitly outside REQ-710.

Builder latitude: Invocation flags, ledger storage format inside ## Review, and exact numerical round limits are builder-decided in REQ-710.

Jester · Optional Advisory Reviewer

Role: Optional fourth/sidecar voice defaulting to the latest available Gemini resolved by the harness (e.g., Gemini 4 Argon; not a hardcoded model ID).

Rules: Receives the same serious brief without being told to act funny or that it is advisory. Its score never blocks or approves and is omitted from PR council grades. Verified defect evidence still counts; slow or failed Jester runs never delay the loop.

Upstream workflow comparison: sol-loop vs. council and review call ratio

The original report inspected t3dotgg/tstack at commit 1085050f3baed1ac724caa4a8166145fb2ac88af (28 October 2026). Despite similar summaries, the two upstream skills have different stopping mechanics:

  • sol-loop (one reviewer, bounded): Freezes scope and base (including untracked files), runs covering checks, and dispatches GPT Sol with stable finding IDs and blocker / should / nit severities. The parent verifies claims, applies minimal fixes, or pushes back with evidence. Defaults to 3 rounds (extendable to 5 for named high-risk cases while supported issues remain, or when requested). Stops when only nits remain, when a dispute persists after two replies, or when the budget is exhausted. Approval must cover the current behavior diff. Prohibits nested reviewers and in-flight edits during review.
  • council (three parallel providers, unbounded upstream): Fixes known issues and runs checks first, resolves three strong models from distinct providers at high effort, and runs parallel read-only reviews. Missing providers are reported rather than substituted. Records per-reviewer round scores ("no score" when absent) with no numerical pass threshold, no round cap, and no deadlock rule.
  • Local adaptations added by this proposal: Keeping council reviewers blind to each other’s findings until initial reviews return, capping council rounds, budgeting the whole round, and adding the non-blocking Jester advisory pass are local do-work additions, not upstream tstack behavior.

Glossary of terms
AI-Evaluation-Loop
User-confirmed name for the opt-in review-fix-recheck workflow captured in REQ-710. Runs up to a bounded number of rounds, tracks findings in a ledger, and approves only the current diff.
Sol-loop
Upstream tstack skill using one reviewer, stable finding IDs, and a 3-round default cap (5 for high-risk cases) with explicit stop conditions.
Council
Multi-provider review mode dispatching three distinct model providers in parallel at high effort.
Jester
Optional non-blocking advisory reviewer in REQ-710, defaulting to the latest available Gemini resolved by the harness (e.g., Gemini 4 Argon). Its score never counts toward approval or PR grades, but verified defect evidence is acted on.
Finding ledger
Structured record inside ## Review tracking each finding’s stable ID, severity (blocker, should, nit), evidence, disposition, and open status across rounds.
completed-with-issues
Terminal status in ordinary do-work run when a request still fails review after its single remediation attempt.

Recovery check in work-reference.md (line 357) that reuses an already-merged builder commit range only if protected paths have not drifted, while still rerunning qualification, tests, gate, and review.
