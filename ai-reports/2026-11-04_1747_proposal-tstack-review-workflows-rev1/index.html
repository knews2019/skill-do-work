What council and sol-loop actually do

The README shorthand hides a meaningful difference: Sol has explicit stopping rules. Council asks for agreement without specifying a round limit.

Council: three independent providers

Fix known issues and run checks first. Resolve three strong models at high effort, launch parallel read-only reviews, collect findings, make accepted fixes, and request fresh reviews until all are satisfied. Missing providers are reported rather than substituted.

Code reviews include a score per reviewer per round. Scores are recorded, with “no score” when absent; the skill sets no numerical pass threshold. The parent must resist scope growth. It specifies no explicit budget or deadlock rule.

council · source

Sol-loop: one reviewer, a round limit

Freeze scope and base, include untracked files, run covering checks, then ask GPT Sol to review. Use stable IDs and blocker / should / nit findings. The parent verifies each claim, makes minimal fixes, or rejects it with evidence.

Default: three rounds. Extend to five for the named high-risk cases while supported issues remain, or when requested. Later rounds examine changed code and open findings. Stop for nits, a dispute persisting after two replies, or budget exhaustion. Approval must cover the current behavior diff.

sol-loop · source
Execution details worth carrying over

Both use capability discovery rather than a hardcoded current model ID. Sol-loop prohibits nested reviewers and scoped edits while review runs. In T3, each round is a fresh delegate task; failures and missing replies are not approval. No review workflow was executed during this research.

Proposed council rule: give reviewers the same frozen scope and evidence before revealing other reviews. Preserve dissent and budget the whole round. This independence rule and a council round cap would be additions, not claims about upstream.
