# Adopt the exclusive-session model and remove the concurrency machinery

## What

Make exclusive repository use an explicit product boundary: one do-work session, one active
REQ, one coder context. Delete the 6,511 words of machinery that exist to detect, coordinate
and recover unsupported concurrent runs, and replace them with a ~200-word operating rule —
a session assumes it is alone, and unexpected repository state matters only when it prevents
the active REQ from finishing.

## Why

Three signals that this machinery costs more than the mode it supports is worth:

1. It is a sixth of the core pipeline — 6,511 words across three files, with the Lock Guard
   section alone at 1.8× the median action file.
2. It took four REQs to stabilize the lock (REQ-018 built it; REQ-035, REQ-044 and REQ-047
   each fixed a correctness hole afterwards), and three for the write_set gate (REQ-032,
   then REQ-036 and REQ-045).
3. It is asymmetric and therefore incomplete: the lock guards REQ ownership across every
   session, while the write_set gate guards file ownership only within one session. Closing
   that gap means *more* machinery, in a mode the product does not support.

## Detailed Requirements

### 1. State the exclusive-session boundary (≤125 words, combined with requirement 2)

The pipeline supports one active do-work session, one active REQ, and one coder context.
Parallel sessions, co-dispatched builders, and cross-session ownership are outside the
product contract. The pipeline does not detect, coordinate, or recover an unsupported
concurrent run. If two do-work sessions are run against one checkout anyway, behavior is
unspecified — and the pipeline spends no instructions or state trying to make that safe.

### 2. State the current-REQ relevance rule

Unexpected repository state matters **only** when it prevents the active REQ from being
implemented, tested, archived, or committed. Otherwise: preserve it, exclude it from this
REQ's staging, and continue — spend no time explaining or repairing it.

### 3. State the three-attempt stop condition (≤75 words)

The coder counts consecutive fix attempts **in its current context only**. After three
failures, stop the local retry loop and report the unresolved blocker. Use `pending-answers`
only when progress genuinely requires a user decision. A restarted coder session starts with
a fresh count.

### 6. Keep these — they are not concurrency machinery

- **Crash recovery proper (~920 words)** — a crashed session still leaves files in
  `do-work/working/`. Only the *concurrency gate* inside it is removed; recovery of an
  interrupted single session stays. Without a lock to consult, recovery no longer needs to
  distinguish "another live session's claim" from "abandoned" — every `working/` file is this
  session's to recover.
- **Qualification, tests, explicit staging, archive and commit checks** — unchanged. These
  remain the evidence that a REQ landed.
- **The `write_set:` frontmatter field** — kept (see Constraints).

## Constraints

- **Replacement cap: ≤200 words total** (≤125 for requirements 1–2, ≤75 for requirement 3).
  Exceeding the cap defeats the request. This is the `crew-members/maintenance.md`
  delete-before-you-add discipline applied to its own subject matter.
- **No new durable state.** No frontmatter fields, no lock or marker files, no retry
  artifacts, no `.git/index.lock` retry logic, no attempt counter written to disk. The
  attempt count lives in coder context and dies with the session.
- **Keep the `write_set:` field; delete only the rule that gates co-dispatch on it.**
  Each REQ still declares which files it touches, and the board keeps rendering the overlaps
  badge. `tools/queue-kanban/model.go` must NOT be touched — its `annotateWriteSetOverlap`,
  the `overlaps` badge and the drawer row all stay. (User decision at capture.)
- **One coherent commit.** The cut blocks reference each other — cleanup's live-claim gate
  reads the lock file the Lock Guard section defines. No intermediate state may leave the
  pipeline referencing a removed section. (User decision at capture: one REQ, not a batch.)
- **Grep for dangling references before declaring done.** Removing a section that other files
  cite by name leaves broken cross-references; the skill's own convention is that a fix to a
  copy-pasted primitive is rarely local.
- Follow the repo's pre-commit ritual: bump `actions/version.md` and add a `CHANGELOG.md`
  entry whose title says what shipped.

## Resolved Decisions

Both questions the earlier analysis left open were answered by the user in the revised report:

- **Where does the attempt counter live?** → Coder session context only. After three failures,
  stop the local retry loop and report the blocker. No frontmatter, no file; a restarted coder
  session starts fresh.
- **How aggressive should the index retry be?** → There is no retry. No proactive
  `.git/index.lock` handling and no concurrency branch. If Git cannot commit the active REQ,
  that is an observed blocker handled by the ordinary failure path.
