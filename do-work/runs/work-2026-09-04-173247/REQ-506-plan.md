# REQ-506 Implementation Plan

## Architecture

Extend per-request `advance` from a phase projector into a phase executor without creating a second command implementation. `advance REQ-NNN [--diff-range <base>..<merge>] [-- <current-phase argv...>]` determines the current mechanical phase, calls the existing typed handler for that phase (`estimate-p50`, `preflight`, `qualify`, or `run-blocked-check`), and returns the subordinate result as structured gate evidence. Tokens after `--` are phase inputs, not a shell string: estimator signals for estimate, the resolved baseline command for preflight, and `run-blocked-check` options for the test gate. Qualification consumes the explicit merged range. Missing phase inputs produce a finding whose tokenized `next_argv` shows how to satisfy it; `advance` never emits instructional paragraphs or guesses judgment inputs.

Add `AdvanceGateRecord` to the public result model with `request_id`, `request_path`, `provenance` (`existing_evidence`, `advance_executed`, `baseline_record`, or `merged_range`), `gate_id`, `state` (`needs_input`, `satisfied`, `findings`, or `failed`), subordinate `outcome`, `findings`, `changes`, `next_argv`, and `verification_argv`. `AdvanceLifecycleResult` carries the ordered records. These are the only fields `work.md` consumes: identity prevents cross-REQ attribution, provenance names the evidence source, state says whether agent work remains, and outcome preserves success/findings/failure rather than translating it into prose. Existing Markdown sections/frontmatter remain the durable phase markers; the gate record is invocation evidence, not a second lifecycle store.
