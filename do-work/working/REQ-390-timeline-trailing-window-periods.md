## Plan

The Timeline's period toolbar is three calendar-period chips backed by ~200 lines of UTC calendar arithmetic in `web/board-timeline.js` (`timelinePeriodStart`, `timelineSteppedPeriodStart`, `timelinePeriodWindow`, `timelinePeriodAnchor`, `timelinePeriodLevelOfWindow`, `timelinePeriodGridOfWindow`, `timelineSteppedWindow`, `TIMELINE_PERIOD_LEVEL_NAMES`). Trailing windows need none of it: a chip becomes `[nowMs - N days, nowMs]` clamped to the bounds, and "All days" becomes `[boundStartMs, boundEndMs]` — the same window the view opens on. One new pure function, `timelineTrailingWindow(trailingWindowValue, nowMs, boundStartMs, boundEndMs)`, clamps each endpoint to the bounds and then settles through `timelineZoomedWindow(…, 1, 0, …)`, exactly the pattern `timelineTypedWindow` and the old `timelinePeriodWindow` both use, so the chips inherit the shared floor/ceiling/edge rules and acquire none of their own. Clamping each endpoint BEFORE settling is required, not decorative: the settle preserves a WIDTH, so a 90-day window on a 3-day archive would otherwise be slid forward off now instead of cut short at the range start. With the chips anchored at now, the calendar grid disappears from the stepping path too, so `‹`/`›` collapse to the screenful pan they already do for a window of the reader's own — `timelinePannedWindow(start, end, ±1, …)` — and the whole grid-vs-exactness split (`timelinePeriodGridOfWindow` plus `timelineSteppedWindow`) is deleted rather than ported. Chip lighting and the state readout are then derived by walking `#view-timeline [data-timeline-period]` in the DOM and recomputing each button's candidate window with the same function the click uses, so the control set lives in `template.html` alone and there is no parallel list in JS to go stale. The four surfaces the REQ names — toolbar markup, window maths, the Go browser probes, and the state-restore path — plus the shipped ARIA/hint/comment prose, all follow from those two changes. The cost is test surgery: `generate_test.go` carries two large JS-behavior tests that exist solely to pin the calendar-period maths (`TestJavaScriptBehaviorTimelinePeriodStepsOnCalendarBoundariesAndJumpsToNow`, `TestJavaScriptBehaviorTimelinePeriodChipsLandOnNowAndStepsStayAligned`, ~700 lines together) and two unrelated tests that borrow `timelinePeriodStart` as an oracle, and three browser probes click `day`/`week`/`month` for reasons that survive the change but need different controls.

- D1 — ‹ and › always pan one screenful, and the calendar-grid stepping path is deleted, not ported. RECOMMENDED. One stepping rule replaces two, and 'pick a width, then walk back through history' is a coherent story for now-anchored chips. - D2 — Keep every DOM identifier (`data-timeline-period`, `.timeline-periods`, `#timeline-period-prev/next`, `#timeline-period-state`) and rename only the JS functions whose meaning changed. RECOMMENDED. - D3 — Chip values are `1|7|30|90|all`, matching `data-durations-window="30|90|all"` on the same page. RECOMMENDED. - D5 — 'All days' is `[boundStartMs, boundEndMs]`, the payload range plus the forecast and the 2% cosmetic padding, i.e. the window the view opens on. RECOMMENDED.
