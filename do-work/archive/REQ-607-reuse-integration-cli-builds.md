## Implementation Summary

- `skills/do-work/tools/do-work-cli/internal/suiteinstall/suite_commands_test.go` (modified) — wrapped `buildTestCLIBinary` with `sync.Once` (`builtTestCLIBinaryOnce`) so the test CLI binary is compiled exactly once per test binary execution in an isolated temporary directory, and added `TestMain` to clean up the temporary build directory upon test process exit.

## Decisions

- **D1 Build once per test binary with `sync.Once` in `suiteinstall`:** In `suite_commands_test.go`, three heavy test functions (`TestBuiltInstallAndUpdateExit130WhenSignalsInterruptBlockedConfirmation`, `TestBuiltInstallExits130AfterRecoveringASignalInterruptedMidWriteInstall`, `TestBuiltInstallExitsZeroWhenASignalLandsAfterTheInstallIsVerified`) each independently invoked `buildTestCLIBinary(t)` to compile `./cmd/do-work-cli`. Caching the path in a package-level singleton eliminates 2 redundant `go build` invocations per run.
- **D2 Clean up build directory in `TestMain`:** Instead of per-test cleanup which would delete the binary while subsequent tests in the suite still need it, `TestMain` ensures the temporary directory is cleaned up when the test runner process terminates.
- **D3 Audit of other package-local CLI builders:** An audit across `skills/do-work/tools/do-work-cli` showed that `lifecycleadvance` (`advance_commands_test.go`), `nextselection` (`next_commands_test.go`), and `finalization` (`finalization_req499_test.go`) already use `sync.Once` singletons to build once per test binary. `corehelpers` and `cmd/do-work-cli` each contain only a single test function that builds the CLI, so they already build only once.
- **D4 Rejection of cross-package sharing via `DO_WORK_TEST_DO_WORK_CLI_BINARY`:** `DO_WORK_TEST_DO_WORK_CLI_BINARY` is an environment variable designed for heavy maintainer probe scripts. Sharing a pre-built binary across independent Go test packages would require content-hashing source trees to prevent stale binaries, risking race conditions across worktrees and build flags (`-race`), and perturbing the heavy verification runtime fingerprint. Because `GOCACHE` already makes inter-package compilation fast (~0.3s), cross-package sharing is not justified by measured savings.

## Lessons Learned

**What worked:**
- Using `sync.Once` and `TestMain` in Go tests to create a safe per-test-binary singleton with reliable cleanup on process exit.
- Benchmarking the specific case (`--case heavy-cli-build`) using the reproducible baseline tool created in REQ-606 to measure exact CPU and wall time deltas.

**What didn't:**
- Attempting cross-package binary caching via environment variables introduces substantial cache invalidation, fingerprint perturbation, and worktree isolation hazards for minimal return (~0.3s).

**Worth knowing:**
- In Go `testing`, `t.TempDir()` is scoped to the individual test function and removed as soon as that test completes; per-binary singletons must use `os.MkdirTemp` and clean up in `TestMain`.
