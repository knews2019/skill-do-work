## Decisions

- **D-01 (DECIDE & STATE):** Keep the public utility as a Shell entry point but perform replacement in embedded Python 3. Byte offsets, NUL-containing exterior data, exact missing-final-newline behavior, mode preservation, and `os.replace` are materially safer than reconstructing a client Justfile line-by-line in shell/awk.
- **D-02 (DECIDE & STATE):** A recognizable legacy block with missing, duplicate, reordered, or interleaved custom top-level content is rejected unchanged. Without old end sentinels, claiming an ambiguous span would risk swallowing a user recipe into do-work ownership.
- **D-03 (DECIDE & STATE):** Existing marker-free custom Justfiles receive an append because the explicit install invocation authorizes a fresh section; existing managed or complete legacy sections still use the reviewed consent gate.

## Lessons Learned

**What worked:**
- Treating the client file as bytes and ownership as one inclusive marker span made the preservation guarantee directly testable, including NUL exterior data and missing filename assumptions.
- A candidate copy provides the consent diff without requiring a dry-run mode in the mutation utility.

**What didn't:**
- A first-pass legacy span would have absorbed any custom top-level recipe interleaved between the five old recipes. Rejecting ambiguous legacy structure is the only safe behavior when the old block has no end marker.

**Worth knowing:**
- The section file itself must be exactly one newline-terminated managed span; absent-target templates must embed those exact bytes once.
- Repeated current-content reconciliation performs no rename, preserving byte identity without unnecessary inode churn.

## Orientation

[MAP CHANGED] Do-work now owns one explicit `do-work:recipes` section instead of five independently inferred recipe spans. `tools/replace-text-section.sh` is the shared create/migrate/replace boundary that the suite installer can reuse while preserving every client-owned Justfile byte outside the markers.
