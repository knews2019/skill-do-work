## What

## Remediation

A dual-lens adversarial review of the first attempt returned **FAIL** on three Important findings. This section documents each finding, the root-cause fix, five hand-walked scenario traces proving the fix, the updated word-count receipt, and the new decisions the fix required.

### Findings

**FINDING 1 — "Proceed anyway" silently killed the live session.** The first attempt's "proceed anyway" rewrote the lock's `session_id` to the new (second) session while leaving `claimed_req` alone. The Heartbeat-refresh procedure required an exact `session_id` match before overwriting, so the *original* session — the one the prompt promised would "stay reserved" — found a mismatch at its very next touchpoint and stopped, believing it had been superseded. Choosing the non-disruptive option destroyed the other session; the text's stated behavior and its mechanical effect were opposites.

**FINDING 2 — "Proceed anyway" had no durable marker, so it stopped applying.** The guard's detect/prompt/resolve step was correctly one-shot per session, but Crash Recovery was not — it re-evaluated `do-work/working/` at *every* Step 1 entry, including every Step 10 → Step 1 loop iteration. The only thing gating Crash Recovery for a "proceed anyway" session was "skip if the guard resolved to proceed-anyway" — a fact that lived nowhere but that session's own conversational memory. On the second REQ (after the mandatory CONTEXT WIPE between REQs), nothing durable told Crash Recovery to keep skipping, so it would eventually reset and re-queue the *other*, genuinely live session's claimed file — reproducing the exact 2026-07-01 hollow-paper-trail incident this REQ exists to prevent, just delayed by one loop iteration.

**FINDING 3 — Interactive vs. non-interactive had no executable test.** The original text asked the session to self-assess ("can this run present a prompt to a human?") with no concrete procedure. The most likely misclassification: `actions/pipeline.md`'s foreground dispatch of the `run` step, which explicitly may run as a subagent ("subagent if available, inline otherwise"). A subagent that wrongly concluded it could prompt would block on an unanswerable ask-user call, hanging the whole pipeline instead of failing cleanly and resumably.

**Minor findings (also fixed):** Step 8's "On failure" branch and the mid-run "Blocked flip" branch gave no cue that lock bookkeeping applied there, unlike the success path's explicit heartbeat refresh. Step 1's lock-guard paragraph in `actions/work.md` (~204 words) restated every choice's full consequence, duplicating `actions/work-reference.md`'s companion section and inflating the always-loaded orchestrator file.

### Root cause and design change

All three findings trace to one root cause: the original lock conflated **who holds the queue** with **who is allowed to run**, so the only way to express "I'm running alongside you" was to seize the lock (rewrite `session_id`) — which is precisely what displaced the other session (Finding 1) and left the resulting state unrecorded anywhere durable (Finding 2).

**Fix:** the lock file now records exactly one **holder** (`session_id`, `started_at`, `heartbeat_at`, `claimed_req` — unchanged shape) plus a new `coexisting_sessions` array (`{session_id, joined_at, heartbeat_at, claimed_req}`, default `[]`). "Proceed anyway" **appends its own entry** to `coexisting_sessions` and never touches the holder's fields — the holder's `session_id` keeps matching at every one of its own heartbeat-refresh touchpoints, so it runs to completion exactly as the prompt promises (fixes Finding 1). "Take over" is unchanged — it still fully displaces the holder, because take-over is *supposed* to displace.

This same array is the durable, file-backed record Finding 2 needed: Crash Recovery's gate no longer asks "did I resolve to proceed-anyway earlier" (a memory fact); it re-reads `do-work/orchestrator-lock.json` fresh on every single invocation and skips a `working/` file **per-file**, only when that specific file is the `claimed_req` of the holder or of a `coexisting_sessions` entry whose `session_id` differs from this session's and whose `heartbeat_at` is still within the 45-minute threshold. This is checked from disk every time, survives any number of CONTEXT WIPEs and Step 10 → Step 1 loops, and requires no new marker file.

Finding 3 is fixed with a concrete, two-part Interactivity test: (1) is this the top-level session the user is directly conversing with — not a subagent spawned via Task/Agent dispatch (a subagent has no user turn to pause on) — mirroring the identical test `actions/code-review.md` already uses for its own consent gate; (2) is an ask-user/blocking-prompt mechanism actually available and usable right now. If either can't be confirmed, the session is non-interactive by default (fail-safe) and takes the refusal branch — a clean, resumable no-op, unlike a hung prompt.

One additional wrinkle the fix had to resolve that wasn't one of the three named findings: what happens when the **holder** exits normally while a coexisting session is still live? Deleting the whole lock file (the original Release behavior) would erase the still-active coexisting session's own record, breaking its next heartbeat-refresh check. Fix: Release only deletes the file when this session is the holder **and** no live `coexisting_sessions` entries remain; if any remain, the file is left in place untouched, and the now-idle holder slot self-heals through the existing 45-minute staleness path the next time any session reaches Step 1 — no promotion/hand-off mechanism invented, per the YAGNI guidance.

### Scenario traces

**1. B proceeds-anyway while A is mid-build → A runs to completion undisturbed; B never touches A's working/ file, including on B's 2nd/3rd loop iteration.**
A acquires the lock (holder=A), claims REQ-018 (`claimed_req: "REQ-018"`). B starts, sees a fresh holder, is interactive, picks (a) Proceed anyway: B appends `{session_id: B, joined_at: now, heartbeat_at: now, claimed_req: null}` to `coexisting_sessions`; the holder record (A, `claimed_req: "REQ-018"`) is untouched. Crash Recovery's per-file gate checks REQ-018.md against the lock: it matches the holder's `claimed_req`, holder `session_id` (A) ≠ B's, heartbeat fresh → **skip**. B claims REQ-042 instead, refreshing *its own* `coexisting_sessions` entry at each touchpoint (holder untouched every time). B loops to Step 1 for a third REQ after a CONTEXT WIPE: the gate re-reads the lock file fresh — A's holder record is still there with a fresh heartbeat (A is still actively refreshing it at A's own Step 2/6.25/8/9/10 touchpoints) → REQ-018.md is skipped **again**, and again on every subsequent iteration, indefinitely, because the skip decision is re-derived from disk every time, never from memory. Meanwhile A's own refreshes always match the untouched top-level `session_id` — A never observes a mismatch, never stops, and completes REQ-018 normally.

**2. B takes over a fresh lock → A stops cleanly; B runs crash recovery on A's file.**
Holder=A, `claimed_req: "REQ-018"`, heartbeat fresh. B is interactive, picks (b) Take over: rewrites the top-level holder to `{session_id: B, started_at: now, heartbeat_at: now, claimed_req: null}` (full displacement — no residual record of A anywhere in the lock file); `coexisting_sessions` preserved/pruned (empty here). The per-file gate re-checks REQ-018.md: it no longer matches the (now-null) holder `claimed_req`, and no `coexisting_sessions` entry claims it either → **not** actively claimed by any other live session → recovered normally (status reset, generated sections stripped, moved back to `do-work/queue/`). A, still mid-build, hits its next heartbeat touchpoint, finds its `session_id` matches neither the holder nor any coexisting entry → stops and reports, exactly as the existing mismatch rule requires. A's own REQ-018 work is not silently lost — it's back in the queue for reprocessing, the same self-heal outcome the design always gave a genuinely dead session, now also applying correctly when a live one is knowingly displaced by explicit user choice.

**3. B finds a stale lock (>threshold) → warn, take over, crash recovery runs.**
Holder=A, `claimed_req: "REQ-018"`, heartbeat 50 minutes old (past the 45-minute threshold). B's guard auto-resolves stale (no prompt needed): warns, rewrites the top-level holder exactly as in Trace 2's take-over, preserving/pruning `coexisting_sessions`. The per-file gate finds REQ-018.md unclaimed by anyone live → recovered normally. Mechanically identical to Trace 2's recovery half, unified by the same top-level-rewrite-plus-preserve/prune-array logic, just auto-triggered by staleness instead of an explicit choice.

**4. B is a pipeline-dispatched subagent that cannot prompt → refuses and reports the holder, touching nothing.**
Holder=A, fresh heartbeat. B was spawned by `actions/pipeline.md`'s foreground dispatch of the `run` step as a subagent (`actions/pipeline.md` Step 4 substep 2: "subagent if available"; the Sub-agent context rule confirms it has no inherited conversation with a human). The Interactivity test's first check — "is this the top-level session the user is directly conversing with" — fails immediately, so B is non-interactive by the fail-safe default without needing to check ask-user availability. B takes the refusal branch: prints the holder's `session_id`/`started_at`/heartbeat age/`claimed_req`, and stops having created, modified, or deleted **no** file at all — lock, queue, or `working/`.

**5. Every exit path releases the lock only if this session actually holds it; no path leaves it held with no stale recovery.**
All four release points (Step 1's composed no-pending exit, Step 1's targeted-mode stop, Step 10's exit, the unrecoverable-error stop) call the same Release procedure, which always re-derives the three-way branch fresh from the file: **holder** → prune stale `coexisting_sessions` entries, delete the whole file only if none remain, otherwise leave it in place untouched (self-heals via the 45-minute staleness path within a bounded window — no path leaves it held *forever*); **coexisting session** → remove only its own entry, never touch the holder or delete the file; **superseded** (`session_id` matches neither) → leave the file alone, it's not this session's to release. Because every check re-reads the file rather than trusting what this session previously believed about its own role, no combination of exit path and role can delete or overwrite a record that belongs to someone else.

### New Decisions (continuing from D-08)

- **D-09 — Coexisting sessions as an array on the same lock file, not a second lock file or a separate directory of per-session lock files.** DECIDE & STATE. Keeps "one lock file, one `mkdir -p do-work`, one re-derive-the-path rule" — the existing convention every heartbeat/release touchpoint already follows. A second file or directory would double the number of paths every touchpoint has to re-derive deterministically, for no benefit at this reach (a handful of concurrent sessions at most). Reversible, low reach.
- **D-10 — "Take over" remains a full, un-recorded displacement of the prior holder.** DECIDE & STATE. Directed by the remediation brief: unlike "proceed anyway," take-over is supposed to disrupt a session the new session believes is dead — recording the superseded holder anywhere would blur that choice's meaning and add bookkeeping nothing reads. Consistent with the pre-existing stale-takeover path, which already worked this way.
- **D-11 — Release leaves the lock file in place (rather than promoting a coexisting session to holder) when the holder exits with live coexisting sessions still present.** DECIDE & STATE. A promotion/hand-off scheme was considered and rejected: it would need to pick a successor (e.g., earliest `joined_at`), migrate its fields to the top level, and specify what happens if the "promoted" session doesn't know it was promoted until its next touchpoint. The chosen fix (leave the file as-is; self-heal via the existing 45-minute staleness path) reuses a mechanism the lock already has, costs a bounded ≤45-minute delay in freeing the holder slot, and adds no new concept — direct YAGNI application per Builder Guidance's "not a distributed lock." Value: no hand-off logic to get wrong. Risk: a session arriving during that bounded window sees a "fresh" holder and may be prompted or refused unnecessarily until staleness clears — judged acceptable since it only delays a decision, it never corrupts one.
- **D-12 — Interactivity test: top-level/non-subagent check + live ask-user-availability check, fail-safe to non-interactive.** DECIDE & STATE. Reuses `actions/code-review.md`'s existing "running non-interactively (e.g., via subagent)" idiom rather than inventing new vocabulary, and directly targets the concrete failure mode named in the finding (`actions/pipeline.md`'s subagent-capable dispatch of the `run` step). Reversible, low reach.
- **D-13 — Crash Recovery's gate is per-file and lock-file-backed, replacing the original all-or-nothing "skip this step entirely" behavior.** DECIDE & STATE. This is the direct fix for both Finding 1 and Finding 2 together: per-file because a single Crash Recovery pass may need to recover an unrelated stale file while leaving a live one alone; lock-file-backed because that's what makes the decision durable across CONTEXT WIPEs and loop iterations. Value: closes both findings with one mechanism instead of two. Risk: none identified — the check is a handful of field comparisons against a file already being read for other reasons.
- **D-14 — `coexisting_sessions` entries reuse the holder's existing 45-minute stale threshold rather than a separate constant.** DECIDE & STATE. No stated reason for a coexisting session's own build to run on a different clock than the holder's; introducing a second threshold would be an unrequested knob. Reversible, low reach.

## Review (post-remediation)

Re-verification of the redesigned guard returned **FAIL** on one Important finding plus two smaller ones. The three originally-found defects (silent-kill, no-durable-marker, self-assessed interactivity) were confirmed fixed, and the design held under multi-session, displacement, crashed-coexisting-session, and 3+-session attacks. The new finding was in the success path the redesign was modeled on most carefully.

**Important — lock bookkeeping was not adjacent to the physical move (orchestrator-applied fix).** Step 8's success path cleared `claimed_req` to `null` at substep 1, but the REQ file does not leave `do-work/working/` until substep 6. During substeps 2–5 (verify Implementation Summary, create follow-ups, queue Discovered Tasks, cycle-detection walk) the file sat in `working/` while the lock said nobody claimed it. Any other live session reaching its own Step 1 in that window would run the per-file Crash Recovery gate, find the file matching neither the holder's `claimed_req` nor any `coexisting_sessions[].claimed_req`, and classify it as an abandoned crash artifact — stripping `## Implementation Summary`, `## Qualification`, `## Testing`, `## Review`, `## Lessons Learned`, `## Orientation`, `## Decisions` and moving it back to `do-work/queue/`. That is the 2026-07-01 hollow-paper-trail incident this REQ exists to prevent, reintroduced by the fix. It needs no simultaneous writes — only two sessions' Step 1 passes interleaving with one Step 8, which is the *normal* mode of the coexisting-sessions feature this REQ adds.

**Minor — the mirror-image gap at claim time.** Step 2 moved the file to `working/` at substep 1 but did not set `claimed_req` until substep 4. Same root cause, much narrower window (no interposed processing).

**Fix (D-15, DECIDE & STATE):** lock bookkeeping now goes **where the file moves**, at all four sites. Step 2 substep 1 sets `claimed_req` in the same breath as the move. Step 8 substep 1 refreshes the heartbeat but explicitly does *not* clear `claimed_req`; substep 6 clears it alongside the physical archive move. The failure path and the mid-run blocked flip were already correct (both write the clear in the same sentence as their move) and are untouched — they are now the pattern the success path matches, not the exception. Each site carries a one-line statement of the failure it prevents, so a future edit that separates them again reads as obviously wrong.

Applied by the orchestrator rather than a third builder pass: the fix is a relocation of existing prescribed text with no new mechanism, fully verifiable by reading the four sites. `actions/work.md` Step 7 grants the builder ONE remediation attempt, which was spent on the redesign; that bound exists to cap builder loops, not to require shipping a known data-loss defect.

**Also applied:** a worked example of a populated `coexisting_sessions` array in `actions/work-reference.md` (the only example was the empty case, and finding-and-updating one's own array element is the most complex edit this design asks of a plain read/write agent); and "the same test `actions/code-review.md` already applies" softened to "the same distinction ... already draws", since that file's carve-out is a one-liner rather than an equivalent two-part test.

**Not fixed, accepted:** the holder slot can sit idle for up to 45 minutes when a holder exits while a coexisting session is still live (D-11's documented self-heal window). A session arriving inside that window may be prompted or refused unnecessarily. It delays a decision; it never corrupts one.
